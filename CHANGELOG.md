# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Changed
- **The uptime response time is the median over 24 hours, plus the slowest check, not an average** (owner-approved 2026-10-13). The figure was a plain mean of every Better Stack sample in the last 24 hours, so seven checks near the 30 s timeout out of about 510 turned a 21 ms median into a 282 ms "average". **Figure removed: the 24-hour average response time.** In its place:
  - **SN Systems (desktop), Uptime:** the Monitors line reads "median 21 ms over 24 h" (several monitors: "medians 120 ms to 340 ms over 24 h", one value when they are equal, never a mean of medians; a figure past a second reads in seconds, as "1.5 s"). The Slowest line is now the slowest single check, for example "28 s from Asia · 5h ago" (with the monitor's name when there are several), and shows with one monitor too. It was the monitor with the highest average, shown only with two or more.
  - **S&N Analytics, Uptime monitor details (classic page and native window, one script):** the "Resp." column is now "Median", a new "Slowest" column reads "28 s from Asia, 5h ago" (both in seconds past one second; hours counted down, as on the desktop card; an unreadable time is left out), and the footer says "median and slowest response over 24 h". Anything not read says "not read", never 0.
  - **The `uptime-status` ability and `sn-status{uptime}`:** `response_ms` keeps its name and now carries the median (its description says it was the mean until today); each row gains `median_ms`, `max_ms`, `max_region` (in words: the US, Europe, Asia, Australia; any other code as given) and `max_at` (when, as Better Stack reports it). All null on the light tier and for heartbeats.
  - **Remote MCP door:** `remote-uptime-status` mirrors the new keys (always null remotely: only the admin detail tier reads them), so the payload contract moves 16 to 17. The worker's own CONTRACT_VERSION bump is a separate PR.
  - The 15-minute response cache moved to a new key (`sn_uptime_response_stats`), so a mean cached by the old code is never read as the new figures. The read now lives in `inc/uptime-status-response.php`.

## [2026.10.10] - 2026-10-14 — saves clear only what changed, and deploys mark pages stale

### Changed
- **A note save that changes nothing another page shows no longer empties the whole edge cache.** Since #1850 every save of a published post purged the theme's whole Cloudflare cache tag, which empties every page on the site. In the week to Oct 13 that was 40 save purges, about 5.7 a day, in bursts of 3 to 6 within seconds.
  - **What is compared.** Just before the save, the plugin records what other pages list of the note: title, slug, publish date, status, password, excerpt, the opening 60 words (as the link preview and the index excerpt each strip them), reading time, links to other notes (cited-by), tags and categories, featured image and sticky.
  - **When none of it changed**, and the theme tags each note (juanlentino/signal-and-noise#530), the save purges two tags in one call: the note's own (`sn-note-<ID>`) and the lists' (`sn-lists`). Core's sitemaps still go by URL. A tag clears every copy of the note's page, including share and feed links with `?utm_source=` (each is its own copy at the edge), in every tier; a URL purge would not.
  - **Anything else keeps the whole-tag purge:** a theme without per-note tags, a change to any listed field, a first publish, unpublishing or trashing, a page, or a save whose "before" was never seen (a scheduled note going live). If Cloudflare refuses the two tags outright, the whole tag goes instead.
  - **The post-save probe runs again** after a note purge. Cloudflare's "Old per-URL purge path" note now appears only for a theme that does not tag each note.
  - **Bursts of saves are not merged:** they are separate requests, and merging would mean skipping or delaying a purge.
  - **Ledger:** the purge ledger records the narrow purge as trigger `save`, scope `note`. The `cache-freshness` reading gains `by_scope` (`save:tag` and `save:note`), so the `save` count in `by_trigger` now covers both kinds. A note purge does not move the desktop's "last full edge purge".
  - Pinned by the new tests/cloudflare-purge-save.php and tests/purge-ledger.php.
- **Cache clearing does less damage and says what it did** (cache research, 2026-10-13).
  - **A stale post-save probe purges the whole-site cache tag, not the whole zone.** The `sn-render` tag covers every page, feed and machine file, which is all a stale note page needs; images, styles and scripts stay cached. The zone goes only when Cloudflare refuses the tag call. The probe's "fresh" read now sends a new random `?sn-cache-probe=` value each time, because the fixed `=1` was itself cached at the edge. Under Connections > Cloudflare, Post-purge probes rows read "stale → whole-site tag purge" or "stale → zone purge" (rows from before today were zone purges and still say so), and the box's description names both. Attention says "The whole-site cache tag was purged." for a tag row. The `purge-verification-log` rows gain `escalation` (tag, zone or none).
  - **A theme or plugin update, and a version rollover, mark the zone stale instead of deleting it** (Cloudflare `invalidate_cache`, all plans, same limits as a purge). Cloudflare serves the old copy while each page revalidates, and serves it if the new code fails. Saves, Styles saves, the probe and the manual purge still delete. The Cache box's "Last purge" reads "full zone, marked stale" after one; the ledger row carries scope `invalidate`. 
  - **A stale-probe row in Attention clears once every page was refreshed, by any route.** It used to clear only on a later zone purge, which updates and probes no longer send. Now a confirmed purge of the whole-site tag (a save, a Site Editor save, a probe's escalation) or a confirmed zone invalidate (an update) also counts, recorded as `sn_cf_last_html_refresh`. A note's own tags do not count, and neither does the probe's own escalation seconds after its reading.
  - **Saving, trashing or unpublishing a published navigation menu, template or template part, and deleting one (the Site Editor's "Clear customizations"), purge the whole-site tag** (once per request; each Site Editor save is its own request). Nothing purged on those changes, so a menu or footer edit waited up to the 2-hour edge lifetime. Ledger trigger `site-editor`, scope `tag`. The Cache box's Auto-purge line names these saves and the mark-stale on update, on both surfaces.
  - **The Cloudways app purge is retired by default.** Varnish is off for this app (Cloudways API: `varnish_enabled` false), so the call only emptied Redis, which the manual purge already does, at up to 10 seconds of blocking API calls. `define( 'SN_CLOUDWAYS_APP_PURGE', true )` in wp-config.php turns it back on. Connections > Cloudways reads "Retired" in Last purge and Result, with why; the Cloudflare Cache box's Cloudways purge row reads "Retired" with no "Last attempt" time (that figure is removed while retired, because it would only grow). Purge ledger rows say "retired: Varnish is off for this app" in the Cloudways column instead of relying on the theme to note it.
  - **The Cloudflare Cache box shows "Breeze page cache: on, off or not read"** on both surfaces, from the theme's last purge report (`legs.breeze_page_cache`, theme signal-and-noise#532).
  - **Feeds refresh after a deploy too.** With updates marking pages stale, the edge revalidates each feed with its stored Last-Modified and ETag, which came only from post dates, so the origin answered 304 and the old feed body stayed until the next note. The feed build date now also counts the last render change (a deploy, a Styles save, a purge), as a note page does; the RSS `lastBuildDate` moves with it.
  - The probe ignores its own cache-buster in HTML-escaped (`&amp;`) and URL-encoded (`%3F...%3D`) forms too.
  - URL purges go 100 to a call (was 30), Cloudflare's limit on every plan.
  - Pinned by the new tests/cloudflare-purge-probe-escalate.php, and by tests/cloudflare-purge-send.php, tests/purge-ledger.php, tests/cloudways-purge.php, tests/admin-cloudways.php and tests/os-leaf-connections-cloudflare.php.

### Fixed
- **"More on this" on other notes refreshes after a related-notes rebuild, and two Core Web Vitals failure reasons say only what is true.**
  - **Related notes lag.** About 30 seconds after a save, the related-notes rebuild can change the "More on this" list on OTHER notes. Since the narrow save purge, nothing refreshed those pages, so they kept the old list until the 2-hour edge expiry. Now the rebuild (the one after a save and the daily one) compares every note's related list before and after, and purges only the tags of the notes whose list changed, in one Cloudflare call. Over 100 changed notes, or with a theme that does not tag each note, it purges the whole tag instead. A rebuild that changed no list purges nothing. The purge ledger records it as trigger `related`, scope `note` (or `tag`). Pinned by the new tests/ml-related-purge.php.
  - **Reading time drift.** The narrow save purge compared a freshly counted reading time on both sides, but pages show the stored minutes. Now the "before" is the stored value and the "after" is what the save writes, so a save that corrects a drifted reading time purges the whole tag (the index and link previews show it). Pinned in tests/cloudflare-purge-save.php.
  - **Field vitals failure reason.** When a by-device or by-path read fails, the reason quoted the last Analytics Engine error stored site-wide, which could belong to another read up to 5 minutes old. It is now quoted only when it was recorded during this read; otherwise the reason says "no error was recorded".
  - **Top-paths failure reason.** It quoted up to 200 characters of the database's own error, which can name tables. It now says "the daily analytics table could not be read". Pinned in tests/analytics-vitals.php.

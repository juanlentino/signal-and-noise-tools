# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Added
- **A Health check goes red when a second page cache comes back.** The Cloudflare edge is the only page cache (owner, 2026-10-13), and Breeze is deactivated, but Cloudways can switch it back on. A Breeze page cache serves pages without Cache-Tag, so the tag purges cannot clear them. The new `breeze_active` check (Health surface, Other checks family) reports Breeze in `active_plugins`, or `WP_CACHE` true with a `wp-content/advanced-cache.php` drop-in, and its fix hint says to deactivate Breeze. ## [2026.10.14] - 2026-10-14 — agent runs priced, the Pulse Monitor hears S&N, fourteen big files split

### Added
- **The OpenStation Pulse Monitor now hears Signal & Noise** (OpenStation 1.1.14, Experimental feed). A new, deletable `inc/openstation-pulse.php` hooks the feed only when it exists. The feed-open pixel beats as a visitor (or a bot) when an admin has turned on counting site visitors, and stays off the trace otherwise; the live-now poll reaching origin no longer reads as API use. S&N's own bot classifier can add a bot verdict, so fediverse preview fetchers stop counting as visitors. A Better Stack monitor reporting down counts as a failed request in the health snapshot, read from the cached status only, never the network. It only shows once Pulse has seen 4 or more requests in its 2-minute window, so on a quiet site a down monitor does not move the trace. Two beats: `provenance` on each signing dispatch (failed when the Worker does not answer 2xx) and `cache-purge` on a whole-zone purge (failed only when Cloudflare refused it; a purge queued for a retry is not a failure). Not built, with reasons in `docs/openstation-compat.md`: the analytics beacon (it posts to the Worker at the edge and never reaches WordPress), a cron override (no cached verdict exists, and the 5-minute runner never trips the monitor's 10-minute threshold) and an `sn-apply` beat (the owner's own requests never beat while the owner watches). No URL, IP or user agent is stored or relayed. Pinned in `tests/openstation-pulse.php`.
- **AI › Models & Budget shows what OpenStation agents spent this month, beside Copilot and outside the cap.** OpenStation 1.1.14 adds `usage` and `model` to the agent runner's result, so each `openstation_agent_completed` run (and its `desktop_mode_agent_completed` name) is priced at list rates with the same table as Copilot into a bucket of its own (`sn_ai_agents_spend_month`). A run that reports no usage, no model, or a model with no list price on file is counted in `sn_ai_agents_unpriced_month`, never recorded as $0.00. A station older than 1.1.14 reports no usage for agent runs, so every run there counts as unpriced, and the page says so. The Agents row, its note and the unpriced count paint on the classic page and its native twin. The cap, its meter and the feature rows do not move. The page intro and the cap-reached notice now say Copilot and agents run outside the cap, where they said "except Copilot". Copilot's recorder now shares the pricing helper (`snt_ai_station_price_run()`); its behavior is unchanged.

### Fixed
- **Internal only: the sn_apply surface guard no longer reads a commented-out or orphaned require as real.** `tests/sn-apply-surface-coverage.php` checks that every `inc/sn-apply/` file is required exactly once. Since the parts splits it searched the joined text of the loader and every family file, so two orphan files that required each other read as required, and so did a file whose only require was a comment like `// require_once __DIR__ . '/x.php'`. It now walks from the loader (`inc/abilities-sn-apply.php`) through the shells it reaches and counts only real `require_once __DIR__ . '/...'` lines in those files. Both blind spots now go red (shown with planted files), and a new in-sweep control proves it on every run. No plugin code changed.
- **SN Systems (desktop): a day's edge 5xx that the plugin and theme installs that day explain no longer reads amber or counts toward "to look at".** Each install puts WordPress in maintenance for a few seconds, and the owner's own open admin and OpenStation tabs get a 503 or two each, often counted twice when the rights Worker forwarded them (Oct 8 to 13 measured about 2 to 2.5 per install). The Edge row's value now reads, for example, "5 · 2 installs that day" beside its "5xx · Oct 13" label, in the text color, when every 5xx that UTC day is explained: at least one install recorded that day in the deploy history (`sn_deploy_history`, the same log Deploy Status merges), no more than 3 per install, and every one a 503 on the dashboard (wp-admin, OpenStation and the REST routes its cards poll, the same list the "Your dashboard" row counts), the live poll, wp-cron, wp-login or the favicon, with the day's stored per-path rows accounting for the whole count. A 500, a 522, any 5xx on a front-end page, more than the allowance, or a day stored before the per-path rows stays amber exactly as before. The count stays whole and the Visitors, Day before and Your dashboard rows are unchanged. The rollup has no per-error time, so "during an install" is "on the same UTC day" (the rollup's own day and the row's label; a site-timezone day would pair an evening install with the next UTC day's 503s). Installs come from the deploy history rather than the purge ledger's `update` rows, which also count purges that are not installs; a core or third-party install is not in the history, so its day stays amber. A 503 on a public REST route a reader loads (the feed-open pixel, citations, the provenance credential) stays amber. Live on Oct 13 the row stays amber: 2 of its 5 were 503s on the abilities API, but 2 were 502s on /notes and 1 a 500 on a scanner path. The BREAK alert (`inc/alerts.php`) is unchanged: it judges one real content page at a time, so a maintenance 503 on the dashboard never reached it. No figure removed.

# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

- **Rights evidence posts on its own, after a 72-hour review window, with automatic holds.** Owner-approved. The first daily pass of a month composes the last complete month's records and stores them `composed` with `review_until` (compose + 72 h) and a `summary` `{reads, train}`; it posts nothing. A later pass posts a composed record at or after `review_until` when the month is not held, so a month no longer needs a hold and a lift to go out. A held month still composes (View now streams the stored bytes that would post) and never posts. Two rules hold a month with a stored reason (`sn_rights_evidence_hold_reasons`): a compose or ledger-walk error, which today only stopped the pass; and a per-family `crawling.train` that moved more than 3x either way against the previous month's posted value, both at 50 or more (it applies from the month after this ships, the first with a stored summary). The worker's coming `422 {error:"rights-evidence refused", divergences}` (parallel worker PR) marks the entry `refused`, drops its bytes so they are never re-sent, holds the month with the divergences as the reason, and lets the next pass recompose; a transport failure stays `unanchored` and retried. A backlog month waiting out its window is neither a target nor a failure: it stays queued, uncounted, and leaves once posted. Monitoring > Machine Readers, both twins: per waiting month View, Hold and Post now (the owner's bypass of the window, behind a confirm; `rights_evidence_hold`, `rights_evidence_post_now`, map 78 to 80), per held month the rule's reason and Lift (which now clears the reason); the status line names the months in review. A new watch, `rights_evidence_review`, ripens on a waiting month (with the hours left) or a rule's hold (with the reason), so the morning brief carries it; no email. The `rights-evidence` read reports `review_until`, `summary`, `divergences`, `hold_reasons` and `in_review`; `rights-evidence-now` says it posts only past the window and reports `in_review` and `refused`. Pins changed with the intent kept (held never posts): H1 (a held month composes, posts nothing), H2 (the held pass now takes and releases the lock), H4 (an unheld month enters its window), plus D1/D8, E1 to E4, I6, K4 and K5, whose first pass no longer posts. `docs/MACHINE-READERS.md` (new section: the review window, holds and refusals). `tests/rights-evidence.php`, `tests/rights-evidence-admin.php` and `tests/watches.php` pin it.

## [20.2.0] - 2026-10-01 — who the crawlers say they are


- **Rights evidence schema 2: the identity block.** Owner rulings 2026-10-01: `crawling.reads` and `crawling.train` stay totals by claimed user agent, and every schema-2 record now carries `identity: {basis: "claimed user agent", verification: {source: "cloudflare verified bot category", since: "2026-09-27T15:49:59Z"}, crawling: {reads, train} each as {verified, unverified, unverifiable}, rights_files: "claimed user agent; the rights stream records no verification"}`, the shape the ledger checker (signal-and-noise-provenance #35) requires for schema 2. `since` is a sensor fact, the first aggregate row with a non-empty `verified_bot` (`SN_RIGHTS_EVIDENCE_VERIFIED_SINCE`). Aggregate rows are per day, so a day wholly at or after `since` counts as verified (Cloudflare's verified-bot category set) or unverified (empty), and earlier days plus the partial start day (2026-09-27) count as unverifiable. Each triple sums to its crawling count, no train component exceeds its reads component, a window ending before `since` is all unverifiable and one starting after it has nothing unverifiable. Composed in `sn_rights_evidence_compose()` (pure); the dry run and the View download carry it. The normalizer already kept `verified_bot`; it is now pinned on a worker-shaped row. A composed September-shaped payload and the August one pass the ledger's `evidenceDivergences()`, with three broken controls refused. `docs/MACHINE-READERS.md` (new Identity section, plus the cache-generation, per-ledger cache and dry-run window notes from the follow-ups below) and the 2026-10-01 handoff are updated. `tests/rights-evidence.php` (141) and `tests/machine-readers-api.php` (67) pin it, 7 mutations red.

- **Rights evidence: eight review follow-ups to 20.0.0/20.1.0.** (1) The daily refresh no longer takes a ledger file (or a worker reply) saying `confirmed` without a numeric `bitcoin_block` as final: one predicate, `sn_rights_evidence_is_final()`, makes a record final only when conflict, retracted, or confirmed with its block, so a blockless confirmation keeps being re-read. (2) One malformed row in the ledger index's `rights_signals` (no slug, an unsafe slug, no positive version) now refuses the whole rights-signal history before any read, instead of silently dropping that signal from the reservation. (3) The 12-read refresh cap rotates: non-final records are read in month/family order starting after the last key the previous pass read (option `sn_rights_evidence_refresh_cursor`), wrapping, so every one is re-read in turn. (4) The permanent rights-signal version cache in `sn_rights_evidence_chain` is keyed by the ledger's base URL, so switching `sn_prov_ledger_owner`/`sn_prov_ledger_repo` never reuses another ledger's versions; block times stay shared. (5) The Machine Readers cache flush no longer deletes 90 windows x every AI-training family of hypothetical filtered keys on each settings save: a filtered key carries a generation (`snt_mr_cache_gen`) that the flush bumps, so every filtered read still refetches; the unfiltered keys and their 360 deletes are unchanged. (6) A backlog month that keeps failing can no longer starve the current month: after 7 failing passes in a row on one backlog month (`sn_rights_evidence_backlog_fails`), the next pass works the current month when it is not held, the backlog month stays queued and its count restarts; a held current month was already queued before the backlog target is chosen, now pinned. (7) `wp sn rights-evidence dry-run` refuses the current month, future months and months whose start is past the sensor's 90-day window, with a clear error and no sensor read. (8) The erratum is driven by the stored records: every v1 with a ledger path (retracted included, a 409 conflict excluded) gets its erratum, with the reservation composed once from the ledger and no sensor read. Nothing is posted by this change. A slug listed twice in `rights_signals` also refuses the history, and the backlog failure counter is consumed only once the pass holds its lock (a pass that finds the lock held leaves it untouched). `tests/rights-evidence.php` and `tests/machine-readers-api.php` pin it, 20 mutations red.

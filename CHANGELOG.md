# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Fixed
- **SN Systems (desktop): a day's edge 5xx that the plugin and theme installs that day explain no longer reads amber or counts toward "to look at".** Each install puts WordPress in maintenance for a few seconds, and the owner's own open admin and OpenStation tabs get a 503 or two each, often counted twice when the rights Worker forwarded them (Oct 8 to 13 measured about 2 to 2.5 per install). The Edge row's value now reads, for example, "5 · 2 installs that day" beside its "5xx · Oct 13" label, in the text color, when every 5xx that UTC day is explained: at least one install recorded that day in the deploy history (`sn_deploy_history`, the same log Deploy Status merges), no more than 3 per install, and every one a 503 on the dashboard (wp-admin, OpenStation and the REST routes its cards poll, the same list the "Your dashboard" row counts), the live poll, wp-cron, wp-login or the favicon, with the day's stored per-path rows accounting for the whole count. A 500, a 522, any 5xx on a front-end page, more than the allowance, or a day stored before the per-path rows stays amber exactly as before. The count stays whole and the Visitors, Day before and Your dashboard rows are unchanged. The rollup has no per-error time, so "during an install" is "on the same UTC day" (the rollup's own day and the row's label; a site-timezone day would pair an evening install with the next UTC day's 503s). Installs come from the deploy history rather than the purge ledger's `update` rows, which also count purges that are not installs; a core or third-party install is not in the history, so its day stays amber. A 503 on a public REST route a reader loads (the feed-open pixel, citations, the provenance credential) stays amber. Live on Oct 13 the row stays amber: 2 of its 5 were 503s on the abilities API, but 2 were 502s on /notes and 1 a 500 on a scanner path. The BREAK alert (`inc/alerts.php`) is unchanged: it judges one real content page at a time, so a maintenance 503 on the dashboard never reached it. No figure removed.

## [2026.10.13] - 2026-10-14 — the queue says how far it runs, and cards ride out installs

### Added
- **SN Queue (desktop) and Connections › Scheduled: the runway** (queue calendar phase 2, item 6; owner-approved 2026-10-14). How far ahead the schedule covers, in one sentence: "Covered through Jan 25, 2027 (103 days)". The date is the last scheduled note's day; the days are calendar days from today, both in the site timezone. Unknowns are said in words: "Not covered: nothing is scheduled." or "Not covered: the last scheduled note, Oct 12, is overdue." On the card the sentence replaces the depth line ("25 scheduled · to Jan 25, 2027") in the same row, and the scheduled count moves beside the drafts as secondary text ("25 scheduled · 0 drafts"). The count and the date are still on the card, so no figure is removed. The sentence cannot share its row below about 360px wide, so the card's default height goes from 640 to 650: the row is 19px taller with its row gap (measured in review), and 627 + 19 = 646 fits (a saved layout keeps its own size). An empty queue is said once: the card's "Nothing scheduled" stands alone, with no runway line and no "0 scheduled" under it. Both Scheduled twins gain a **Runway** box with the same sentence and the count. The `content-queue` ability gains `runway` (`through`, `days`, `text`) in its payload, description and schema. The twins count from `wp_count_posts()`, the card's own source. Days are counted from the dates, not the instants, so a timezone whose DST switch happens at midnight (Santiago, Havana, Beirut, Cairo, the Azores) no longer loses a day; the same fix applies to the Cadence lines (two notes 2 days apart there read as a cluster) and the Suggested slots (the usual spacing read a day short). Read-only; dates only. Live today: "Covered through Jan 25, 2027 (103 days)", 25 scheduled.

### Fixed
- **SN Deploy, SN Systems, SN Traffic and SN Queue (desktop): a plugin or theme install no longer flips the cards to their error state.** While WordPress is in maintenance mode it answers every request with a 503 for a few seconds, and this week's edge errors were mostly those 503s, hit by the owner's own open desktop. A 503, or a request that got no answer (offline, a dropped connection, an HTML page where JSON was due), is now a brief miss: the card keeps its reading exactly as it was (no recolor, no warning glyph, no alert) and adds one line in the plain text color, "Updating, retrying.", then tries again after 5 s, 15 s and 30 s. Only a fourth miss in a row shows the card's existing error state, and the next try then waits the card's ordinary period (it waited 1 to 5 minutes from the first miss before). WordPress's Retry-After: 600 is a header the cards never read, and a brief miss honors no retry hint either way; a 429's `retry_after` is still honored. On SN Systems, the Health, Cron, Edge and Cache lines' re-read stays quiet while the uptime check is on that ladder, and a miss of that re-read is painted only once the uptime read settles, so the live verdict never says "not re-read" and then takes it back. SN Queue arms no retry while its tab is hidden. An HTML 403 or 429 through `wp.apiFetch` loses its status and so counts as brief too (about 50 s more before its error, 3 extra requests), accepted. The rule lives once, in `assets/snt-poll-cadence.js` (`brief`, `briefWait`); a card loaded without it keeps today's behavior. Left as they were: the pulse (no card of its own; it already backs off), SN Reading and SN Anchors (a failed re-read already leaves the card as it was), the live figures (a failed read already keeps them, and the next read is 30 s away), and OpenStation's own session poll. No figure removed.
- **The Colophon's numbered headings fall back to the theme's full body font stack** ('DM Mono', 'Courier New', monospace). The fallback had dropped 'Courier New' since #1935; tests/token-governance.php catches this only where the theme sits beside the plugin, which CI does not have. No visible change while DM Mono loads.
- **Uptime (phone, remote twin, desktop card's light read): availability, 30-day incidents and 90-day availability refill right after a plugin or theme update, not on a later cron run.** The update purge clears the transient group, so `sn-status{uptime}` and `uptime-status` without detail read those three figures null. The refill queued for it waited for the first admin page load and then the next cron tick, and the hourly warmer could be up to an hour away. The purge chain (`sn_after_full_cache_flush`) now queues one warmer run due now and spawns cron at once, the way the live poll does for an overdue refresh. Purges in a row still queue one run (WordPress refuses a second within 10 minutes); a purge that keeps the transients (a styles save) queues nothing; without a Better Stack token nothing is queued. No figure removed.
- **SN Traffic (desktop) and every live figure: "Reading now" recovers on the next poll after a plugin update, not up to 5 minutes later.** An update clears the realtime cache, and the refresh already queued for it can lose its run to the update's maintenance mode. Each poll then saw "a refresh is already queued" and did nothing, so the card read "Reading now: not read" with no "Today so far" row until the host's next 5-minute system cron (seen live on 2026.10.12: cache purged at 08:02 UTC, refilled at 08:05). A poll that finds the cache stale and its queued refresh overdue now runs it at once (WordPress's own cron lock still allows one run at a time). No figure removed.

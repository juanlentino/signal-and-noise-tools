# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

- **Impostor reads are counted but not credited.** A read that names a crawler Cloudflare verifies when genuine (the rights-signals taxonomy's new `cf_verified`, taxonomy 1.5.0: the agents Cloudflare's verified-bots directory lists) and that Cloudflare did not verify, on a day verification was recorded, now stays in `total` and is credited to no vendor, family or purpose, exactly like a control token. It is listed apart as `impostors` (`{agent, hits, networks, basis: inferred}`; a rule decided it, so never `claimed`), crosstab cells gain `impostor_hits`, and lanes file it as `claimed_bot` / `impostor`. A verified read is never one, whatever its network (Claude-User from Google Cloud stays credited), nor is a read before the since date, this site's own tools, an agent the directory does not list (PerplexityBot, CCBot, Bytespider, cohere-ai stay credited, unverified), or a row from a sensor that sends no `cf_verified`. Reader anomalies keep impostor reads in their series, so the co-movement that found them still fires, and the "is this crawler real" table still shows them. Machine Readers' Reader evidence (both twins), the public stats page and the desktop widget each add one line: "Claimed a known crawler but failed Cloudflare's check". Over the 14 days to 2026-10-18 that is about 7,600 reads, among them 1,378 of ClaudeBot's 1,436 and 768 of Googlebot's 1,202. Remote contract 19: the machine-readers summary twin gains `impostors` (additive); the remote MCP worker's `CONTRACT_VERSION` bump is a separate PR.

## [2026.10.41] - 2026-10-18 — BREAKING: audit abilities report the login guard, not LLAR; security watches, change log and file integrity


- **Author archives answer 404 to visitors who are not signed in.** `/notes/author/<slug>/` answered 200 for the real author and 404 for a made-up one, so anyone could guess the author slug and have it confirmed, and that slug can be the login username. Nothing on the site links an author archive. Now a real one answers the same 404 as a fake one; signed-in users still see them, and the `sn_security_block_author_enum` filter switches this off along with the `?author=` guard.

- **oEmbed no longer publishes the author archive link.** Every oEmbed response carried `author_url`, a link whose last segment is the author slug, and it was the one public surface on the site that published it; when that slug matches the login username, it is half of a login guess. The link is dropped; the display name, which every byline already shows, and the embed itself stay.

- **The Audit log now records account and site setting changes.** Nothing recorded them before. New accounts, role changes (set, added, removed), an account's email changing, turning open registration on or off, the default role and the site admin email changing, plugin activation, deactivation and deletion, and theme switches each add one row to the existing audit log: when, what, the account or item it touched, and the signed-in user who made it. Rows are kept for the retention window and capped at 200 (oldest dropped), and the daily prune and Prune now delete old ones and say how many. No IP address, no email address (old or new) and no password is stored. A new administrator account, a role change to administrator and a default role of administrator are marked as the most important kind: they lead the finding sentence and carry an **admin access** pill. Both twins show an **Account and site changes (last 30 days)** table with the same words, the CSV/JSON export gains a `changes` section (the ability export masks the people in it unless `include_pii` is passed), `signal-noise/run-audit-prune` returns `change_rows_dropped`, and the weekly digest (off unless enabled) prints the week's count with the administrator ones named, and no longer calls a week with changes quiet. The hooks only observe; they never block or alter a change.

- **The Cloudflare posture record no longer stores custom WAF rule expressions.** It kept the first 400 characters of each one and read them out through sn-status, and an expression can name the login address. It now keeps only what is asked of it (whether a rule targets the abilities API). A record stored before this change is cleaned on read until the next refresh rewrites it.

- **The application-password and administrator-2FA watches name accounts by display name and user ID, not login username.** The login username can be the secret half of a credential, and watch notes travel through the MCP tools.

- **A watch and a Site Health test for a published login username.** The site already locks the REST users list and the `?author=` scan, but oEmbed publishes each author's slug (`user_nicename`) in its author link, and that archive answers. Core derives the slug from the login username when a user is created, so unless someone changed it, the slug is the login. The new `public_username` watch and the "Signal & Noise public username check" row in Site Health compare the two core fields for every administrator, live, ignoring case and core's slugging. They name user IDs only, never either value. Core has no profile field for the slug (Nickname and "Display name publicly as" set other fields), so the note gives the WP-CLI command: `wp user update <ID> --user_nicename=<new-slug>`.

- **A daily, read-only file integrity check.** Nothing compared installed files with their published checksums: core does it only while updating itself, and Site Health has no such test. Once a day the plugin now compares core files with core's own checksums (`get_core_checksums()`) and plugins hosted on wordpress.org with the plugin checksums API. Plugins not on wordpress.org, this site's private plugins among them, count as not checkable. A file and time budget keeps a run short. The new `file_integrity` watch turns ripe when a core or plugin file is modified, an unexpected PHP file sits in `wp-admin/` or `wp-includes/`, core checksums could not be fetched, the run ran out of budget inside core, or the check has not run for two days. A missing core file alone is reported but not ripe, since hosts delete `readme.html`. It stores counts and up to 20 relative paths (`sn_file_integrity_last`), never file contents. The job is in the cron dashboard registry and is cleared on deactivation.

- **Cloudflare edge posture now reads its three blind spots.** The daily posture read adds the Free Managed Ruleset (is a rule that runs it deployed and enabled), the one rate-limit rule (does it exist, is it enabled, what does it do, and is its expression non-empty: it silently matched nothing until 2026-09-27; the expression itself is never stored or shown), and leaked credentials detection (on or off). All three use the Zone WAF Read permission the custom rules read already needs. Each is a row in Security › Firewall (native and classic), a field in the sn-status `cloudflare` section, and a finding in the Cloudflare edge posture health check when it is off, missing, disabled or matches nothing. A read the token cannot make says "unavailable (needs Zone › Zone WAF › Read)", never off or zero, and a phase with nothing deployed (Cloudflare answers 404) reads as missing, not as a failed read. Read-only.

- **Lockouts on the Audit log come from our own login guard, not Limit Login Attempts.** That plugin is no longer installed, so the audit log stops reading its options. The lockout facts are now the login guard's own decisions over the last 7 days: lockouts, throttles and account throttles, read from the cached login-defense headline (`sn_login_defense_headline()` now carries `locked_out`, `throttled` and `account_throttled`; a headline cached before that is read again, never served as zeros). The box on both twins is **Login lockouts (login guard)** and links to Security, Login defense; the glance card reads **Lockouts (7 days)**. A failed guard read says "unavailable" and an absent one "not configured", never 0. The weekly digest prints lockouts, throttled and account throttled under **Login guard (edge layer)**, drops the audit section's Lockouts line, says "unavailable" when the guard's log cannot be read, and no longer calls a week with a lockout quiet. The daily prune no longer polls for lockouts, and `inc/audit-log-lla.php` is deleted. The old `lockout_triggered` day counter is no longer written or shown in the 30-day table; old days keep it, and the counters reader and the CSV/JSON export still return it. **Ability change:** `signal-noise/run-audit-prune` no longer returns `lla_delta`, and `signal-noise/get-audit-log` view=summary returns `guard` (`state`: ok, unavailable or unconfigured, plus the three counts) in place of `lla`. The ⌘K audit summary toast reads the guard's lockouts.

- **Three security watches: application passwords, administrator 2FA, and the login guard routes.** They watch and never enforce; LLAR, Two Factor and Cloudflare keep doing that. **`app_passwords`** reads core's application passwords. They are the one standing credential that signs in to the REST API without the login address, Two Factor or a passkey. The watch turns ripe when one was created this week, or one has gone unused for 90 days, and names the user and the app, never the secret. **`admin_2fa`** reads Two Factor, where the WebAuthn provider plugin adds passkeys. It turns ripe when Two Factor is inactive, or an administrator has nothing stronger than email codes or backup codes. **`guard_routes`** reads the Cloudflare routes once a day. It turns ripe when the login address's routes no longer point at the login guard, a retired address's route is left over, Cloudflare cannot be read, or the check has not run for two days. It stores counts only, never route patterns; saving the Login URL again restores and prunes the routes.

- **The 404 a stranger gets at `/wp-admin/` now looks like every other 404.** It was rendered while WordPress still counted the request as admin, and in the admin core leaves out the block stylesheets: the header's navigation collapsed into its overlay menu at desktop width, and the page lacked the `error404` body class. The plugin now switches the request to front-end context before rendering the theme's 404 (`sn_login_front_context()`), so `/wp-admin/`, `/wp-login.php`, customize.php and a random dead link all answer with the same page. That also stops the admin routes from giving themselves away by looking different.

- **The login-address leak check no longer reads a blind run as clean.** If most of the public pages it reads fail to load (for example when the server cannot reach itself), the `login_door_leak` watch now turns ripe and says how many pages it managed to read. Before, a run that read nothing reported clean.

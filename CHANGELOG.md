# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Changed
- **sn-status takes the single tools' inputs.** The 2026-10-24 wave-4 read retired nothing: none of the eight absorbed singles had collapsed, and the reason was input, not habit. sn-status could not force a fresh deploy or uptime read, ask for uptime's full payload, filter the scheduled cron list, or size cron history, so a caller needing any of that fell back to `get-deploy-status`, `uptime-status`, `list-cron-events` or `get-cron-history`. It now takes `force_refresh` (deploy, uptime), `detail` (uptime), `sn_only` and `hook` (cron_scheduled) and `limit` (cron_history), each forwarded only to the source that declares it and only when set, so a bare request dispatches exactly as before. One behavior change: a request with `hook` that names cron_scheduled now gets that hook's events only. `get-analytics-events` was already off the door (19.3.0); its 2 calls in the window predate that. The `wave4_telemetry` watch moves to 2026-11-25.

## [2026.10.64] - 2026-10-25 — built on core: robots, canonical, feeds, app passwords, AI spend

### Changed (discovery on core, 2026-10-24)
- **Core prints the robots meta again.** The plugin removed `wp_robots()` and printed its own tag; it now hands the same directives to core through one `wp_robots` filter (`sn_seo_wp_robots()`), so core's own noindex runs again where the plugin had silenced it: a private site (`blog_public`), core search results, `?replytocom` and unapproved-comment previews. `sn_seo_robots_directives` stays the seam (the theme's notes-search noindex rides it). The tag now reads in core's format (`max-image-preview:large, max-snippet:-1, max-video-preview:-1`); the directive set is unchanged on every public page kind (home, a note, a page, tag archives, `/notes/` and its pages, `/notes/tags/`, the notes search, 404, MailPoet).
- **Core prints the canonical on singular views.** `rel_canonical()` is no longer removed: the per-post `_sn_canonical_url` override, MailPoet's no-canonical and the paged `/notes/` self-canonical go through `get_canonical_url` (`sn_seo_canonical_url()`), and core adds what the plugin lacked: page 2 of a note split with `<!--nextpage-->` canonicalizes to its own `/2/` URL, not to page 1. The plugin still prints it where core prints none (the posts page, tag archives, `/notes/tags/`). One canonical per page kind, pinned with core's own printers in `tests/seo-head-on-core.php`.
- **A feed's conditional GET is core's alone.** The plugin sent a second Last-Modified and ETag on top of core's `WP::send_headers()` and answered 304 to a mismatched ETag with a fresh If-Modified-Since (RFC 9110 says the ETag wins). Its validator is deleted; the last render change reaches core's through `get_lastpostmodified` (`sn_seo_feed_lastpostmodified()`), so a deploy still moves the feed validator. `get_feed_build_date` still dates `<lastBuildDate>`.
- **A feed 304 is counted.** Core's 304 exits before `template_redirect`, so the RSS tracker now counts on `wp_headers`, the last hook before that exit: a 200 and a 304 are each counted once. The feed `X-Robots-Tag` moved to the same filter, so a 304 carries it too. `tests/feed-conditional-get.php` runs core's real `send_headers()`.
- **The change in counting is dated and labeled.** On origin/main a 304 core answered was never counted, so totals step up from the deploy. The first count under the new method stores its UTC day once (`sn_rss_tracker_304_since`, via `add_option`); `get-rss-stats` (and `sn-metrics{rss_stats}`, which carries its payload) returns it as `data.counts_304_since`, and the wp-admin RSS view and its OpenStation twin both say "Conditional fetches (304) are counted since <date> (UTC), so a step up from that day is measurement, not growth." The key is local-door only: `remote-get-rss-stats` keeps the shared callback and its schema, so `SN_REMOTE_CONTRACT_VERSION` does not move (the edge-errors `installs_by_day` precedent).
- Dead The SEO Framework checks are gone from the touched files (TSF was removed 2026-05-17). `tools/fetch-wp-test-core.sh` also fetches `robots-template.php`, `link-template.php`, `class-wp.php` and `post.php` for the two suites.

### Added (built on core hooks, 2026-10-24)
- **App passwords reach the audit log.** An app password skips the login door, the edge guard and 2FA, and a refused Basic-auth sign-in never fires `wp_login_failed` (core calls `wp_authenticate_application_password()` straight from `determine_current_user`), so none of it was recorded. Core's `application_password_did_authenticate` and `application_password_failed_authentication` now count sign-ins per day (`app_password_ok`, `app_password_failed` beside the MFA fields in the counters view, the export and the weekly digest), in their own small option with autoload off so the MCP door, which signs in on every call, never rewrites the autoloaded audit blob. The first refusal of each reason code on a day is a row in the changes list, and when the list is over its 200-row cap those refusal rows are trimmed before any real change (`snt_audit_trim_changes()`), so a spray cannot push real changes out; it is not counted as a change (`snt_audit_is_change_row()`, used by the audit log finding on both twins and by the digest). `wp_create_application_password`, `wp_update_application_password` and `wp_delete_application_password` are change rows on the account (an administrator account is marked high). Never stored: the attempted username, any password or hash, the uuid, an IP address. The auth callbacks never ask who is signed in, since that would re-enter `determine_current_user`, and a nested pass (another plugin asking on `updated_option`) is dropped instead of recursing.
- **The last mail refusal, in the weekly digest.** Core's `wp_mail_failed` now keeps the time, the error code and the message (trimmed, any address taken out; the recipient, subject and body in the error data are never read), and `wp_mail_succeeded` counts. When the mail server refused a message in the last 7 days, the digest says so and how many it accepted, worded as a handover, not an inbox delivery.
- **Core's cron errors in cron history.** `cron_reschedule_event_error` and `cron_unschedule_event_error` (wp-cron.php, since 6.1) are now failed rows for the event's hook with the step, code and message, so a recurring job that will not come back shows up beside its last run.

### Changed (built on core, 2026-10-24)
- **The auto-update readout asks core.** `get-deploy-status` core.auto_updates now reads `WP_Automatic_Updater::is_disabled()` (loaded on the read only) instead of a copy of it; the copy missed `wp_installing()`. The major/minor answer stays ours, from the same constant, option and filters.
- **One lock on the anonymous users route, and it answers core's 404.** `inc/security-headers.php` also 401'd `/wp/v2/users` on `rest_authentication_errors` by a `REQUEST_URI` substring; it answered first and hid the route removal in `inc/rest-hardening.php`, and it was the weaker control (live, `/wp-json/WP/V2/Users` walked past it to the removal's 404). It is retired with its `sn_security_lock_rest_users` switch. Anonymous `/wp/v2/users`, `/wp/v2/users/{id}` and `/wp/v2/users/me` now answer `rest_no_route` 404 on both URL spellings; `docs/REST-HARDENING.md` and `docs/security/rest-audit-verification.sh` say so.

### Fixed
- The WP-Cron offload docblock said `spawn_cron()` reads `DISABLE_WP_CRON` during `init`; since 6.9 `wp_cron()` only queues `_wp_cron()` for `shutdown`, which is where the constant is read.
- **A page published on a path a redirect holds takes it back.** The redirect handler runs before core resolves the page, so a store entry left on a path (a page renamed away from it, then a new page published or restored there) hid the live page. A page entering publish now removes any store entry on its own path: a live page wins over a redirect (owner, 2026-10-24).
- **The ai/ai dedupe docblock no longer calls an existing-terms tag mode future.** The AI plugin's Content Classification has offered "Only suggest existing terms" since it landed in 0.7.0 (read at the 0.7.0 and 1.0.2 tags). Comment only; both dedupe filters are unchanged. Pinned in `tests/ai-ai-dedupe.php`.

### Changed (content built on core, 2026-10-24)
- **A tag merge hands the reassignment to core.** `sn_tag_merge()` re-implemented what core's `wp_delete_term()` already does with `default` and `force_default`: give every post carrying the old tag the canonical, then delete the old tag. It now makes that one call per source tag. `posts_moved` is still counted from `get_objects_in_term()` before each delete, since core returns no list; the history entry and the old-slug redirect map are recorded as before.
- **A renamed or re-parented page keeps its old URL.** Core keeps a renamed post reachable but skips hierarchical types, so a page whose slug or parent changed, and every page under it, 404ed at its old path (the Search Console 404s that grew `inc/legacy-page-redirects.php`). A `post_updated` hook (`inc/page-rename-redirects.php`) now records a 301 from each retired path to the new one in the redirect store, where Site > Redirects lists it like any other entry. Published before and after only (no drafts, no unpublish, no trash); each published descendant moves at its own path; an old path another published page now holds is never recorded; a redirect sitting on a moved page's new path is removed (it would hide the page, and after a rename back it is half of a loop), owner entries included; entries aimed at an old path are repointed so every redirect stays one hop.
- **Each provenance commit records the core revision saved with it.** `sn_prov_record()` stores the newest core revision id as `core_revision_id` beside the signed payload, the way `change_class` sits there: outside the hashed bytes, so no content hash, signature, Worker body or ledger record changes (a test proves the hash and canonical bytes are identical with and without it). anchor-status in-flight rows carry it, and the note dossier's Edits table (sn-posts `include_dossier`) gains a Core revision column. The id is a pointer, not evidence: core prunes revisions, so a stored id may name one that no longer exists, and the dossier says so. Revisions off for a post means no id.

### Fixed (content built on core, 2026-10-24)
- **The legacy page map no longer says 404 slug guessing is off.** Its header said general 404 slug guessing was "deliberately disabled site-wide". Nothing hooks `do_redirect_guess_404_permalink` (neither this plugin nor the theme ever has), so core's prefix guessing is on. The behavior is unchanged; whether to keep it is an open owner question.

### Changed (AI on core, 2026-10-24)
- **Copilot and agent spend come from core's AI event, call by call, and every other AI call has a row of its own.** Core 7.0 fires `wp_ai_client_after_generate_result` after every AI Client call with that call's token usage and the model the provider actually served (`PromptBuilder::generateResult()`). `inc/ai-copilot-spend.php` now prices each call from it, so a run that switches models is priced at each model's own rate (the station hooks summed the run and priced it at the last model's rate), the Copilot follow-up leg is priced (it reported no usage), and agent spend no longer needs OpenStation 1.1.14. Attribution reads `$context['source']` off OpenStation's `openstation_ai_model_config` filter, a pass-through that fires right before the station generates, handed to the call through core's before and after events so a call that fails inside the provider cannot lend its label to the next one: `ai-copilot/search` and `ai-copilot/followup` are Copilot, `agents/runner` is Agents, and everything else (agent drafting, the MIO window, the Drafts widget, comment analysis, the AI plugin's features, any unlabeled call) lands in a new Other AI bucket (`sn_ai_other_spend_month`, `sn_ai_other_unpriced_month`), never dropped. The plugin's own calls stay out: `snt_ai_generate_with_constraints()` holds `snt_ai_own_call_depth()` above zero around its generate call, which `inc/ai-bootstrap/usage-log.php` already prices into the cap's ledger. The `openstation_ai_search_completed` and `openstation_agent_completed` spend subscribers are removed: the core event carries everything they did, per call (the agent telemetry subscriber on `openstation_agent_completed` is untouched). Cache tokens are still summed into input by the provider (WordPress/ai-provider-for-anthropic#33), so every prompt token is priced at the fresh input rate, as before. AI › Models & Budget, classic and native, paints the Other AI row beside Copilot and Agents, outside the cap; the unpriced hints count calls, not turns or runs, and the Agents note no longer says a pre-1.1.14 station is unpriced. Pinned: `tests/ai-copilot-spend.php` (rewritten on the core event, 23 red on main), `tests/os-leaf-ai-models-budget.php` (10 red on main).
- **The cap-reached notice says what the cap pauses (owner call A, 2026-10-24: the cap is plugin-only).** It said Copilot and agents run outside the cap and every other AI feature is paused, which was never true of the AI plugin's features. Both twins now say the AI features of this plugin pause until the next calendar month or until the cap is raised, while Copilot, Agents and the AI plugin keep running, their spend listed separately and not counted against the cap (no position word: `tests/positional-words-batch7.php` bans them in leaf strings). The cap itself is unchanged. Pinned in `tests/os-leaf-ai-models-budget.php` (3 red on the old wording).

### Security
- **The official mcp-adapter's transport floor is raised to `manage_options`.** Its default server (the one the AI plugin's MCP Access experiment installs) passes no permission callback, so `HttpTransport::check_permission()` falls back to `mcp_adapter_default_transport_permission_user_capability`, default `read`: any logged-in subscriber reached the transport. Our own MCP doors require `manage_options`; `sn_mcp_adapter_transport_floor()` holds the adapter to the same floor. Inert while the adapter is absent. Pinned in `tests/mcp-endpoint.php` (red on main).

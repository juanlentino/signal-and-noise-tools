# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Added
- **Hacker News is asked directly.** A referrer undercounts Hacker News (its apps send none) and a submission by someone else is invisible until traffic arrives. Inside the hourly alert run, the Algolia search API finds any story whose URL is on this site and the official API gives its live points, comments and front-page position for its first three days; both are public, need no key, and receive only the site's host name. A story found young mails once (`HACKER NEWS: "..." was posted to Hacker News: 14 points, 3 comments`), reaching the front page mails once more, and a spike on a path Hacker News holds says so in its line. Stories that predate the first run are stored as history, not mailed. `inc/hn-mentions.php`; pinned in `tests/hn-mentions.php`.

## [20.9.0] - 2026-10-03 — the cache runs itself

### Removed
- **The cache status and the purge buttons leave the admin; the command stays (owner, 2026-10-03).** Purging is automated, so a readout that says "fresh" all day and a button nobody should need are noise. Gone: the "Last purge" cell in the classic S&N Operations box (and its helper `snt_dash_freshness_compare()`), the desktop SN Cache widget (`sn-cache`, its script, the localized `cacheFreshness` key and the `snt-cache-purged` event only it listened for), the Caches card on the Dashboard systems wall on both surfaces (`snt_freshness_card()`, with `inc/freshness-indicator.php`, `assets/freshness-dot.js`, its `sn-freshness-dot` handle in the desktop window and the id and filler class the wall carried only for it; the wall is server-rendered cells now and reflows by itself with one card fewer), and every "Purge all caches" button: the two admin bar items (Purge All Caches, Purge Cloudflare) with their admin-ajax handlers, the Operations box action, the Maintenance toolbar on the Dashboard leaf and on both classic screens, the purge card under Connections › Cloudflare on both leaves, and the Quick Actions widget button. A saved desktop layout that still names `sn-cache` is harmless: OpenStation mounts only ids its registry knows, the way `sn-pulse` went in 9.53.0. What stays: the `signal-noise/purge-all-caches` ability and its MCP exposure, the command palette entries (`SN: Purge all caches` in wp-admin and on the desktop), the `purge_caches` and `cf_purge_now` form handlers (a stale form post still lands), Full reset, the purge log (`sn-status{cache}`, the purge ledger, the probes and Last purge rows under Connections › Cloudflare, the `cache-freshness` and `purge-verification-log` abilities) and the per-note Purge edge action. The cache now speaks only when the automation failed: the attention queue's edge reader keeps its stale-render rows and adds one for a purge Cloudflare refused, "Cloudflare did not accept a cache refresh (HTTP 403)", read from `sn_cf_purge_failure()` when that function exists (it ships separately). Pinned in `tests/desktop-mode-integration.php`, `tests/openstation-app-attention.php`, `tests/os-leaf-connections-cloudflare.php`, `tests/admin-bar-quick-actions.php`, `tests/dash-freshness-compare.php`, `tests/dash-screen.php`, `tests/os-leaf-dashboard-systems-wall.php`, `tests/admin-tab-dashboard-glance.php` and `tests/openstation-host.php`.

### Added
- **An alert is a system notification in the app.** The hourly alert run stores the headline it mails (`snt_alerts_notice`); the OpenStation app, on desktop or phone, shows it through `wp.os.notify` once per device, on load, when the app comes back into view and every fifteen minutes while it is open. A tap opens Analytics for a spike or a break and the attention list for a refused cache refresh. Only while the app is open: OpenStation v1 has no Web Push (its docs list it as a later phase), so the email stays the channel that reaches a closed app. `inc/alerts-notice.php`, `assets/snt-alert-notify.js`.

### Changed
- **Every Cloudflare purge reads the answer.** Automatic purges were fire-and-forget: a non-blocking call whose response nobody read, so a rejected token, a throttle or a timeout looked like success, and the only thing that could notice was the post-save probe finding a stale page two minutes later (3 of the last 20 saves). Each call now blocks and is read. A transport error, a 429 or a Cloudflare 5xx is retried after 1, 5 and 15 minutes; a failure time cannot fix (a 4xx), or the fourth failed try, is recorded in `sn_cf_purge_failure` and cleared by the next confirmed call. A refused call is no longer stamped as a purge or marked on the ledger's edge leg; a retry WordPress cannot store is recorded as a failure; the record clears only when a confirmed call covers what failed (the whole zone, or the same call); a confirmed zone refresh cancels narrower retries still waiting, and a retry that succeeds later writes its own ledger row. `inc/cloudflare-purge-send.php`; pinned in `tests/cloudflare-purge-send.php`.
- **A page is not "not modified" after the code that renders it changed.** A note answered a conditional request 304 whenever the request's date was at or after the post's own modified date. The edge revalidates with the date it stored, a theme or plugin update does not move that date, so an old render the edge still held was renewed as it was, every two hours, for as long as the post went unedited (the owner's report, 2026-10-03: after an install, a page still showed the old version). A 304 now also needs the request's date to be at or after the last render change, the time of the last purge chain (`sn_last_purge_report`). `sn_seo_singular_not_modified()`; pinned in `tests/seo-og.php`.
- **Invalidate on a code update is built and held off.** Cloudflare's `invalidate_cache` (2026-09-28) would mark the zone stale on an update and keep the previous copy if the new code failed. With the old 304 rule it would have kept the old markup on every note, so every trigger still purges (`SN_CF_SOFT_TRIGGERS` is empty); the sender's invalidate path and its fallback to a purge stay for when an install has shown the 304 fix holding.
- **A save also purges the theme's cache tag.** With theme 15.2.0 every cached page, feed and machine file carries `Cache-Tag: sn-render`; a post save or a post leaving publish sends one tag purge, which covers every page the URL list cannot name. The URL list and the post-save probe stay for now, until a tag purge has been seen to clear the live edge; then both retire.
- **The purge command leaves Redis alone.** `purge-all-caches` cleared the whole object cache every time, which dropped WordPress's update checks (Core read "unknown") and every cached reading for no gain to a stale page. It now refreshes transients, page files and the edge only; `flush_object_cache: true` is the explicit Redis flush, and a full reset (`include_template_overrides`) still includes it. The tool description no longer says "use after deploys": deploys and saves refresh the caches on their own.
- **A cache refresh that failed is in the alert email.** The hourly alert run reads the failure record and mails it once (`CACHE: Cloudflare did not accept a cache refresh ...`), also when the analytics reads it otherwise depends on have failed.

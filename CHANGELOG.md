# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

## [2026.10.12] - 2026-10-14 — drafts get a suggested date, and failures say which note and why

### Added
- **SN Queue (desktop) and Connections › Scheduled: a suggested publishing slot per draft** (queue calendar phase 2, item 2; owner-approved 2026-10-12). A suggestion only: nothing is scheduled, and the only action is the draft's edit link. Each listed draft gets the next open day after today that keeps the cadence rule (never under 2 days from a note, never in a planned gap): the earliest gap over 7 days is split first, as evenly as it can be (several drafts spread across one hole), else the usual spacing after the last note, at the site's usual publish time (the median of the scheduled notes, site timezone). On the card each draft gets one 11px line under its title, "suggested: Fri, Jan 29, 2027", with the reason as the tooltip (about 15px per draft; the 640 default holds for the measured state, which had no drafts). Both Scheduled twins gain a **Suggested slots** box with the rule and the same sentence per draft ("Suggested: Fri, Oct 30 at 9:00 AM; splits the Oct 25 to Nov 4 gap into 6 and 6 days. A suggestion only: nothing is scheduled."), or "No drafts, so no slot to suggest." / "Drafts not read, so no slot is suggested.", and a reason in words when no slot can be read (nothing scheduled, fewer than two notes, or no open day in the next year). The twins' Cadence and Suggested slots boxes share one read of the schedule. The `content-queue` ability's draft rows gain `slot` (in its description and schema); drafts are listed newest edit first, ties by ID. No figure removed.

### Changed
- **Internal only: the remote MCP set's source is split into smaller files** (house line cap). `inc/abilities-remote-set.php` (1,138 lines) keeps its header and the first eight permission callbacks and loads four parts files in the order the registrations always ran: `abilities-remote-set-parts.php` (Increment 2's seven twins), `-search-parts.php` (the Search Console twins), `-ratified-parts.php` (the three ratified twins) and `-contract-parts.php` (edge errors and the contract-14 twins). Code moved unchanged; the same 18 remote abilities register in the same order with the same arguments. Three suites that read the file's source (`ml-drift`, `machine-readers-daily`, `archive-push`) now read every part. Nothing changes on screen and no figure is removed.
- **SN Systems (desktop), Uptime: one figure per row** (owner, 2026-10-14: the Monitors line was too long). "3 of 3 up · 100% over 30 days · medians 20 ms to 38 ms over 24 h" is now three rows: "Monitors 3 of 3 up", "Availability · 30 days 100%" and "Response · 24 h medians 20 ms to 38 ms" ("median 21 ms" for one monitor or equal medians). A figure no monitor reports now says "not read" in its row; before, it was left off the line. Incidents and Slowest are unchanged. The card's default height grows from 580 to 600 for the extra row. No figure removed.

### Fixed
- **An Analytics Engine failure is explained only by its own error, never by another read's.** The last error is stored once for the whole site and kept 5 minutes, so a failed read could quote an older, unrelated error as its reason. The rule the field vitals read got in 2026.10.10 now lives in `sn_analytics_last_error( $since )`, and every place that quotes the error uses it:
  - **S&N Analytics, Test connection (classic page and native window, one notice):** the failure notice quotes the error this test recorded, kept for the notice, or says "no error was recorded for this test" (it said "no diagnostic recorded", and could show another read's error recorded after the test).
  - **The `analytics-dual-write` ability:** `error` on a failed read (and on `sampled_visitors`) is the error recorded during this check, or "no error was recorded during this read" (it was an empty string, or an older read's error).
  - **S&N Analytics, the "Analytics read failed" notice (classic page and native window):** this notice belongs to no single read, so it now says how long ago the error was recorded, for example "HTTP 500, recorded 3 mins ago." (or "when it was recorded is not known"), then the message. **Removed: the request URL ("from https://api.cloudflare.com/...")**, which carried the account id. The native window now actually paints this notice: its painter read a data function that did not exist, so it never showed. Both twins print the same sentence from `inc/analytics-admin-error.php`. The notice still leads the page, but both twins now decide it after the view's reads: a read that succeeds clears the stored error, so a load whose reads answered no longer shows an old error, for up to 5 minutes, above a report that loaded fine.
  - The code and the start of the message only: the request URL, which carries the account id, is never quoted.
- **S&N Health, Time-relative drift: a scan that could not judge every post now names the posts and says why.** The sentence read only "1 of 12 AI calls failed; those posts were not judged this scan." It now names up to three posts with a reason in words, then "+N more", for example `2 of 12 AI calls failed; those posts were not judged this scan: “First title” (the answer was cut off at the answer limit); “Second title” (the provider refused: Overloaded).` Titles sit in typographic quotes. The reasons: "the provider refused: <its message>", "the provider returned no text", "the answer was cut off at the answer limit" (a JSON reply that opened and never closed), "the answer was not the expected list" (valid JSON of the wrong shape, such as a bare string or null), or "the answer was not valid JSON (it may have been cut off)". "Every AI call failed" names the posts the same way.
  - **The provider's message is scrubbed before it is shown**, in these reasons and now also in the breaker sentence ("The AI provider refused the first 2 of 2 calls (...)"), which used to quote it with only tags removed. Removed: links (http and https, www. and domain/path), email addresses, Authorization, x-api-key and api-key header values, Bearer and Basic tokens of any length, JWT-shaped strings, sk-, pk-, key-, api-, org- and proj- ids, and any opaque run of 32 or more characters. The message is then cut at 160 characters, never mid-character. The breaker logic is unchanged.
  - **Where it shows (classic page and native window, one sentence):** when the check also found stale phrases, its finding card now carries the sentence as a warning notice. Before, a check with findings dropped the sentence on every surface, so a partial scan looked complete. With no findings it stays under "Could not run", as before.
  - **`get-health-scan` and `remote-get-health-scan`:** each `flagged` row gains `partial` (the sentence, or "") and `failed` (one row per post: `post_id`, `title`, `reason`; at most 20 kept in the stored scan; absent or empty when not tracked, as in scans before 2026-10-14). Both schemas declare them, so the remote payload contract moves 17 to 18; the worker's own CONTRACT_VERSION bump is a separate PR.
  - **The answer limit for one drift call is 1,500 tokens (was 600).** One verdict is an estimated 44 tokens, so 600 held about 13 of the 25 phrases a post may send and a longer post was cut off and counted as failed on every scan, paying for the call each time. Cost (estimate, Sonnet 5.5 at $10 per million output tokens): the limit is a cap, not spend; a post that needs the room pays up to 900 more output tokens, about $0.009, once per revision (verdicts are cached). No figure removed.
- **The `cache-freshness` ability no longer calls a healthy week "a handful of rows".** Since 2026.10.10 a note save writes a save row and, when the related-notes rebuild changes a related list, a related row after it, so a busy week fills the 50-row purge ledger ring; the description now says `last_7_days_is_floor` reading true is then expected, not a fault. A healthy week still has zero Redis flushes outside manual.

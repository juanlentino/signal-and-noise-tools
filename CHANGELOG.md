# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Changed
- **You can paste your own owner key.** Make it in Terminal with `openssl rand -hex 32`, paste it as Owner key under Connections › Credentials, then run `wrangler secret put SN_OWNER_KEY` in both Worker repos (the keyring prints both commands) and enroll your devices. The owner key and its previous twin take a paste only when it is exactly 64 hexadecimal characters; surrounding spaces are trimmed and it is stored lowercase. Anything else is refused with "Paste the 64-character key from `openssl rand -hex 32`." and nothing is saved. A new pasted key moves the current one to the previous row, as Generate does. Generate and `clear` still work, and the value still shows as its last four characters only. The keyring's Owner key box (classic and dashboard) and the Owner devices card now describe this flow. Pinned in `tests/keyring.php`, `tests/os-leaf-connections-keyring.php` and `tests/owner-devices.php`.

### Added
- **Owner identity for SN Traffic Lanes (Phase 1, plugin half).** Your own visits can now be told apart from readers at the edge, by a signed marker instead of an unsigned flag. Nothing reads the new data until the analytics Worker ships, so no figure changes with this release.
  - **One owner key on the keyring** (Connections › Credentials, worker group): owner key, with a previous twin used only during a rotation. Setup is three steps: generate the key, paste the same value into both Workers (the two `wrangler secret put SN_OWNER_KEY` commands the row prints), enroll your devices. It is generated here (32 random bytes, 64 hex), never derived from the site secret and never pasted. **Generate** moves the current key to its previous row, where it stays valid until cleared. Set the new key on both Workers right away: enrolled devices are re-signed with it on your next wp-admin visit. The one key signs both the device marker and the optional agent token; the signed messages are domain-separated, so a marker can never pass as a token. Values show as the last four characters only.
  - **Owner devices** (Measurement › Analytics, beside "Exclude my own visits", classic and dashboard): enroll this browser under a label, revoke one device, or revoke all. The card shows each device's label, when it was enrolled, when it was last seen and whether this browser is enrolled; it never shows a device id, a marker or a key. Enrolling sets `sn_owner_dev` (Secure, HttpOnly, SameSite=Lax, host-only, 400 days), only on a wp-admin response, never on a page a reader can be served. A wp-admin visit re-signs an older marker once a day with the current key, and reads nothing when the browser carries no marker. A new device shows "No browser has shown this marker yet; revoke and enroll again." until its marker first comes back on a wp-admin visit. If the page has already started sending, enrollment refuses and saves nothing, instead of recording a device whose browser never got the marker. Every change to the device list runs under a short lock against a fresh read, so two tabs never drop each other's rows. Enroll refuses until the owner key is generated. Generate keeps the old key valid as the previous key until you clear it; the card names that step after Revoke all.
  - **`GET /wp-json/signal-noise/v1/owner/revoked`**, behind the analytics server token (Bearer, compared in constant time, closed when the token is unset), answers `{"revoked":[ids],"at":time}` for the analytics Worker, at most the newest 1,000 ids.
  - **`wp sn owner-token --agent=<agent> [--ttl=<seconds>]`** (optional; nothing in this phase needs a token) prints an `SN-Owner-Agent` header for an owner tool (Claude Code, Playwright, a script, the local MCP server). The TTL is 12 hours at most. The token is never stored or logged.
  - **Owner views now reach the edge.** The server no longer suppresses the beacon for excluded roles, so a logged-in owner view is sent and the analytics Worker keeps it out of every reader figure (today's Worker drops it, as before). The role list still gives those users the legacy owner flag. The "Exclude my own visits" copy says what stays true before and after the Workers ship.
  - **Collector status** ignores the analytics Worker's optional owner flags (`ae_owner_bound`, `owner_key_set`, and the earlier two-key names) when judging config health, so an unset owner key never reads as a failure ("All 9 config bindings report true." stays).
  - **Handling the token:** put `wp sn owner-token` output straight into an environment variable, never echo it; in Playwright attach it with `page.route` limited to `https://juanlentino.com/**`, never `extraHTTPHeaders`; never use curl `-L` with it. The keyring hint and the command's help say so.
  - One signer for both formats (`inc/owner-identity-sign.php`), pinned byte for byte to the contract's test vectors, with tampered, expired, too-far-ahead, too-old, non-canonical and previous-key cases. Pinned in `tests/owner-identity-sign.php`, `tests/owner-devices.php` and `tests/keyring.php`.
- **SN Traffic Lanes, the lanes table and its report (Phase 1, plugin half).** Every page view and every machine read now lands in exactly one lane per day, in a new table, `wp_sn_analytics_lanes`. No existing figure, tool or default changes.
  - **Nine lanes.** Owner (an enrolled device), owner agent (a signed token), owner signal not verified (an invalid token, logged in, or the legacy flag), this site's own tools, verified bot, claimed bot, unknown machine, suspected automation and human. Each row keeps a reason: for example `ua_list`, `network`, `over_cap`, `bot_score`, `remainder`, `feed_server`, `web_bot_auth`, `cf_verified`, `category_mismatch`, `impersonation`, `ua_claim`, `no_claim` or `owner_token_invalid`. Claimed bots also keep their family and purpose; verified bots keep their purpose. A robots.txt control token (Google-Extended, Applebot-Extended) is `claimed_bot` / `impersonation` ahead of any signature or Cloudflare category, because no vendor crawls under a control token, and like every house figure it is credited to no family and no purpose. The key columns are never NULL, so a re-roll can never store a duplicate.
  - **A nightly rollup.** It runs after the analytics rollup and bot signals, at priority 30. It covers the trailing seven complete days and never writes today. Beacon days are site-local, read from the public dataset the dashboards use plus `sn_owner_hits`. Machine days are the sensor's UTC dates, from the rights-signals aggregate view, which now carries `owner_identity` and `owner_agent` (rights-signals #89). A day already stored under another `lane_rule_version` (now 1) is never relabeled. A failed, truncated or empty read keeps the stored days, and the report names which. `sn_owner_hits` is read only once a public page view carries a rule version (before that the dataset may not exist); after that, a failed owner read skips the night. An over-cap list that did not read skips the beacon pass only; the machine pass still runs.
  - **The human lane.** It uses the dashboard's own class expression and over-cap list. Human is the dashboard's human minus the visitor-days the bot-signal score marks; those are under suspected automation, reason `bot_score` (the report says so). The bot score still subtracts nothing from the dashboard. An over-cap visitor-day is `over_cap`, never `bot_score`.
  - **`lanes_since`, per sensor, set from evidence.** For the beacon, it is the first public page view stamped with a rule version. For the machine sensor, it is the first read that carries the identity column. A range that starts earlier is marked partial.
  - **Integrity › Lanes** (classic and dashboard; it reads only the table). The invalid-token count for the last 30 days comes first. Then: lanes for 7, 30 and 90 days per sensor, the reason split, the last 14 days, both `lanes_since` dates, the rule version, and "today pending". A note says that visitor-days do not add up across lanes. The reason split, the daily view and how a lane is decided are folds that state their answer closed; the by-lane tables and the notes stay open. No MCP or REST surface yet (Phase 2).
  - Pinned in `tests/analytics-lanes.php`, `tests/analytics-lanes-beacon-run.php`, `tests/analytics-lanes-machine.php` and `tests/os-leaf-tools-lanes.php`.
- **A stale-CV alert.** /cv/ is a translation and does not follow the English résumé on its own. When the English résumé changes, the Résumé screen (classic and dashboard) and a new Health check (`resume_es_stale`, Other checks family) say "The Spanish CV (/cv/) is out of date" and list the English lines added, changed or removed since the translation. The baseline is captured from the live English résumé on the first run. After that it moves only when the Spanish file's `translated_from` names the live English (the "English version" code the alert shows), so a typo fix or a partial Spanish update cannot clear an alert whose lines are still untranslated. No AI, no network. The scan now runs one more check. Pinned in `tests/resume-es-stale.php`.

From 2026-10-16 01:15 UTC the ticks timed out (`/_sn/version` cron: `refresh_status` "error", `refresh_http` null; `wrangler tail`: "The operation was aborted due to timeout" at 15.1 s), so collector-status showed `cron_fresh` false. Pinned in `tests/analytics-refresh-rest.php`.

### Fixed
- **The /stats Automated tile now counts over-cap visitor-days, as the dashboards do.** A visitor-day over the page-view cap (more than 50 views) counts as bot everywhere the dashboards read Analytics Engine directly, but both daily rollup queries dropped it from every row, bot included, so the tile (suspect plus bot from the daily table) undercounted. The rollup now files those views under the bot row (`sn_analytics_counted_class_select()`, whose bot branch is the readers' own condition). Human and suspect rows do not move: over-cap views were never in them. Analytics Engine has not yet run the fold's form (`index1 IN` inside `if()`), so if it refuses it, the run falls back once to the old shape and still writes the day with the old figures, and `sn_analytics_rollup_shape` records which shape ran (`folded` or `unfolded`). Size, not measured exactly: the 14-day bot-signal readout saw 5 over-cap visitor-days that carried beacon signals, each over 50 views, so a floor. The other group-by builders (breakdowns, buckets, UTM, realtime) still drop over-cap rows from their bot rows and are unchanged here. Pinned red-first in `tests/analytics-rollup.php` (daily-table bot, human and suspect equal the readers' for a fixture day with an over-cap visitor; a refused fold still writes the day) and `tests/analytics-human-rule.php`.
- **The analytics network-list mirror names the deployed worker.** `inc/analytics-network-terms.php` said it mirrored worker 1.21.7; 1.26.0 is deployed.

# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Fixed
- **The flagged human visitor-days readout answers (`sn-metrics{bot_signals_flagged}`, `signal-noise/bot-signals-flagged`).** On the live site every call failed with "Analytics Engine did not answer": Analytics Engine refused the details read with HTTP 422, because `if(blob1 = 'tm', double2 * _sample_interval, 0)` pairs a Double with an Integer. ## [2026.11.26] - 2026-11-11 — This site's own tools are their own figure, in no class; the flagged human visitor-days, listed

### Added
- **This site's own tools are counted as their own figure, beside human, suspect and bot and in none of them.** Traffic the site makes about itself (the theme's live contrast check, the ledger verifiers) is not traffic. The analytics Worker keeps those beacons out of the public datasets and writes them only to `sn_owner_hits`: identity 6 since 2026-10-19 (the `x-sn-first-party` header and its secret, proven) and, from analytics worker 2.1.0, identity 7 (a user agent that starts `SignalNoise-` and no stronger identity, a claim). The traffic lanes now file identity 7 as own infrastructure, reason `first_party_claimed`, beside identity 6's `first_party`; before, it would have fallen to `unverified_owner` / `unknown_code`. The rule version stays 1: no stored row ever carried code 7, and code 6 joined under rule 1 the same way (#2230). One helper (`sn_lanes_first_party()`, `inc/analytics-lanes-first-party.php`) sums the beacon's own-infrastructure rows the lanes table already stores per site-local complete day, page views and visitor-days, proven and claimed apart, and says which days it covers (`from`, `through`, `days`, `partial`; partial whenever the window includes today, since the lanes hold complete days only; null when no day of the window is stored, never a fabricated 0). The machine sensor's own-tools reads are reads, not page views, and are left out. It is painted on Analytics > Quality, classic and native, as one sentence under the class legend ("This site's own tools, in none of the three classes: ..."), never a bar segment or a table row a reader could add in, and served on the local door's `get-analytics-summary` (and `sn-metrics{analytics_summary}`) as `first_party`, the same for every class. The class totals are unchanged: the summary's every other field is byte-identical with and without it, and the Quality breakdown's `total` is still human + suspect + bot. LOCAL DOOR ONLY: the local registration runs a new `sn_ability_get_analytics_summary_local()` around the shared reader (the RSS twin's pattern); the remote twin keeps `sn_ability_get_analytics_summary()` and its schema, so remote contract 31 does not move (`tests/remote-contract-shapes.php` green, `tests/fixtures/remote-output-schemas.json` unchanged). The descriptions that define the classes say it in one sentence: own tools (the header, a proof, or a `SignalNoise-` user agent, a claim) are in no class and counted separately as `first_party` (`get-analytics-summary`, the `class` argument of `sn-metrics` and of the section reads, and the analytics rows read, which both doors share); the remote summary twin says they are never in its totals and are counted on the local door only. **Install this release before analytics worker 2.1.0 deploys**: until it is installed, a code-7 beacon would land in the lanes as an unknown owner code. Tests: `tests/analytics-lanes.php`, `tests/abilities-analytics.php`, `tests/abilities-remote-analytics.php` (the parity pins now read "the admin schema minus `first_party`" and "the twin keeps the shared reader"), `tests/analytics-derived.php`, `tests/analytics-bottrend-render.php`, `tests/openstation-analytics-quality-painter.php` (new); each red against the code before this change, except the two "added to no class" pins, which pass on it by nature and were seen red against a planted change that adds the figure into a class. The lanes test double (`tests/lib/lanes-fake-wpdb.php`) now returns only the columns a statement selects, so the reader's `visitor_days` column is pinned too. The remote door's matching wording is sn-remote-mcp-worker 2.13.3.
- **Owner-only, local door only: the presumed-human visitor-days the bot-signal score flags, listed (`sn-metrics{bot_signals_flagged}`, `signal-noise/bot-signals-flagged`).** For deciding whether to build a "strict human" figure; nothing is built and nothing is subtracted. Over the trailing `days` (sn-metrics passes `range`; default 30, at most 90, 365 and all refused): every visitor-day the bot-signals readout counts as human (its human flag, not over the page-view cap, the rule now shared as `sn_bot_signals_counted_human()`) whose score reaches the threshold of 3, and apart the near misses at exactly 2. Each row: site-local day, the first page view's source as the dashboard labels it, country, region, city, device, browser, OS, network (the ASN organization), page views, visible time in ms, the signals that fired, the score, and the relay and intent flags; third-party text is cleaned as the place names are, and no visitor code, IP address or user agent is returned. The readout's own read (`sn_bot_signals_sql()`) runs unchanged; a second read over the same visitor-days (same window, split bound and presence bit) names the details from Analytics Engine constructs the plugin already runs, and a third counts the window's visitor-days, so `truncated` is true at the 5,000-row limit or whenever fewer visitor-days came back than the window holds. Read on each call, stitched across the two dataset generations, never stored; a failed read is an error, not an empty list. No remote twin: the verdict map says why. The SQL has not yet run against Analytics Engine. Tests: `tests/analytics-bot-signals-flagged.php` (new), `tests/abilities-sn-metrics.php`, `tests/mcp-capabilities.php`.

### Fixed
- **Traffic Lanes: the beacon's own-tools lane is painted.** Since identity 6 joined (#2230), the beacon's own-infrastructure page views counted in "All lanes" and in the reason split, but the by-lane table and the daily view had no row or column for them, so the beacon's lanes did not add up to their total. The beacon now lists own infrastructure as the machine sensor does, and the reference says what each own-tools reason means: `first_party` proven by the header, `first_party_claimed` a user-agent claim; on the machine sensor, `first_party` is the sensor's own-tools list or the header, which it does not tell apart.
- **The native Quality view paints the traffic classes.** It handed the breakdown's two top-level keys (`totals`, `top_bot_networks`) to the table as rows, so its Traffic quality table held two blank rows. It now paints Presumed human, Suspect and Bot with their views, the top bot networks as the classic panel does, and the own-tools sentence.

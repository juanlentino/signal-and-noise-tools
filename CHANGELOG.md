## [2026.10.83] - 2026-10-31 — Cite this note, a /verify compare from a link, and /stats without the NOT READ flash

### Added
- **Cite this note: one citation builder, and the Google Scholar head meta.** `sn_cite_this_for( $post_id )` (new `inc/cite-this.php`) returns a note's APA line and BibTeX entry as read now: pinned to the chain head's version (`sn_zenodo_head_commit()`) and that version's own commit date in UTC (the Article's `dateModified` only as a fallback: it is the newest stamp anywhere in the chain, and a founding snapshot can be stamped after a backfilled v1), ending with the production DOI (`sn_zenodo_doi_for()`) when there is one and the permalink when there is not. A note with only its founding snapshot claims no version. Its inputs are the Article's own, and the BibTeX escape and key are ports of the WebMCP bridge's `snBibEscape` and `snCiteKey`, pinned in `tests/cite-this.php` against that module's output. The theme's new cite line (signal-noise/note-cite) prints it; without this plugin the line renders nothing. On a single note, `wp_head` now carries `citation_title`, `citation_author`, `citation_publication_date` (the publish date, `YYYY/MM/DD`) and, with a DOI, `citation_doi`. The DOI is cited only when it records the version being read (owner, 2026-10-31): each note is deposited on Zenodo once, so on 45 of 59 notes the DOI records an older version, and those citations name the version read at its permalink instead. `sn_zenodo_doi_version()` returns the version a DOI records: deposits from now on store it (`_sn_zenodo_version`), and an earlier deposit recorded the chain head at its deposit time, the latest version committed by then. The head's `citation_doi` follows the same rule. A founding snapshot claims no version, so it never matches a DOI. Checked against Zenodo's own records for all 59 live notes: the derived version matched 59 of 59 (the DOI is hidden on 42 and shown on 17).
- **/verify runs a compare on arrival from a link.** `?compare_a=N&compare_b=M`, the compare form's own field names, beside the page's `?note=`: the theme's "Updated" line sends a note's last two versions this way (`#compare` opens the tab). Each version must be a plain number (no sign, exponent, decimal or leading zero, at most six digits), the two must differ, and the page's note id must have the uid shape. Anything else is ignored without a word, so a malformed link leaves the page exactly as a bare `?note=` link does. A well-formed pair runs as the form would, so a version the note does not have gets the form's own "Could not fetch both versions" sentence. There is no range check against the latest credential: review found that URL edge-cached for up to two hours and never purged, so right after an edit it would have refused the newest version. Valid values fill the form, focus moves to the compare output (unless the reader already moved it) and the polite region reads the diff once; a link without `#compare` selects the Compare tab first. The arrival runs once every deferred script has (`DOMContentLoaded`, `load` as backup), so the panel it lands in is the one shown. URL values reach the page only as input values, after the pattern passed. The form's own compare is unchanged (one shared `runCompare()`). The output takes focus without a ring, like the panels (`prov-verify.css`). New behavior suite `tests/prov-verify-compare-arrival.cjs` (61 assertions, sweep wrapper `.php`) runs the real script and the real core in a VM, with hostile parameters.

### Fixed
- **/stats no longer flashes "NOT READ" in its live figures.** The strip is edge-cached HTML, so its two display figures and the Being read now list wait for `assets/live-now.js`; until its first answer they showed "not read" in display type on every load. The markup still says "not read" (a reader without script and the Markdown twin read it: a review found that `<noscript>` would have blanked the twin, whose converter skips it), but where script runs, `public-stats-front.css` hides each part still marked `data-sn-live-pending`, keeping its line so the answer shifts nothing, until the first answer fills it. A read that fails, or an answer the strip cannot use, writes "not read" itself (owner, 2026-10-12: an unread figure says so, never 0), with "Not measured right now." under it, and the strip is `aria-busy` only while the script waits (set by the script; a server-set busy would never clear without script). The method paragraph gets `id="sn-public-stats-method"`, the target of the theme's /stats hero link, "How it's measured", and is printed on the not-measured-yet page too. `tests/public-stats-live-pending.php` drives the real script through an answered read, a failed read and an unusable answer; fourteen mutants seen red.
- **Check Again lists the updates it just found.** On Dashboard > Updates, Check Again (`update-core.php?force-check=1`) ran the plugin's cache clear after WordPress's own theme and plugin checks on the same screen load, so it deleted the records those checks had just written, and the screen, which reads them right after, said there were no theme or plugin updates until the next page load. The clear now runs first (priority 9 on `load-update-core.php`, before core's checks at 10), and core's checks rebuild what it cleared from fresh GitHub tags. Confirmed through WordPress's own `WP_Hook` (records missing before, fresh after); `tests/force-check-no-nonce.php` dispatches the action the way core does and failed on the old order. One edge: if WordPress.org's update API fails during Check Again, core skips the theme's GitHub hook (the plugin still lists, its offer runs on core's earlier write), and a plain revisit of Updates or Themes re-checks.

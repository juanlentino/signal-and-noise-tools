All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

## [Unreleased]

## [2026.10.28] - 2026-10-17 — reading-aid detectors, and lost provenance dispatches recover in minutes


- **A note whose provenance dispatch was lost now leaves Recording within minutes, not up to an hour.** A save records its commit as unanchored and schedules one dispatch event 300 seconds later, in WordPress's single `cron` option. Two overlapping requests can each write back the copy they loaded, erasing the other's events. On 2026-10-16 note 2430 v2 lost both its dispatch and its edge probe that way while four saves seconds later went through. The only backstop was the hourly reconcile sweep. A five-minute event, `sn_prov_orphan_sweep` (`inc/provenance-orphan-dispatch.php`), now finds a published signed subject modified in the last two hours whose commit is unanchored, never attempted, never refused, unsigned, has no dispatch event scheduled, and is older than the settle window plus two minutes. It calls `sn_prov_enqueue_dispatch()`, the same path a save takes, so the stored commit goes out as it is: no new version, no content touched. It reads nothing when the Worker URL or secret is missing or refused (a dispatch would return before marking the commit, and the check would loop), and skips password-protected posts for the same reason. Each recovery is logged to `sn_prov_orphan_log` (newest 20, not autoloaded). The event writes the cron option only when it is missing.
- **sn-scan editorial_conventions and the sn-validate body check know the four new reading aids.** Three new shape tests (`inc/editorial-conventions-detect-aids.php`). An ordered list or a steps group whose every item opens with a date (a month name or a year) is suggested as a timeline, and that one finding replaces the steps suggestion it used to get. A `sn-pattern-steps-enumerated` or `sn-pattern-compare-columns` group nested inside a group of its own kind is flagged as malformed, at the outer group. A core/table in a note without `is-style-sn-table` gets a class fix (`block_replace` with the styled block, the ledger coalesces), or a form finding when it has no header row. `scope="col"` is not checked: the editor cannot write it, so the theme adds it on render. Each new detector is dormant until the theme registry carries its id, so merge the theme first. Read over all 80 live and scheduled posts: zero findings. The same check with a nested group planted in post 2631's real steps markup fires once. 2631 itself no longer carries the nesting.
- **Security: the sn_apply active-content refusal now stands on core instead of regexes.** `snt_sn_apply_active_constructs()` (`inc/sn-apply/active-content.php`) walks an agent write with WordPress's own `WP_HTML_Tag_Processor`, which decodes attributes the way a browser does, so a URL like `&#106avascript:` (no semicolon) and a handler after an unquoted value holding a quote (`<img src=x"y onerror=...>`) are caught where the old patterns missed them. Elements come from core's post allowlist: `<script`, `<iframe`, `<object` and `<embed` are always refused, and `<form`, `<base`, `<link`, `<meta`, `<style`, `<noscript`, `<xmp`, `<noembed`, `<noframes`, `<plaintext`, `<frame`, `<frameset` and `<applet` are refused while `wp_kses_allowed_html( 'post' )` leaves them out. Every `on*` attribute is refused by name, and every URL attribute core lists in `wp_kses_uri_attributes()` (plus `xlink:href`) goes through `wp_kses_bad_protocol()` with `wp_allowed_protocols()`, so a refused scheme is named (`javascript:`, `vbscript:`, `data:`). The contents of `<title>` and `<textarea>` are read as markup too (inside SVG or MathML a browser parses them that way), and a fragment cut off mid-tag is read once more with its openers closed. Block comments and prose keep one probe for a quoted `javascript:`. The named 422 `snt_sn_apply_active_content` and its `data.constructs` are unchanged. Newly refused, by core's policy: `data:` images, and a relative link whose colon comes before any `/?` (`/p?x=a:b`), which core's own kses would mangle on save. Newly allowed: `javascript:` as plain text in a non-URL attribute such as `title`. Tests load core's HTML API and kses through a new shared loader, `tests/lib/wp-core-kses.php`, which also carries core's `array_any()` polyfill (kses.php calls it, and CI's test lane runs PHP 8.3).
- **Security: a plain-prose splice can no longer break out of an attribute.** sentence_replace, drift_replace and emdash_replace write their replacement into the stored markup at the phrase's byte offset without checking that the offset sits in a text node, and a replacement with no `<` passed the fragment check. Spliced into a phrase inside an `alt` or `title`, `" onmouseover="alert(1)` closed the value and added a handler. This gap predates the rebuild above: the regex version checked only the fragment too. Now every splice into existing content (the single sentence_replace, the single drift and em-dash applies, `payload.edits` members, and `batch` members) reads the whole post before and after with `snt_sn_apply_splice_active_error()` and refuses, with the same named 422, any construct that occurs more often after the splice. A handler the post already carried is not counted against an unrelated edit. The fragment check still runs first. link_insert had the same hole, also from before the rebuild: it wraps the anchor in `<a href="...">`, so with the anchor inside an `alt` or `title` the link's own quote closed the value and a same-host target_url such as `https://<site>/onclick=alert(1)` became a real `onclick`. `snt_ai_link_apply_impl()` now runs the same splice check, and so do link_reshape's and unlink's computes. The `link_insert` and `drift_replace` previews in `validation-fingerprint-parts.php` only build a dry-run diff and never write.

# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Added
- **/stats speaks the readership evidence.** The Humans and machines bar sets presumed-human views against machine **readers** (live 30 days: 45,262), not every machine read: 65,040 of 110,302 were this site's own monitors and checks, and the note now says so beside the full total. A new section under the three columns, **AI training, claimed against proof**, states the claim and the proof in one sentence (4,760 reads from crawlers that say they gather AI training data; Cloudflare verified 50), draws one outlined bar the page's width split by how each read is known (verified in the page's red, named-only hatched, before verification was recorded in the rule gray; decorative, the key carries every part as a count), and says that reads presenting Google-Extended, a robots.txt token and not a crawler, are credited to no one. The beacon's likely-automated visitor-days sit under the bar once a day is measured, never subtracted and never painted as 0. The hourly snapshot carries the split through the summary's own evidence fold, so an older snapshot paints the page as before.
- **The desktop widgets carry three more figures.** Deploy Status says the Remote MCP contract on its row ("2.2.0 · contract 16"), amber with both sides named on a mismatch; the Provenance card counts reads presenting a control token ("Control tokens, credited to no one 575 · Google-Extended"); SN Traffic says the presumed-human visitor-days likely automated, or "not measured yet", beside the views and never subtracted.

### Fixed
- **Machine readers and Reader evidence render natively in S&N Analytics.** 2026.10.1 shipped them as white boxes with invisible text: `canonical_piece()` sends every `view/*` key through the classic renderer and the native capture, and the classic markup used a settings fieldset and core notices the dark window never maps, while every test called the painters directly. Both views are rebuilt on the analytics vocabulary (panels, KPI tiles, `snt_an_trend_svg()` for reads per day and the anomaly series, one shared verified-share bar), the key is painted once per view, and the dead proof, band and delta-card painters are deleted. A new host-path test drives `canonical_piece()` and fails on any light-surface class; it is red against 2026.10.1. The Engagement heatmap's empty hours and the Overview's seventh tile are fixed in the same pass.
- **Paired widget groups share the row again.** The card kit's `pair()` started each column at its content's width, so one long value ("Purge dispatched, verifying" right after an install) stacked Edge and Cache on a card with room for both. Columns now grow from zero and stack only below 110px each.
- **An unreadable denylist size is not reported, never "0 ranges, updated ?".** The login-guard worker answers null when its list meta is unreadable; both Login defense twins and the weekly digest read that as 0. One shared line says "size not reported by the worker", counts the IPv6 list beside IPv4 and gives the refresh time in UTC.
- **Status pills hold the 11px floor.** `.sn-pill` was 0.82em, so in a 12px table cell (S&N Analytics › Posts: Indexed, Orphaned, Not indexed) it drew 181 pills at 9.84px; it is now `max(0.82em, 11px)`. The audit's 82 low-contrast pills were the checker misreading `color(srgb …)` values; measured properly they read 9:1 to 16:1.
- **Every watch names a screen that exists.** Three pointed at screens since renamed: `mcp_adapter_read_door` at "Connections › MCP connect" (now AI › MCP Clients), `rights_evidence_review` at "Monitoring" (now Measurement) and `dompdf_bump` at "Content › Resume" (now Resume Page). A new pin reads the tab registry and fails on any watch whose "Tab › Leaf" is not a real label.
- **`notes_drift_reread` is retired.** search_drift measured /notes with no drift a month past the watch's re-read date (2026-09-11); by the watch's own rule that makes the first reading sample noise, which is its answer. Its ripeness reader goes with it.
- **Discography's years no longer sit on the covers.** The Signal & Noise app painted each release's year as a corner badge over its cover art; the year is now a caption under the title, all on one line across the grid. A badge stays for states (an anchored note's v2); `caption` is the new item field for a quiet fact. A release with no cover from Muso.AI or Spotify (the 2007 one) keeps the album icon: there is no art to show.
- **/stats column labels keep their size on phones.** The theme's phone rule sets every grouped h3 to 1.3rem !important (meant for the service headings), so Sources, Countries and Who the machines are drew at 20.8px on a phone against 11.5px on a desktop. The label rule now holds at every width.
- **/stats keeps How they read by key.** The four rows were kept by the desktop's English labels, so a reworded label would have dropped a row from the public page without a sound.

## [2026.10.1] - 2026-10-11 — every machine-reader count says how it is known, and the machine readings move to S&N Analytics

### Added
- **Every attributed machine-reader count says how it is known.** Five words, `signed`, `verified`, `claimed`, `inferred`, `unmeasured` (inc/machine-readers-basis.php). The machine-readers summary (and its remote twin) gains `verification`: per family, per purpose, for `ai_training` and `ai_training_by_purpose`, `{claimed, verified, verified_matched, unverified, unverifiable}` by Cloudflare's verified-bot category, with the rights evidence's classifier and since date (rights evidence schema 2 is unchanged). `verified_matched` is verified AND the category fits the claimed purpose (train: AI Crawler; unknown and dev never match). A `basis` map names each field's basis; `identity` (Web Bot Auth) is `signed`, which is not `verified`. For the 7 days to 2026-10-11, training reads claimed 1,984 with 25 verified, all Anthropic's own network. Crosstab cells carry the same split plus `first_party_hits` (the exact part from this site's own tools), `first_party`, `impersonation` and `basis`. A read before the since date is unverifiable, never "never verified": the family and agent exceptions read each agent's whole split.
- **Control tokens are credited to no vendor.** Hits presenting Google-Extended or Applebot-Extended (robots.txt names, never a crawler's own user agent) leave `families`, `purposes`, `ai_training` and `ai_training_by_purpose` and are listed in `impersonations` with their networks; `total` still counts them. Live: 170 reads, all from Google LLC, so `purposes.train` reads 1,984 instead of 2,154 and `ai_training` 3,283 instead of 3,453. The purpose tables, the counted-both-ways comparison and the family delta cards leave them out too.
- **This site's own tools read apart.** `families[].first_party_hits` (live: 20,042 of unclassified-machine's 20,509); a first-party part in the desktop and public /stats split of machine reads ("This site’s own tools"). The summary gains `reader_families`, the top 3 third-party families with their verified reads, so the desktop tile's top family and the dashboard's Top families list name a reader, not the site's own ledger verifier, its share with control-token hits out of the denominator too.
- **Reader anomalies leave first-party reads and control tokens out, split verified from unverified, and fold co-movements.** On 2026-10-05 unclassified-machine flagged at 13.1 sigma on the site's own ledger verifier; that no longer reaches the series, and uptime (the site's own monitor) leaves the pipeline. Each family gains `by_verification` (signals withheld until a series has 20 verifiable days). Three or more families deviating the same day on unverified reads from one network are one `reader_co_movement` signal naming the network (on 2026-10-10 seven families spiked on Google LLC addresses), counted in `counts.co_movements` and named on Site Health.
- **The unnamed list shows who was verified and from where.** `unnamed` reads the unknown view with `detail=network` (rights-signals 1.30.0), folds per sample before the top-20 cut, and carries `verified_hits`, `not_measured` and the top 5 networks; against an older worker `verified_hits` is null and basis `unmeasured`, never 0.
- **`likely_automated` beside the presumed-human totals.** `get-analytics-summary` (class human; null otherwise) and its remote twin carry the beacon's observe-only bot-signal score summed over the range from a new nightly per-day store, with `measured_days` and `unmeasured_days`, basis `inferred`, subtracted from nothing; it is a tile in the Overview stats row on both surfaces, beside the presumed-human figures, and counts UTC days (the store's day), so a site-local range's edge can differ by a day. The store keeps every night's read (up to 400 days), and a capped or empty read keeps the stored days and is logged. `basis: inferred` names the class itself.
- **S&N Analytics gains two views, Machine readers and Reader evidence**, after Traffic & edge, on both surfaces, each with its own 7, 14, 30 or 90 day window (a longer range opens at 90 days and says so). Machine readers answers who reads and for what: a hero band with the evidence legend, the headline tiles and one finding built from the payload, then the family delta cards, Who reads beside What for, Rights files beside Feed fetches, and the reference bands. Reader evidence answers how each count is known: claim against proof, Signed beside Verified, the split by family and by purpose, control tokens, the named agents Cloudflare did not verify with their top network, the unnamed samples, and the reader anomalies as a verified and unverified day histogram with the co-movement verdicts. Every split is an evidence strip with its counts as text, the legend keys all four of its parts once per view (the half segment is outlined, not only lighter), each tile is one grid element, two boxes share a row only within 1.5x of each other, and every capped table ends in a "+N more" line naming the end it cut. Both views read the edge sensor with its own credentials, so they open with Analytics Engine unconfigured; every people view stays behind that gate. No folds.
- **The SN Provenance tile and the dashboard widget say claimed and verified.** AI-training reads read "N claimed · M verified" with a small evidence strip (the legacy family figure only when the summary predates the split), and their links open Machine readers in S&N Analytics.

### Changed
- **Monitoring › Machine Readers is configuration only**, native leaf and classic tab alike: the sensor status with links to the two S&N Analytics views, the two Site Health verdicts, the Edge sensor readout beside the Sensor settings form (unchanged), and the monthly rights evidence. Every reading it showed moved to Machine readers or Reader evidence. The desktop tile, the dashboard widget, the note dossier and the family delta cards link there now.
- **The classic renderers the readings left behind are deleted**: inc/machine-readers-render-taxonomy.php whole, the family, surface, compliance, summary, feed, truncation and identity renderers, the old delta-card list, two legend helpers and a split-rows helper, with their tests and their fold and KPI CSS. Every name was checked for a live caller first.
- **The human class reads as presumed human (not flagged).** Class selectors (native and classic), the native Traffic & edge view, the quality legend, the human-rule note, the bot-signals panel, the edge card, the station home card and the public /stats labels; ability descriptions say the classes are inferred. Stored class keys are unchanged.
- **Purpose `unknown` reads as unmapped** in the classic and native tables and the dashboard's Reads by purpose list; the stored key is unchanged. `ai_training` is described as the legacy family figure, with `ai_training_by_purpose` preferred.
- **Remote MCP contract 15 -> 16** (the machine-readers and analytics summary twins; pinned once, after the last schema change before release). The remote worker's own `CONTRACT_VERSION` follows in its own release; until then Deploy Status reads `contract_match: false`, by design.
- **Versions are by date: `YYYY.M.N`.** The next cut is 2026.10.1, then 2026.10.2, and N starts again each month. One site installs this plugin and nothing else ever will, so the number only has to go up and say how old an install is; the WordPress shape it replaces rolled from 14.0.0 to 24.0.0 in a month. `tools/cut-release.sh` computes the date number (`fix` is accepted and means the same as `release`; `major` is refused) and refuses a version that would not sort above the current one. The release workflow tags the cut and no longer drafts a GitHub release, which nothing read; the Theme releases and Plugin releases links under Tools › Links open the tag lists, which keep growing. docs/VERSIONING.md says why.

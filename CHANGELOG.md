# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

## [2026.11.24] - 2026-11-10 — Core-first round: faster health scans, 06:15 rollup, structured Insights, core admin forms

### Changed
- **Abilities take a bodyless call the way core's own abilities do.** Every ability input schema that typed itself `array( 'object', 'null' )` so a GET, DELETE or POST with no input would validate (101 registration sites in 56 files, none with a `required` list) is now `'type' => 'object'` with a top-level `'default' => array()`. Core's `WP_Ability::normalize_input()` swaps a null input for that default before validation, in the REST run controller and in `execute()` alike, on 7.1.4 and on 7.2, so no input, null, `{}` and `[]` all still pass, and callbacks receive an array. Properties and `additionalProperties: false` are unchanged; the remote twins changed with their admin abilities, so the parity pins hold, and the remote contract (version 31) does not move, because it hashes output schemas only. Output schemas, nested properties and the REST field schema keep their nullable unions. Visible change: tools/list on our MCP doors now carries `"default": {}` on these tools (their `type` was already forced to `"object"`); `sn_mcp_normalize_schema()` turns an empty default into `{}` on 7.0 too, as core's client prep does on 7.1. The official MCP adapter (0.7.1) would advertise these tools flat instead of wrapping their arguments in a required `input` property; its port watch is still pending, so no adapter at 0.7.0 or later is active on this site. Comments that called the union load-bearing or "the only way" are corrected. Tests: `tests/abilities-bodyless-on-core.php` runs 39 real registrations through core's own validator (and `prepare_input()` on 7.2) with each of those inputs, with a control that drops the default and must reject null; Group E in `tests/abilities-categories.php` now demands an object with a top-level default and refuses the union; the per-ability pins follow. `tools/fetch-wp-test-core.sh` fetches the four core files the new suite reads.
- **Two admin screens now use core's own form and disclosure primitives (core-first audit, 2026-11-10).** The RSS tracker's three writes (Save Settings, Reset to Defaults, Purge now, on Measurement > RSS and in its OpenStation window) post to `admin-post.php` as `sn_rss_save_settings`, `sn_rss_reset_defaults` and `sn_rss_purge_log`, each checked with `check_admin_referer()` against a nonce made for that action alone, then `manage_options`. They used to be read on `admin_init` under one shared nonce checked by hand. A stale form now shows core's standard "link expired" page; before, it returned silently and the change was lost with no message. The option name, its keys and values, the redirect and the `?sn_rss_ok` flash (`purged-N` included) are unchanged. The OpenStation window replays the same hooks through its admin-post pipeline, so its RSS-only pipeline is removed. A tab left open across the update posts the old form and is refused, so reload before saving. On Analytics > Posts, the "Show all notes" panel is now a native `<details>` with the panel header as its `<summary>`, so the browser provides the toggle, the keyboard handling and the expanded state. It used to be a script toggle and a separate "Toggle panel" button. Core's postbox.js was considered and not used: it binds every postbox title on the page, so the other panels would fold too, it saves every panel's state to user meta, and it has no default-closed state. The panel still opens closed, other panels are unchanged, and opening it still fires the lazy-load event. It no longer remembers in the browser whether it was left open, so it opens closed on every visit, like the estate's other folds. Tests: `tests/rss-tracker-admin-post.php` (new), `tests/os-leaf-monitoring-rss.php`, `tests/openstation-host.php`, `tests/analytics-panels.php`, `tests/analytics-clamp-asset.php`.
- **The Insights scan and the weekly digest ask the AI Client for structured JSON.** Both requests now carry a JSON schema through core's `as_json_response()` (`snt_insights_response_schema()`, `snt_narration_response_schema()`), passed as a new optional `$json_schema` argument of `snt_ai_generate_with_constraints()`. The scan's schema root is an object, so its questions arrive under `questions` and the parser unwraps them; the schema attempt's system instruction describes that object (`snt_insights_system_instruction( true )`, passed as a new optional `$structured_instruction` argument), while the plain retry keeps today's wording. The tolerant parser also unwraps a `{"questions": [...]}` object, so a fenced one is not cached as an empty scan. A response that came back under the schema is decoded as-is, with no fence strip and no salvage. The wrapper calls a reply structured only when it is a JSON object (both schema roots are objects); a schema request whose reply is not one (the format ignored, a refusal stop, another provider) goes to today's tolerant parser, so it never parses worse than today. If the structured request is refused (`prompt_client_error` with HTTP status 400, or `prompt_invalid_argument`, the client declining the options; core labels every provider 4xx `prompt_client_error`, and a 429, 401, 403, 404 or 413 is not retried), the wrapper writes one `error_log` line saying so and sends the request once more without the schema, through itself: the monthly budget cap is checked again, and spend is recorded only for the request that ran. That retry keeps the scan's thinking, effort, ceiling and timeout, and today's tolerant parsing reads it. A token-limit stop is not retried, since that request ran and billed. The Anthropic provider (1.0.5, and its main branch) still sends the deprecated top-level `output_format` with the `structured-outputs-2025-11-13` beta header; whether the API takes it beside the scan's `output_config` effort is what the first live scan shows. Tests: `tests/insights-generation-budget.php`, `tests/insights-narration.php`.
- **The nightly session rollup runs at 06:15 UTC, so /stats Visits counts yesterday from the morning.** It ran an hour after it was first scheduled (21:43 UTC on the live site) and records the day before, so the newest day of the /stats window was missing about 22 hours a day ("29 of 30 days"); now about 6. Not 00:30 UTC, the time held for analytics 2.0.0: the rollup writes each UTC day once and never rewrites it, and the human class leaves out visitor-days over the page-view cap through a list cached for an hour. A visitor-day starts at New York midnight (05:00 UTC in winter, 04:00 in summer), so at 00:30 the one holding most of yesterday is still open, and if it crossed the cap after the run its rows would stay stored as human. 06:15 is after New York midnight plus that hour in both seasons. On the first request after the update, an event at any other time is moved once (`SN_SESSION_ROLLUP_AT`, `sn_session_rollup_schedule()`, now in `inc/analytics-session-rollup-schedule-parts.php`). When the move would skip yesterday (the update lands after 06:15 UTC and before the old run), or an absent event is re-armed after 06:15 UTC (a reactivation, a cleared event; the old schedule re-armed it an hour out, which wrote yesterday), one run for yesterday is queued a minute later with the day as its argument; the option `sn_session_rollup_backfill` holds the day queued, so no day is queued twice. A missing day would hide Visits and One page only on /stats for the next 29 days. A pending one-off with no arguments (a "Run now") is left alone, as in the edge rollup. The rollup replaces a stored day (an upsert per day and class; exit rows deleted and rewritten), so a second run is safe, and the run itself is unchanged. The hold for analytics 2.0.0 is over: the verdict is frozen, so the verify step on this hook returns at once. `tests/session-rollup-schedule.php` pins the time against New York midnight plus the list's cache in both seasons (red at 00:30 and at 05:30), the skipped day, the backfill on a move and on a re-arm (each day once), the "Run now" case and the backfill run.
- **The test sweep passes on WordPress 7.2 Beta 5 as well as 7.1.4.** In 7.2, core's block parser is built on `WP_Block_Processor`, so a block delimiter inside a plain HTML comment, and attribute JSON that never closes, now read the same to `parse_blocks()` and to the sn_apply delimiter reader. `tests/sn-apply-block-delimiters.php` and `tests/sn-apply-fingerprint-splice.php` now ask which the loaded core does (`tests/lib/parser-walker-agree.php`). Where the two disagree (7.1), the write is refused as before. Where they agree (7.2), the write must splice exactly the block `parse_blocks()` puts at that path and leave every other block as stored. The check that refuses a disagreement stays, because the live site runs 7.1. `tests/run.sh` now says how to sweep 7.2 (`WP_TEST_CORE_REF=trunk` until wordpress-develop has a 7.2 branch). One visible change comes with 7.2 itself: core lets list items through its automatic excerpts (7.1 already listed `core/list`, but its `core/list-item` children were dropped; 7.2 adds `core/list-item` and treats `core/list` as a wrapper), and the social card dek is built on core's `excerpt_remove_blocks()`, so a post with no hand-written excerpt (and a page with no meta description) that opens with a list will start its dek with the list's text. On 7.1 the list is skipped, as before; nothing changes until the site updates. `tests/og-card-dek-fallback.php` reads the loaded core's list and expects what it says. Otherwise test setup and comments only.

### Fixed
- **The alt-text check reads an image's caption and nearby heading with core's HTML API.** `sn_health_caption_after_offset()` and `sn_health_heading_after_offset()` were the last byte regexes in the alt-quality reader; they now walk core's Tag Processor tokens after the image, with the same scoping, the same two-element skip budget and the same 2000-byte distance bound (block-delimiter comments still do not count toward it). A figcaption or heading written inside a comment, a script or a textarea is no longer read as one, a `</figure>` inside a comment no longer ends the figure, a `>` inside an attribute no longer leaks the rest of the tag into the caption or heading text, and a script inside a caption is no longer read as caption text. An inline SVG's `<title>` inside a heading or caption still counts as its text, as before. The other answers that change follow how HTML itself reads the markup: an empty `<!-->` comment no longer swallows markup up to a later `-->`, and a comment closed by `--!>` ends there; `</figure class=x>` closes the figure and `<figurex>` is not one; the text of an HTML `<title>` or a `<style>` inside a heading or caption no longer joins it; `I <3 it` keeps its `<3 it`; and an unclosed `<script>` or `<!--` inside a figure runs to the end of the post, so that image now gets no caption or heading. The with-alt reader finds every image's own `</figure>` in one pass, so a long post with many bare images is no longer walked once per image (200 such images in 500 KB: 0.05 s). Run side by side with the regex helpers at all 59 images on hand (32 in the shared image cases, 12 in two saved stored pages, 15 in rendered pages), the answers match. Tests: `tests/health-alt-after-offset.php` (pinned from the regex helpers first; each answer that changed names the regex bug; the reader is checked case by case and its token count is bounded on the 200-image post). `snt_html_span_processor()` now counts the tokens its processors visit, for that bound.

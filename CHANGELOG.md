# Changelog

All notable changes to Signal & Noise Tools are documented here.

This file holds two things only: **`## [Unreleased]`**, the working log that
accumulates across pull requests, and the **current release**. Everything older
lives in [docs/changelog/](docs/changelog/).

A pull request does not bump `Version` and does not tag — it closes an issue and
adds a bullet below. A release is a separate, deliberate act:
`tools/cut-release.sh`.

## [Unreleased]

### Changed
- **A note save that changes nothing another page shows no longer empties the whole edge cache.** Since #1850 every save of a published post purged the theme's whole Cloudflare cache tag, which empties every page on the site. In the week to Oct 13 that was 40 save purges, about 5.7 a day, in bursts of 3 to 6 within seconds.
  - **What is compared.** Just before the save, the plugin records what other pages list of the note: title, slug, publish date, status, password, excerpt, the opening 60 words (as the link preview and the index excerpt each strip them), reading time, links to other notes (cited-by), tags and categories, featured image and sticky.
  - **When none of it changed**, and the theme tags each note (juanlentino/signal-and-noise#530), the save purges two tags in one call: the note's own (`sn-note-<ID>`) and the lists' (`sn-lists`). Core's sitemaps still go by URL. A tag clears every copy of the note's page, including share and feed links with `?utm_source=` (each is its own copy at the edge), in every tier; a URL purge would not.
  - **Anything else keeps the whole-tag purge:** a theme without per-note tags, a change to any listed field, a first publish, unpublishing or trashing, a page, or a save whose "before" was never seen (a scheduled note going live). If Cloudflare refuses the two tags outright, the whole tag goes instead.
  - **The post-save probe runs again** after a note purge. Cloudflare's "Old per-URL purge path" note now appears only for a theme that does not tag each note.
  - **Bursts of saves are not merged:** they are separate requests, and merging would mean skipping or delaying a purge.
  - **Ledger:** the purge ledger records the narrow purge as trigger `save`, scope `note`. The `cache-freshness` reading gains `by_scope` (`save:tag` and `save:note`), so the `save` count in `by_trigger` now covers both kinds. A note purge does not move the desktop's "last full edge purge".
  - Pinned by the new tests/cloudflare-purge-save.php and tests/purge-ledger.php.
- **Cache clearing does less damage and says what it did** (cache research, 2026-10-13).
  - **A stale post-save probe purges the whole-site cache tag, not the whole zone.** The `sn-render` tag covers every page, feed and machine file, which is all a stale note page needs; images, styles and scripts stay cached. The zone goes only when Cloudflare refuses the tag call. The probe's "fresh" read now sends a new random `?sn-cache-probe=` value each time, because the fixed `=1` was itself cached at the edge. Under Connections > Cloudflare, Post-purge probes rows read "stale → whole-site tag purge" or "stale → zone purge" (rows from before today were zone purges and still say so), and the box's description names both. Attention says "The whole-site cache tag was purged." for a tag row. The `purge-verification-log` rows gain `escalation` (tag, zone or none).
  - **A theme or plugin update, and a version rollover, mark the zone stale instead of deleting it** (Cloudflare `invalidate_cache`, all plans, same limits as a purge). Cloudflare serves the old copy while each page revalidates, and serves it if the new code fails. Saves, Styles saves, the probe and the manual purge still delete. The Cache box's "Last purge" reads "full zone, marked stale" after one; the ledger row carries scope `invalidate`. 
  - **A stale-probe row in Attention clears once every page was refreshed, by any route.** It used to clear only on a later zone purge, which updates and probes no longer send. Now a confirmed purge of the whole-site tag (a save, a Site Editor save, a probe's escalation) or a confirmed zone invalidate (an update) also counts, recorded as `sn_cf_last_html_refresh`. A note's own tags do not count, and neither does the probe's own escalation seconds after its reading.
  - **Saving a navigation menu, a template or a template part in the Site Editor purges the whole-site tag** (once per request). Nothing purged on those saves, so a menu or footer edit waited up to the 2-hour edge lifetime. Ledger trigger `site-editor`, scope `tag`. The Cache box's Auto-purge line names these saves and the mark-stale on update, on both surfaces.
  - **The Cloudways app purge is retired by default.** Varnish is off for this app (Cloudways API: `varnish_enabled` false), so the call only emptied Redis, which the manual purge already does, at up to 10 seconds of blocking API calls. `define( 'SN_CLOUDWAYS_APP_PURGE', true )` in wp-config.php turns it back on. Connections > Cloudways reads "Retired" in Last purge and Result, with why; the Cloudflare Cache box's Cloudways purge row reads "Retired" with no "Last attempt" time (that figure is removed while retired, because it would only grow). Purge ledger rows say "retired: Varnish is off for this app" in the Cloudways column instead of relying on the theme to note it.
  - **The Cloudflare Cache box shows "Breeze page cache: on, off or not read"** on both surfaces, from the theme's last purge report (`legs.breeze_page_cache`, theme signal-and-noise#532).
  - URL purges go 100 to a call (was 30), Cloudflare's limit on every plan.
  - Pinned by the new tests/cloudflare-purge-probe-escalate.php, and by tests/cloudflare-purge-send.php, tests/purge-ledger.php, tests/cloudways-purge.php, tests/admin-cloudways.php and tests/os-leaf-connections-cloudflare.php.

## [2026.10.9] - 2026-10-13 — the queue fits and warns, and field vitals read

### Changed
- **The README opens with what the plugin is, for someone landing cold.** It now says this is the plugin that runs one person's site, built in the open and not a product. Three things make it unusual: agents edit under rules, notes are signed, nothing is rented. A screenshot of the OpenStation desktop follows. The jargon in "What it does" is glossed (Jev, the read and write endpoints, the health scan), and the theme hooks table moved into In depth. Docs only.

### Added
- **Cadence warnings on the SN Queue card and on Connections › Scheduled (queue calendar phase 2, item 1).** The owner's rule: notes under 2 days apart are a cluster, notes over 7 days apart leave a gap. It is checked from the latest published note through every scheduled one, in date order, counting days in the site timezone. A scheduled note whose date passed before it published sorts before the latest published note and never hides it. With nothing scheduled there is no line; the card's "Nothing scheduled" headline already says so. The card lists each warning in words, up to three, then "+N more in Scheduled". Examples: "Cluster: 2 notes Oct 20 and Oct 21", "Gap: no note Oct 25 to Nov 4 (12 days between notes)". Every line links to Scheduled, and a gap line keeps its Planned button. Connections › Scheduled has a new open Cadence box with the same rule and sentences, on both the native window and the classic page. When there is nothing to report it says "No clusters or gaps from the latest published note through the scheduled ones." Deliberate gaps come from the existing setting the Planned button writes (`sn_content_queue_planned_gaps`, which keeps the newest 20), never from code. The holiday pause (empty days Dec 20, 2026 to Jan 3, 2027, between the Dec 19 and Jan 4 notes) is already stored there, so it raises nothing. Any planned range that contains a gap now covers it. Changed: the card's single gap line (the first hole by the publishing-cadence flag's statistical threshold) is replaced by these lines. The `gap` field stays in the content-queue reading for other readers, and the card paints it only for an older payload. The card's default height goes from 590 to 640 (a figure changed), so one warning line shows without a scrollbar. That was measured live with the longest sentence and its Planned button: 627 at 265 wide, where it wraps to three lines, and 585 at 312. Today's live queue (notes every 2 to 4 days, then the holiday pause) shows no warning. Read-only: titles and dates only. Pinned by tests/abilities-content-queue.php (including a note published Oct 5 between an overdue Oct 1 note and an Oct 20 note), tests/desktop-status-resilience.cjs, tests/desktop-mode-integration.php and the new tests/queue-cadence-twins.php (both twins escape a sentence).

### Fixed
- **Field Core Web Vitals read again (every read failed on 2026.10.8).** The `get-analytics-vitals` ability, the `analytics_vitals` section and the "Core Web Vitals at p75, by device" table on both Engagement twins (the classic page and S&N Analytics) always said the read failed. The cause, read from the Analytics read-failed notice on the live site: Analytics Engine answered HTTP 422, "the 2nd and 3rd arguments to IF() function must have the same type but instead had Double and Integer", because the query picked the stored CLS value (a Double) or the rounded LCP and INP value (an Integer). The query now rounds every vital the same way, choosing only the step: 10 ms for LCP and INP as before, 0.001 for CLS (it was the stored value). A figure changed: CLS p75 can now read up to 0.001 higher than the raw value; the good, needs improvement and poor shares are unchanged, since every threshold is a whole step. A failed read now says which part failed and why, in the ability's error: "the by-device read failed (Analytics Engine said HTTP 422: ...)", "the by-path read ...", "the top-paths read (the daily analytics table) failed: ...", or that a read reached the row cap. Only the status code and Analytics Engine's message are passed on, never the request URL (it holds the account id), and a cached failure keeps its reason for its 5 minutes. Pinned by tests/analytics-vitals.php.
- **The SN Queue card fits its content (seen live on 2026.10.7 at about 265 wide).** Its default height goes from 780 to 590 (a figure changed): 780 was budgeted for the busiest state and left about 200px empty under Open Scheduled on an ordinary day. 590 is measured on the live desk with the real queue (26 scheduled, six week rows, the next-up box with a three-line title, the counts row, three published and the link): 573 at 265 wide and 549 at 312, plus about 10px of slack. The busiest state (an overdue line, the gap line, three drafts and three Later rows, about 180px more) now scrolls inside the card. A card you already placed keeps its saved size, so drag yours shorter once, or remove and re-add it. "26 scheduled · to Jan 25, 2027" no longer breaks over two lines beside "0 drafts": each stays on one line, side by side when both fit (312 wide) and one under the other when they do not (265 wide). "Open Scheduled→" reads "Open Scheduled →", spaced like Open Analytics (a trailing space inside a flex link is dropped, so the space is now the link's gap). Pinned by tests/desktop-status-resilience.cjs and tests/desktop-mode-integration.php.

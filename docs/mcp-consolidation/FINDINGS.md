## #1/#4 — Server implementation: hand-rolled, not the adapter
`composer.json` requires only `"php": ">=8.3"` — no `wordpress/mcp-adapter`, no `wordpress/php-mcp-schema`, no `vendor/` dir at all. The whole MCP layer is hand-written in `inc/mcp/` (10 files): `mcp-server.php` (JSON-RPC 2.0 method router, hand-built), `mcp-endpoint.php` (two REST routes, `/mcp` read + `/mcp-rw` write), `mcp-capabilities.php` (allowlists), `mcp-tools.php` (ability→tool projection + dispatch), plus `mcp-resources.php`/`mcp-prompts.php` (resources/prompts already implemented) and three hardening files (`mcp-rw-guard.php`, `mcp-rw-audit.php`, `mcp-read-guard.php`).

**Protocol version**: this server negotiates `2025-06-18`/`2025-03-26`/`2024-11-05` (`mcp-capabilities.php:21`), never `2025-11-25` — so `sn-mcp-conformance.md`'s entire §0/§0.5 framing (audited against the adapter's 2025-11-25) doesn't apply; there's no adapter to be behind.

**Real baseline is 68 tools, not 66**: read allowlist (`sn_mcp_allowlist()`) = 33 slugs, rw allowlist (`sn_mcp_rw_allowlist()`) = 35 slugs, zero overlap, verified by direct count. `sn-mcp-consolidation.md`'s mapping table accounts for 66 and misses two live abilities: `signal-noise/topic-clusters` (v10.21.0) and `signal-noise/cadence-flags` (v10.22.0), both read-door, neither mapped to any of the 11 new tools.

**Verdict: INVALIDATES** the adapter-rewrite framing in the kickoff prompt and conformance §0.5. There is no `wp_register_ability()` + `create_server()` migration to do — consolidating the surface means editing `sn_mcp_allowlist()`/`sn_mcp_rw_allowlist()` in `mcp-capabilities.php` directly. This is *less* work than assumed, not more.

## #2 — Composer dependencies: absent, confirmed conclusively
`composer.json`'s only `require` is PHP >=8.3; `require-dev` is lint/analysis tooling only. No vendor dir, no lock file, zero references to adapter namespaces anywhere in `inc/mcp/`. Closes #1/#4 definitively.

## #3 — Annotations: already fully wired, not a blocker
`inc/abilities-dismiss.php:75-81` and others register `meta.annotations` (`readonly`/`destructive`/`idempotent`, WP Abilities vocabulary). `inc/mcp/mcp-tools.php:241-262` (`sn_mcp_ability_annotations()`) translates this into MCP's `readOnlyHint`/`destructiveHint`/`idempotentHint`, with a documented precedence order and a curated override map (`sn_mcp_rw_annotation_destructive_overrides()`, lines 176-213) for abilities that under-declare risk. `sn_mcp_project_tool()` (lines 279-297) attaches this to every rw-door tool.

**Verdict: INVALIDATES** the conformance doc's "open blocker" — there's nothing to raise upstream; the exact annotation table the spec proposes for the 11 new tools is a pattern this codebase already implements for 35 existing abilities.

## #5 — Shared code paths: mixed, with one major gap
- **Scan family is two families**: structural scans (block-migrations, pattern-adoption, duplicate-body) don't touch `inc/ml-kernel.php`; ML-kernel scans (near-duplicate, link-candidates, keyword-candidates, topic-clusters, cadence-flags) all share `inc/ml-kernel.php`'s TF-IDF/BM25/cosine primitives. `sn_scan`'s "thin wrapper" framing is honest for the second group only.
- **Fingerprint gating**: confirmed exactly as hoped. `ai-drift-apply`/`ai-link-apply` (`inc/abilities-ai-health.php`) require a 32-char md5 fingerprint echoed from the paired suggest call, 409 on mismatch.
- **`dismiss-candidate`**: content-derived key `(post_id, block_fingerprint, candidate_type)`, confirmed non-UUID (`inc/abilities-dismiss.php:96`). But it only dispatches `surface: block-migrations | pattern-adoption` — the other five planned `sn_scan` sources (near-dup, link-candidates, keyword-candidates, topic-clusters, orphan/pair) have **no dismissal store at all** today. `sn_dismiss` absorbing it is new plumbing for 5/7 sources, not a wrapper.
- **Biggest gap found this session: `mode: "revision"` does not exist anywhere.** Grepped every apply ability for `dry_run`/`preview`/`wp_save_post_revision` — zero hits. Every apply writes live via `wp_update_post()` only; "revision" in existing descriptions refers to WordPress's automatic post-save revision, not a staged, non-live write. `sn_apply`'s core PR-pattern selling point is new engineering, not a wrapper — acceptance test 6 (mode:revision → live post byte-identical) would fail against every existing apply ability today.

**Verdict: INVALIDATES** the "wrapper, low risk" framing of `sn_apply`'s migration path specifically. Recommend splitting the apply phase: 5a builds the revision-mode write primitive in isolation first, 5b wires the four gates around it.

## #6 — `ai-*-suggest` model call: confirmed
`inc/ai-bootstrap.php` — gated on `is_supported_for_text_generation()` (corrected in v2.5.0 from a broken `wp_has_ai_client()` check), model pinned `claude-sonnet-5` (both default and fallback, deliberately identical for resolvability), call site `snt_ai_generate_with_constraints()` (line 275). Credential lives entirely in WordPress core's Settings → Connectors (Anthropic provider plugin) — **SN never holds its own key**, so retiring the 14 `ai-*-suggest` tools carries zero credential-rotation risk. Existing token-usage/spend logging (`SN_AI_USAGE_LOG_OPT`, `SN_AI_SPEND_ROLLUP_OPT`) already tracks this independent of MCP telemetry.

## Extra — modernization-program interactions
**(a)** `inc/insights.php:295-302` (v10.24.0) feeds kernel `cadence_flags` into the AI-billed `get-insights` advisor prompt — but the raw `signal-noise/cadence-flags` ability is separate, non-AI, read-door. Retiring `get-insights` doesn't touch the kernel data; it's genuinely just the prose wrapper. But `cadence-flags` itself is unmapped in the consolidation spec (see #5) and needs a home, likely `sn_health`.

**(b)** BM25 exists only as kernel math (`inc/ml-kernel.php:216`), used for candidate-vs-candidate scoring, never exposed as query-driven corpus search — no ability or tool does this today. Best fit: a `query` field added to `sn_posts`'s scope union, not a new tool (same "field, not shape" merge test the spec already uses). `create-draft` has zero code; `sn_apply`'s target union has no "new post" variant, so it needs a 4th target type plus a *structural* (not policy-only) block on `mode: publish` for that change type.

**(c)** The rw door already has kill-switch (`SN_MCP_RW_DISABLED` constant + `sn_mcp_rw_enabled` option, checked before even `manage_options`), credential-split (bound app-password UUID), rate-limiting (checked before tool-name validation), and audit logging (`sn_mcp_rw_audit_record()`) — all door-level, automatically inherited by any new tool registered on the rw allowlist. `sn_apply`'s four gates should be built as an additional, ability-level layer on top of this, not a reimplementation of it.

## Re-baselined build order
Phases 0a/0b/1/2 hold unchanged. Drop the adapter-rewrite framing everywhere (registration is plain `wp_register_ability()` + allowlist edit, no `create_server()` call exists to write). Insert a decision point before phase 3 to place `topic-clusters`/`cadence-flags`. Split the `sn_apply` phase into 5a (build the revision-mode write primitive, new, with its own acceptance tests) and 5b (wire the four gates around it, closer to the original scope). Budget `sn_dismiss` as new plumbing for 5 of 7 scan sources, not a wrapper. Phases 6–12 hold as written.

## Spec deviations (session 2)
- **Interception point is `sn_mcp_call_tool()`, not the JSON-RPC router.** By the router, an execute() failure is flattened to a message string — the WP_Error *code and status are gone*, and the schema_error/server_error split (metric 3, the whole reason Layer B exists) needs them.
- **Outcome classification is HTTP-status-first, not code-name matching.** First implementation used a code-name regex grounded on a single-line grep; adversarial review proved the grep missed every multi-line `new WP_Error(` construction (8+ real codes misclassified, and substring 'missing' flipped `snt_impl_missing` — a real 500 — into schema_error). Re-grounded on a paren-balanced sweep of all 196 constructions under inc/: 168 carry `array('status'=>N)`; 4xx→schema_error, 429→refused (`write_throttle` for `snt_surfaces_throttled`, else `rate_limit`), 5xx→server_error. Status-less reachable set: `sn_tag_not_unused` (caller-argument, mapped explicitly) + the insights/narration AI-response failures (server-side, correct under the server_error default). **Lesson for all later sessions: never ground a claim about `new WP_Error(` sites on a single-line grep.**
- **`door` column added** ('read'|'rw') — the spec's table predates the two-door finding.
- **VARCHAR not ENUM** for layer/outcome/refusal_gate — house style (no ENUM column exists anywhere in inc/).
- **`actor`** resolves the bound app-password UUID on both doors (the resolver is door-agnostic); `routine:<name>` reserved, produced by no code path yet.

Tests: tests/mcp-telemetry.php, 69 asserts incl. watched-RED wiring evidence and failure-shape wpdb stubbing. Full sweep at ship time: 354 files, 12,912 asserts, 0 failures; PHPStan + PHPCS clean.

Session 2 addendum (adversarial-review fix, same v10.25.0): `sn_mcp_telemetry_classify_wp_error()`'s first cut used the code-name regex above, grounded on a single-line `grep` — a paren-balanced multi-line sweep (`perl -0777`) found it missed 8+ real `new WP_Error(` constructions spanning multiple lines, mis-scoring `snt_impl_missing` (a genuine 500) as schema_error via the `missing` substring. Replaced with a STATUS-FIRST classifier: `get_error_data()['status']` decides (4xx→schema_error except 429→refused, 5xx→server_error); a small explicit fallback list only for the ONE status-less code proven reachable (`sn_tag_not_unused`). **Standing lesson, reconfirmed a session later (see below): never ground a `new WP_Error(` claim on a single-line grep.**

# Session 4 Findings — sn_scan (shipped v10.29.0)

Consolidation phase 3: the third CONSOLIDATED tool, `signal-noise/sn-scan`, registered NEW ALONGSIDE OLD (read door 35 → 36; plugin-namespace 25 → 26; nothing absorbed was touched, unregistered, or deleted). Full behavioral detail is in the v10.29.0 CHANGELOG entry; this section holds the deviations, the orphan-media verdict, and what could not be verified.

## The orphan-media verdict

The spec (`sn-scan-spec.md`) flagged orphan-media as "implied by `ai-orphan-suggest` referencing SQL-flagged orphans" and asked this session to investigate whether a pure-SQL, non-AI detection helper already exists before deciding whether to absorb it.

**It does**: `sn_health_check_orphaned_media()` (`inc/health-check-orphaned-media.php`) is a standalone, callable, zero-AI function — pure `$wpdb` LIKE-substring checks over `wp_posts`/`wp_postmeta` plus a featured-image/theme-mod cross-reference (`sn_health_attachment_is_referenced()`). It is one of the health-checks orchestrator's independent checks (`inc/health-checks.php`'s `sn_health_run_scan()`), entirely separate from `ai-orphan-suggest`/`ai-orphan-apply` (`inc/ai-orphan-suggest.php`), which only consult the SQL-flagged findings AFTER detection to add an AI verdict + a force-delete action. Detection and the AI layer were already cleanly split; sn_scan's `orphan_media` adapter wraps `sn_health_check_orphaned_media()` directly, never `ai-orphan-suggest`. Confirmed by reading both files in full before writing the adapter, per the task's grounding instruction — no new detection logic was written; the adapter's only addition is a trivial sizing `COUNT(*)` query mirroring the detector's own `WHERE` clause (for `corpus_state.posts_examined`), not a re-implementation of `sn_health_attachment_is_referenced()`'s reference logic.

`orphan_media`'s `apply_hint` DOES point at a real ability, `signal-noise/ai-orphan-apply` — despite living in `inc/abilities-ai-health.php`/category `ai-generation`, its impl (`snt_ai_orphan_apply_impl()`) is a pure `wp_delete_attachment()` force-delete, zero model calls, and — critically — no fingerprint gate at all (only `attachment_id` is required). Acceptance test 5 ("prove the fingerprint validates") is therefore vacuously satisfied for this source: there is no fingerprint to drift. **Correction (adversarial review, v10.29.0)**: an earlier draft of this section called the apply impl's pre-delete check "TOCTOU-checked" against orphanhood — false. Reading `inc/ai-orphan-suggest.php:172-198` directly: the re-check is CAPABILITY (`current_user_can('delete_post', ...)`) and EXISTENCE (`'attachment' === $attachment->post_type`) only; it never re-verifies the attachment is STILL unreferenced at apply time. A reference created between scan and apply (the attachment gets inserted into a new post) does not block the delete. This was a pre-existing gap in `ai-orphan-apply` itself, not introduced by sn_scan — **RESOLVED in v10.28.1** (see the "Session 4 (partial) — TOCTOU hardening" section above): the apply impl now re-verifies via `sn_health_attachment_is_referenced_now()` and refuses with `snt_orphan_no_longer` (409). Separately, `apply_hint` here skips the optional AI-verdict step (`ai-orphan-suggest`) a human would normally see first — a product-judgment tradeoff noted for a caller building on this, not something `apply_hint`'s own contract (its `required_args` pass the apply tool's OWN validation) forbids.

## The two-family cost note

Confirms FINDINGS.md #5's split, now load-bearing in the tool description: `block_migrations`/`pattern_adoption`/`duplicate_body`/`orphan_media` are pure structural detectors (`get_posts()`/`$wpdb` walks, `parse_blocks()`/hash comparisons) that never touch `inc/ml-kernel.php` — roughly O(n) per scan. `near_duplicate`/`link_candidates` share the kernel's TF-IDF/cosine primitives; `near_duplicate` is O(n²) pair comparison (the tool description calls this out explicitly, mirroring the spec's cost-tier framing), `link_candidates` is O(n) artifact reads fanned out per source post (the absorbed ability is single-post; sn_scan calls it once per post in scope to build a corpus-wide view — the one place this session's wrapper does more than reshape a single call).

## Deviations from the spec

- **`link_candidates` apply_hint is `null`, not `ai-link-apply`.** The session-4 kickoff named `ai-link-apply` as the expected apply path for this source. Reading `inc/ai-link-suggest.php` in full: `signal-noise/ai-link-apply`'s fingerprint is `snt_ai_drift_fingerprint($raw_content, $anchor, $raw_position)` — a POSITIONAL fingerprint tied to a specific anchor phrase's raw-content byte offset, resolvable only after `ai-link-suggest`/`ai-pair-suggest` (both AI-mediated: `SNT_AI_LINK_SUGGEST_SYSTEM` calls a model) locates and validates that anchor in prose. The deterministic `link-candidates`/`snt_ml_link_candidates()` kernel path has no anchor, no position, and no drift fingerprint to offer — it only ever produces `{post_id, title, slug, url, score}`. Wiring `apply_hint` to `ai-link-apply` here would either (a) fabricate a fingerprint that fails validation, violating acceptance test 5, or (b) require sn_scan to call `ai-link-suggest` internally, violating the tool's own "writes nothing, ever calls no model" guardrail. `apply_hint` is `null` for this source; the reasoning is in the ability description, the adapter's inline comment, and the CHANGELOG.
- **`scan_run_id` is derived from `corpus_fingerprint`, never time or random** (`hash('sha256', $scan_type . '|' . $corpus_fingerprint)`). The spec places `scan_run_id`/`generated_at` "at the envelope level," which is compatible with either a wall-clock ID or a content-derived one — but only a content-derived one lets acceptance test 1 (byte-identical reruns) hold for `scan_run_id` itself, not just the `candidates` array. `generated_at` stays wall-clock (`gmdate('c')`, real "now") — it is explicitly NOT part of the byte-identity guarantee, and no acceptance test claims it should be.
- **`corpus_fingerprint` is derived from THIS scan's own output** (`sha256(scan_type|posts_examined|posts_skipped|sorted candidate_ids)`), not an independent whole-corpus content hash. Hashing every scanned post's body on every call (to get a fingerprint that's provably independent of the candidate list) would mean re-reading content the underlying scans already avoid re-reading unnecessarily on every call; the chosen definition still satisfies every acceptance test that exercises it (identical on rerun, changes on edit) because candidate_ids are themselves content-derived. Documented as a coarse drift signal, not a corpus-wide checksum, directly in the code comment.
- **`freshness` is reported, never honored as a request.** All five non-artifact-backed sources compute live on every call (no cache exists to read from, so "cached" and "fresh" are behaviorally identical — always reported "fresh"). `link_candidates` reads a static artifact and can never rebuild without writing, which this tool's contract forbids — always reported "cached." The `freshness` input parameter is schema-validated (422 on an invalid value) but has zero effect on behavior today; this is stated plainly in the tool description rather than silently ignored.
- **`dismissed` is always `false`; `include_dismissed` is accepted but inert for every scan_type.** For `block_migrations`/`pattern_adoption`, the underlying detectors (`snt_block_migrations_detect_candidates()`/`snt_pattern_adoption_detect_candidates()`) already filter dismissed candidates out of their return value using the existing per-post `_snt_..._dismissed` meta BEFORE sn_scan ever receives the list — there is no way for a thin wrapper to retrieve an already-filtered-out candidate without forking the walker to accept a dismissed-state override, which would mean re-implementing detection logic (explicitly out of scope). The other four sources have no dismissal store at all (`sn_dismiss` is a later phase per FINDINGS.md #5). The bridge projects it through `inc/mcp/mcp-tools.php`'s own `sn_mcp_tool_name_from_slug()` so the stored `tool_name` matches what the MCP door would have recorded for the same ability.

## The two-seam resolution (adversarial review, one HIGH)

The first cut hooked only the per-tool filter above. **Adversarial review REJECTed it on one HIGH**: that filter is gated on `! is_wp_error( $output )` at its single call site (`runner.php:561-582`, verified) — structurally success-only, by construction, not by bug. Every row `door='agent'` could ever produce would read `outcome='ok'`, so the door's failure rate would report an artificial ~0% forever. This is the repo's own "success-only readout" trap (`success-only-caches-pose-as-healthy.md`) recurring in a new place: a healthy-looking number that doesn't measure what it claims to.

The reviewer's citation pointed at the seam already read past once — `do_action( 'desktop_mode_agent_completed', $user->ID, $message, $result, $context )` at `runner.php:239`, fired unconditionally at the end of `desktop_mode_agent_invoke()` whenever the run itself didn't fatal. `$result['toolCalls']` (built at `runner.php:578-593`, one entry per tool call for the WHOLE run):

```php
$tool_trace[] = array(
    'callId' => $call_id,
    'name'   => '' !== $slug ? $slug : $name,
    'args'   => $args,
    'output' => is_wp_error( $output ) ? null : $output,
    'error'  => is_wp_error( $output ) ? $output->get_error_message() : null,
);
```

`error` is non-null exactly when that call failed — the signal seam 1 structurally can't see. Seam 2 (`sn_mcp_telemetry_agent_completed()`, hooked on `desktop_mode_agent_completed`) walks this trace and inserts a row for every failed, in-namespace entry, explicitly skipping success entries (seam 1 already recorded those — `tests/mcp-telemetry-agents.php`'s double-count-guard test pins this by asserting zero inserts from the action path on a success-only `$result`).

**Outcome classification is deliberately coarse.** `sn_mcp_telemetry_classify_wp_error()` keys on `get_error_data()['status']`, but `toolCalls` only carries `get_error_message()` — the status/code never survives the trip. Every seam-2 row is therefore `outcome='server_error'`, flat, undifferentiated, and documented as such. Re-deriving a finer classification by pattern-matching the message string was considered and rejected: that is precisely the regex-classifier mistake `sn_mcp_telemetry_classify_wp_error()`'s own docblock records as a past HIGH finding (session 2) — a single-line/substring scan that miscategorized `snt_impl_missing` as a schema error. A flat, honest `server_error` default beats a plausible-looking guess.

**Residual blind spot, stated rather than hidden.** `desktop_mode_agent_invoke()` returns early, before `do_action( 'desktop_mode_agent_completed', ... )`, whenever the run itself fatals (`runner.php:216-224`: AI unavailable, invoker/agent rate limit, or the max-turns-without-final-answer path). A run that dies one of those ways still loses the tail of tool calls it already executed inside the loop — their `$tool_trace` entries exist in memory but `$result` never reaches either seam, because the action never fires. Nothing in this codebase's contract with the runner exposes that partial trace any other way; guessing at it from inside a fatal-error branch this file doesn't own was rejected as more likely to be wrong than to stay silent about the gap.

## Deviation from the brief: latency_ms

# Session 6a Findings — sn_apply revision-mode write primitive (v10.40.0)

Per session 1's split recommendation: build the `mode: "revision"` write primitive in isolation, before wiring any of the four sn_apply gates (session 6b). No ability/tool registered, no allowlist change, nothing calls this file in production yet.

## Mechanism decision: `_wp_put_post_revision()`, not a hand-rolled `wp_insert_post()`

Read core's `_wp_put_post_revision()` (wp-includes/revision.php) directly rather than assuming its shape — and, per adversarial review, re-verified against the actual WP 7.0.2 source rather than training-knowledge recall, which had drifted on three points (corrected below and throughout this section). It delegates row-shaping to `_wp_post_revision_fields()`, which allowlists a **narrow** field set — `post_title`/`post_content`/`post_excerpt` ONLY (7.0.2 source, revision.php:29-59 — `post_author` is explicitly in that function's own disallowed-field unset list, never a revisioned field) — not a full copy of the parent row. This corrects an implicit assumption in the task brief ("byte-for-byte the same shape as a core-created revision" reads as "full row" but core's own revision rows are deliberately thin). Consequence: hand-rolling `wp_insert_post( array( 'post_type' => 'revision', ... ) )` ourselves would mean re-deriving and maintaining that allowlist by hand, and silently drifting from it on a future core change. `snt_sn_apply_stage_revision()` instead builds a full post array (`get_post( $post_id, ARRAY_A )`) with only the caller's proposed fields overridden, and hands the WHOLE thing to `_wp_put_post_revision()` — core decides what actually gets copied into the revision row, we only decide what changed.

**Grounded failure-shape detail, corrected against the real 7.0.2 source:** `_wp_put_post_revision()` calls `wp_insert_post( $post, true )` — `$wp_error = true` **is** passed (revision.php:372) — so the documented, primary failure shape is a genuine `WP_Error` (`wp_insert_post()`'s own docblock: "@return int|WP_Error The post ID on success. The value 0 or WP_Error on failure."). An earlier pass at this grounding claimed the opposite (WITHOUT `$wp_error = true`, silent int `0`) from training-knowledge recall rather than the real source — wrong, corrected here and in the primitive's docblock. `snt_sn_apply_stage_revision()` still checks both `is_wp_error()` (the real, primary path — exercised in the new Test 10a) and `empty( $revision_id )` (kept as a deliberate defensive/cross-version fallback, not the documented 7.0.2 shape — exercised in Test 10b). Also grounded from the same call site: `_wp_put_post_revision()` runs `wp_slash( $post )` on the row immediately before `wp_insert_post()` (revision.php:370, "Since data is from DB."). This file's snapshot is passed to `_wp_put_post_revision()` raw/unslashed on purpose — core performs the one and only slashing pass; pre-slashing here would double-slash every quote/backslash a caller proposes. A new slash-safety test (gnarly content: literal backslashes, apostrophes, quotes) pins byte-identical storage and would RED on a future double-slash regression.

## The hook-cascade table (corrected against the real 7.0.2 source, not assumed)

`_wp_put_post_revision()`'s internal `wp_insert_post( $post, true )` call has `post_type = 'revision'`. An earlier pass at this table claimed `save_post`/`save_post_{post_type}` were skipped by a core-level `post_type !== 'revision'` guard — **false**, read directly from wp-includes/post.php:5165-5211: `do_action( "save_post_{$post->post_type}", ... )`, `do_action( 'save_post', ... )`, and `do_action( 'wp_insert_post', ... )` all fire **unconditionally**, with no post_type check anywhere in `wp_insert_post()`. This matches the standard WP plugin-author boilerplate — every meta-box save handler checks `DOING_AUTOSAVE` and `wp_is_post_revision()` itself specifically *because* core does not filter the hook for you. Corrected table:

| Hook | Fires for a staged revision? | Why | Our guard |
|---|---|---|---|
| `save_post_{post_type}` / `save_post` / `wp_insert_post` (action) | **Yes, unconditionally.** | No post_type guard exists in `wp_insert_post()` (post.php:5165-5211) — corrects this session's earlier, wrong claim. | Not core's doing: `inc/schedule-sync.php`'s `sn_schedule_sync_post()` and `inc/post-settings.php`'s `sn_post_settings_save()` both carry their own explicit `wp_is_post_revision( $post_id )` check before doing anything — the standard boilerplate pattern, confirmed present in both files by direct read. |
| `transition_post_status` | **Yes**, unconditionally. | Only guarded by attachment-vs-not in `wp_insert_post()`; a revision insert isn't an attachment, so `wp_transition_post_status( 'inherit', 'new', $revision_post )` fires same as any other insert (post.php:5082-5083). | Five modules hook it: `ml-artifacts.php`, `ai-prepopulate.php`, `indexnow.php`, `webhooks.php`, `websub.php`. Each is independently safe because it separately checks post_type (never `'revision'` in any `post`/`page`/allowlist check) and/or requires `'publish'` to be involved on either side of the transition (a revision's status is always `'inherit'`). `ml-artifacts.php` additionally calls `wp_is_post_revision()` explicitly — internal evidence this exact gotcha was already found and guarded once before this session. |

The corrected pattern: **nothing in WordPress core skips a hook because the row is a revision.** Every safety property this file relies on — for `save_post` and for `transition_post_status` alike — comes from a plugin-side `wp_is_post_revision()` (or equivalent) check, verified present in each of the five modules above, not from a core-level filter. Pinned directly in Test 8 with a real-contract-faithful stub (see tests/sn-apply-revision.php header) plus guard-representative callbacks mirroring `ml-artifacts.php`'s and `schedule-sync.php`'s actual guard shapes, proving the *guard*, not an absent fire, is what keeps our plugin's hooks from cascading into an ML rebuild, a cron-fragment sync, or a provenance-chain write on every staged revision.

## The meta problem — recommendation, not yet built

Several future `sn_apply` change types (`surfaces`, `og_card`, `alt_text`) are postmeta writes. Core revisions don't carry arbitrary meta unless a key opts in via `register_post_meta( ..., 'revisions_enabled' => true )` (WP 6.4+) — SN registers none of its relevant meta keys that way today, and auditing every `register_post_meta()` call site to add it is out of this session's scope (6a is the content-field primitive only). **Recommendation for 6b: do not chase `revisions_enabled` yet.** Ship the separate staged-meta draft queue instead (`snt_sn_apply_stage_meta()` / `snt_sn_apply_get_staged_meta()`) — one `wp_options` row per `(post_id, meta_key)` holding `{proposed_value, staged_at, fingerprint}`, explicitly **not** postmeta (pinned: `get_post_meta()` returns unchanged after staging). The reasoning: a postmeta value is live data by every other reader in the codebase the moment it's written (surfaces cache, OG card generator); a staged option row is inert until something explicit promotes it. `fingerprint` is opaque and caller-supplied (e.g. the `sn_scan` candidate's fingerprint) — this primitive stores it, never interprets it, leaving the "is this stale" semantics to 6b's gate design.

## Failure honesty — deliberately bypasses `wp_save_post_revision()`

`wp_save_post_revision()` (the higher-level core function most code calls) silently returns `null`/`0` when the post type doesn't support revisions, when `wp_revisions_to_keep() === 0`, or when content is unchanged (`wp_save_post_revision_check_for_changes` filter). Per the task's own guardrail — a revision-disabled post type must error loudly, never silently write nothing — `snt_sn_apply_stage_revision()` runs its own `post_type_supports( $type, 'revisions' )` and `wp_revisions_to_keep()` checks FIRST, returning `WP_Error` (409, not swallowed) on either, and only then calls `_wp_put_post_revision()` **directly**, bypassing `wp_save_post_revision()`'s own silent-skip paths entirely — including its "unchanged content" skip, so an unchanged-content proposal still stages (sn_apply's `dry_run` diff is the right layer to decide "nothing to change," not this primitive).

## The mode-semantics decision trail (an ambiguity in the task brief, resolved and recorded)

The task brief's design section reads, verbatim: *"mode:'publish' for this change type REFUSES at the mode-support layer exactly like og_card/anchor_sweep refuse revision ... mode:'revision' also refuses (no parent post exists to stage against) — create_draft is its OWN mode semantics: gate-checked draft insert, dry_run previews without inserting."* Read maximally literally, this says BOTH modes refuse — but that is not buildable: `snt_sn_apply_apply_one()`'s own control flow returns an `error` response (never a preview) the instant gate 3 fails, for EVERY mode, including the default `dry_run:true` path (see `inc/abilities-sn-apply.php`'s `$all_passed` check, which gates the diff-preview branch, not just the write branch) — so if gate 3 refused unconditionally, the very "dry_run previews without inserting" behavior the same sentence promises could never be reached, for any request, ever. That is a plain internal contradiction, not a subtle reading.

**Resolution taken**: `mode:"revision"` is the ONE mode create_draft's `snt_sn_apply_mode_support()` grants (gate 3 passes); `mode:"publish"` is the one that structurally refuses (gate 3 fails, reusing the exact og_card/anchor_sweep mechanism, reason naming "scheduled by hand"). ## Canonical target: content-derived, a deliberate LOOSENING from the other 8 types

`snt_sn_apply_canonical_target()` gained an optional `array $change = array()` parameter (backward-compatible default; the function's only call site, `inc/abilities-sn-apply.php`, now passes `$change` through). ## The block-delimiter check — narrower than full Gutenberg validation, by design

`snt_sn_apply_block_delimiter_findings()` is a raw-string, stack-based scan for `<!-- wp:name -->` / `<!-- /wp:name -->` / `<!-- wp:name /-->` balance, using PCRE recursion (`(?4)`) to consume nested-brace JSON attrs without truncating at the first `}` (tested standalone against 9 cases — balanced/self-closing/nested-attrs/unclosed/mismatched/namespaced/plain-text/broken-open — before wiring into the SUT). It deliberately does NOT attempt full Gutenberg block validation (comparing a block's stored `innerHTML` against its registered `save()` callback's re-render) — that would require every referenced block's registered PHP/JS render logic, impractical to run server-side for arbitrary or third-party blocks, and is a materially larger scope than "reject invalid block comment delimiters" as stated in the task. `parse_blocks()` alone does not catch this class of error — WP's own parser is lenient (a malformed delimiter is silently treated as freeform HTML, not an error) — which is exactly the gap this check exists to close.

**THE FINDING — tag vocabulary was gate-only, not structural (trap, memory-worthy).** `inc/sn-apply-create-draft.php`'s first draft passed the caller's RAW tag NAME strings straight to `wp_set_post_tags( $post_id, $names, false )`, reasoning that gate 2 (`snt_sn_validate_check_tags()`) had already proved every name sits in the existing vocabulary. **The hole**: WordPress core's `wp_set_post_tags()` — via `wp_set_object_terms()` underneath it — CREATES a new term for any STRING that matches nothing existing. The `$append` parameter (the third argument, `false` in the vulnerable call) controls whether the call REPLACES or ADDS TO the post's prior term associations; it has **no bearing on whether an unmatched name creates** — that misreading is the entire bug. So a gate-2 regression, a normalization mismatch between gate 2's check and the write step, or a race (a term deleted between the gate-2 read and the write) would silently INVENT vocabulary — the exact side effect `snt_sn_validate_check_tags()`'s own "existing vocabulary only" contract exists to prevent, and the exact class of bug this file's own `post_status`/`post_date`/`post_type` forbidden-field fence right above it demonstrates the fix for: **never trust an upstream gate alone for a dangerous value — make that value structurally unreachable in the write primitive itself.** The general shape of this trap: any WordPress core "set terms" call (`wp_set_post_tags()`, `wp_set_object_terms()`, `wp_set_post_categories()` with non-hierarchical or loosely-matched input) treats a STRING as "find-or-create" — passing STRINGS to any of them is never a safe way to express "attach to existing only," regardless of what any other flag on the call appears to say. The only safe contract is: resolve to the taxonomy's own numeric ids first, in application code, then pass ids.

**Fix (both layers, matching this repo's existing "resolve to the real thing, never trust the label" idiom):** `snt_sn_apply_resolve_tag_ids()` — inc/sn-apply-create-draft.php:287 — resolves every proposed name to an EXISTING `term_id`, reusing the exact same `sn_tag_normalize_key()` + `get_terms()` lookup `snt_sn_validate_check_tags()` performs (never a parallel matching scheme, so gate 2's verdict and this resolver can never disagree about what "existing" means); an unresolved name refuses `snt_sn_apply_unknown_tag` (422, naming the tag). `snt_sn_apply_write_create_draft()` now resolves tags BEFORE calling `wp_insert_post()`, not after — an unresolvable tag refuses before any post row exists, so a bad tag can never orphan a draft — and passes `wp_set_post_tags()` ONLY integer term_ids; an id that doesn't exist simply fails to attach, core never creates a term FROM an id.

# Session 6c addendum — the first real call broke on `target` (shipped v10.41.1)

The first real MCP client call to `sn_apply` (post-ship, v10.40.0) failed input validation on every call, regardless of what the client sent: `input[target][0] is not of type object`. Root cause, confirmed by reading `inc/mcp/mcp-tools.php`'s `sn_mcp_normalize_schema()` directly rather than assumed: `target`'s input schema declared its object/array union as a nested `oneOf` (`inc/abilities-sn-apply.php`) with **no top-level `type` key of its own** — `oneOf` was the property's only key. `sn_mcp_normalize_schema()` strips `oneOf`/`allOf`/`anyOf` at the schema **root only, by design** (its own comment: a nested combinator is "a real constraint the provider accepts"), so nothing in this codebase's own pipeline touches it — but the projected tool schema still reached the client as `"target": {}`, and at least one real MCP client facing a parameter with no discoverable type serializes whatever it's given as a JSON **string**. Same transport-transform class as the `wp_localize_script` scalar-casting lesson already in this program's memory: the schema (or a stub modeling one) has to model the transport's actual behavior, not just its happy-path shape.

**Fix**: replaced the nested `oneOf` with a `type` **array** union (`['object','array']`) carrying `properties` (object branch) and `items` (array branch) side by side. A `type` array is not a schema combinator — nothing strips it, at any depth, anywhere in this codebase's projection pipeline — and it is the exact pattern already load-bearing elsewhere (`sn-posts`/`sn-scan`'s `cursor`, every nullable output field across all five consolidated tools). Runtime target-resolution logic (`snt_sn_apply_resolve_target()`, `snt_sn_apply_is_batch_target()`) is byte-unchanged — this was a schema-only fix, plus a defense-in-depth transport-tolerance decode (`json_decode()` when `target` arrives as a string, 422 on an undecodable non-null string) added to `snt_ability_sn_apply()`'s own top.

**The sweep this fix's own ritual demanded caught a second, un-reported instance.** A new projection-round-trip test (`tests/mcp-projection-schema-types.php`) runs `sn_mcp_project_tool()` over all five REAL registered consolidated tools (`sn_posts`, `sn_site_facts`, `sn_scan`, `sn_validate`, `sn_apply` — this file's own count from Session 3/4/5/6b; there is no sixth tool registered anywhere in `inc/`, `sn_dismiss` is still unbuilt per this file's Session 1 finding #5) and asserts every projected property carries a usable type. It found `sn_validate`'s `checks` property (`inc/abilities-sn-validate.php`) with the **structurally identical** shape: `oneOf` between a literal `"all"` string and an array of surface tokens, no top-level `type`. This was not independently reported live — the sweep found it by pattern-matching the bug class, which is exactly the point of writing the sweep as a structural test rather than a one-off fix. Fixed the same way, same session: `type => ['string','array']`, plus the matching string-decode tolerance in `snt_ability_sn_validate()` (guarded so `checks:"all"` as a bare string — the documented, load-bearing "no proposal, validate published surfaces" call shape — never enters the decode path). No other property across the five tools' schemas triggered the sweep.

**Watched RED**: reverted both schema fixes (`git stash` on the two `inc/` files only) and re-ran the new test — it failed exactly as predicted, two violations, both named precisely (`inputSchema.target`, `inputSchema.checks`), 27 passed / 4 failed. Restored, re-ran green (31/31).

**Lesson for the standing memory**: a schema property whose ONLY type-bearing key is a combinator (`oneOf`/`anyOf`/`allOf`) is invisible to a projection pipeline that only strips combinators at the root — and invisible-to-projection reads as untyped to a client, which some real MCP hosts silently stringify rather than reject. `type` as an array union says the same thing as a two-branch `oneOf` without ever being a combinator a stripping pass could remove. # Session 6a addendum — staged revisions were backdated (shipped v10.41.2)

The second live defect of the `sn_apply` arc, owner-observed: a staged revision (post 1721, rev 2138) sat in wp-admin's revisions browser, but clicking Restore did nothing — the live post never changed. No error, no refusal; the ability had reported success and the staged excerpt genuinely existed as a revision row. Silent no-op class, not a crash.

Root cause, confirmed by reading the real WP 7.0.2 source directly (`/tmp/core-revision.php:75-96`, `_wp_post_revision_data()`) rather than assumed: core sets the REVISION row's `post_date`/`post_date_gmt` from `$post['post_modified']`/`$post['post_modified_gmt']` — i.e. whatever sits on the array `_wp_put_post_revision()` is handed, not the actual moment of insert. Every core caller of this helper runs it from `wp_save_post_revision()`, hooked on `save_post`, which fires AFTER `wp_update_post()` has already stamped the parent's `post_modified` to "now" — so at the instant core reads that field, it genuinely is now. `snt_sn_apply_stage_revision()` (session 6a, v10.40.0) calls the same core helper from a structurally different moment: staging is defined by NEVER touching the live row, so the snapshot handed to `_wp_put_post_revision()` carried `$live['post_modified']` verbatim — the post's actual last edit, which the docblock's own design already knew could be arbitrarily stale (that staleness is the entire point of a non-live staging primitive). The staged revision inherited that stale date as its own `post_date`, collided with (or predated) the newest genuine revision, and wp-admin's revisions browser — which sorts by date — placed the stale-dated staged row as the CURRENT revision. WordPress disables the Restore button on whichever revision it considers current. Silent, by design, on the WordPress side; the bug was entirely upstream, in handing core an input it never expected to be stale.

## The lesson, stated generally

Reusing a core helper OUTSIDE its designed call moment means every input the helper derives from context — not just the inputs the caller explicitly overrides — must be re-derived for the caller's OWN moment. `_wp_put_post_revision()`'s date fields are not documented as "pass the current time here"; they are silently, structurally coupled to WHEN core itself calls the function. Session 6a's original design correctly reasoned about the allowlisted content fields (`post_title`/`post_content`/`post_excerpt` — explicitly overridden) and the identity fields (`post_parent`/`post_status`/`post_type`/`post_name` — built fresh by core, never touched) but missed that `post_date`/`post_date_gmt` are a THIRD category: derived by core from context that is only valid at core's own calling moment, silently wrong at any other. The fix (`inc/sn-apply-revision.php`): override `post_modified`/`post_modified_gmt` on the snapshot to `current_time('mysql')`/`current_time('mysql', 1)` — the actual staging moment — immediately before the `_wp_put_post_revision()` call, using the same idiom core itself uses when stamping a real update. The live post row is still never written; this changes only the array handed to the revision-insert path, so the byte-identical-live-row guarantee (acceptance test 6) needed no change and re-verified green.

# Session 7 pre-design — the acceptance gap (`restore_revision`)

Recorded 2026-08-04, design only — nothing here ships until the owner greenlights the arc. The two-week telemetry baseline (running since 2026-08-01) gates RETIREMENTS, not additions, so the build can land any time after that greenlight; it deliberately did not land the day this was written (release cadence already at 3 for 2026-08-04).

## The gap, restated from the live arc

`sn_apply`'s `mode:"revision"` responses advertise `rollback:{method:'restore_revision', revision_id}` — but no MCP path can EXECUTE a restore. Accepting a staged revision today means classic wp-admin (works post-v10.41.2) or WP-CLI; the Desktop Mode portal's own Restore button is broken UPSTREAM (live-observed: a real blue Restore control producing no server request at all; `wp eval 'wp_restore_post_revision(2139);'` → `int(1721)` instantly — likely desktop-mode PR #444's keep-links-inside-window interception swallowing `revision.php` links; filing it is the owner's call, a public action).

## The decisive fact, found in the shipped code, not the spec

`snt_sn_apply_restore_revision()` already exists (session 6a built the wrapper around `wp_restore_post_revision()`) but is content-only — and the staged-META queue (`snt_sn_apply_stage_meta()`'s one-option-per-key rows) has NO application path anywhere. A human restoring via wp-admin applies the content revision and strands queued meta in `wp_options` forever; the button knows nothing about `snt_sn_apply_staged_meta_*`. So the acceptance path is not merely inconvenient — it is structurally INCOMPLETE for any future meta-staging change type (alt_text, surfaces). Only an sn_apply-owned restore path can atomically finish what staging started (restore content + apply queued meta + clear the queue).

## Trust-posture analysis — the objection that dissolves

First instinct: an MCP-executable restore lets the agent accept its own PR, gutting the pattern. The shipped architecture already answers this. Gate 3 grants `mode:"publish"` to the rw door's bound owner credential and `revision`-only to every other identity (`snt_sn_apply_granted_modes()`, enforced server-side against the calling identity, never a client parameter) — and `og_card`/`anchor_sweep` are ALREADY publish-only live side effects the owner credential can execute today. `mode:"revision"` is a chosen discipline for the owner credential and an enforced CEILING only for future routine credentials. A `restore_revision` change type declared publish-only in `snt_sn_apply_mode_support()` (the exact structural mechanism `og_card`/`anchor_sweep` use to refuse revision mode) inherits that split for free: routine credentials are refused at gate 3 by construction; the owner credential gains nothing it does not already hold. The human gate stays where it already lives for every publish-mode call — `dry_run` defaults true, and `dry_run:false` only ever on explicit owner instruction.

## Verified core contract (real 6.9 source, fetched raw — the 6a lesson applied BEFORE building this time)

`wp_restore_post_revision()` is `wp_update_post()` fed the revision's allowlisted fields, then an `_edit_last` meta stamp and the `wp_restore_post_revision` action. NOTHING in it guarantees a pre-restore snapshot: the pre-restore live state survives only if the last writer happened to leave a matching revision row. Consequence: the change type must guarantee its OWN rollback point, and session 6a's `snt_sn_apply_stage_revision()` is exactly the primitive — before restoring, if the newest existing revision does not match the live row's current content, stage the live row's own current content as a revision (never touching the live row; its defining property). The response's rollback then points at THAT snapshot, so the loop stays closed under repeated application. Per the 6a timing lesson, that snapshot gets the staging-moment date fix for free (it IS `snt_sn_apply_stage_revision()`).

## Proposed shape (to be adversarially reviewed at build time, as always)

- `change.type: "restore_revision"`, PUBLISH-ONLY via `snt_sn_apply_mode_support()` — a restore IS a live write; "staging a restore" would stage a revision of a revision, refused with the honest reason like `og_card`'s.
- `target {post_id}`, `payload {revision_id}`.
- Structural pre-check BEFORE the gates run: the revision exists, is `post_type` `revision`, and its `post_parent` === target `post_id` — the cross-target idempotency lesson (REJECT #8) generalized: never act on another target's artifact. NOT restricted to sn_apply-staged revisions: wp-admin lets a human restore any revision of the post, and narrowing below the human's own capability buys nothing.
- Gate 1 fingerprint: binds to the LIVE row's current content hash (the same scheme `sn-posts` exposes as `content_hash`) — a restore proposed against a since-edited post is the stale-branch merge conflict, 409. This gives the type a REAL fingerprint scheme, not a `skipped`.
- Gate 2 validation: runs the applicable `sn_validate` check families against the REVISION's content — the would-be live state — exactly as they run against a proposed payload today.
- Gate 3: publish-only structural matrix + identity capability, both existing mechanisms, zero new code classes.
- Gate 4: target-scoped idempotency as shipped; replaying a completed restore returns `replayed:true`.
- Write step: ensure-rollback-snapshot (above) → `snt_sn_apply_restore_revision()` (existing wrapper) → apply-and-clear any `snt_sn_apply_staged_meta_*` rows for the post whose fingerprints still match → response `rollback:{method:'restore_revision', revision_id:<pre-restore snapshot>}`.
- `dry_run:true` (default): all gates + a diff of live vs. revision, zero writes — the owner reads the diff in chat and says "apply", the same acceptance conversation the arc's capstone already ran.

## Alternatives weighed

(a) Plugin admin UI card (a "Staged changes" notice with its own nonce'd restore) — redundant with classic wp-admin for content, still can't be reached from the broken portal without fighting desktop-mode's interception on its own turf, and would need its own meta-queue application path anyway (net: all the write-path work, plus UI, minus the MCP loop closure). (b) Do nothing + file upstream — leaves the advertised rollback contract unexecutable and the meta queue stranded regardless of the portal fix. Recommendation: build `restore_revision` (one session, primitive + wrapper already exist), AND file the portal bug upstream — they fix different layers. DECISION PENDING OWNER.

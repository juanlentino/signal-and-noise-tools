the deployed `sn-remote-mcp` bundle) was re-verified here against the code of
both repos (plugin `dc6f4acb`, Worker `bab42d3`, which the live status route
reports as deployed) and against the live site. Every claim was treated as a
lead. This file records each finding, its verdict, the evidence, what shipped,
what did not and why, and the numbers.

Shipped: plugin branch `fix/mcp-doors-audit`, Worker branch
`feat/contract-24-output-schemas`. No version bump, no tag.

## Findings

### F1. The bridge budget and code mode (Owner)

- p50/p95 bridge latency are not recorded anywhere readable without a
  Cloudflare token. The Worker logs `ms` per `bridge_call` to Workers Logs
  only. The origin records `latency_ms` per remote call, but it times only the
  ability's execution, and the one reader (`sn-site-facts{tool_telemetry}`)
  returns averages: 154 ms over 92 remote calls since remote logging began
  (2026-10-12); `remote-machine-readers-summary` averages 1,000 ms. Averages
  cannot give percentiles, so none are claimed.
- Subject: the Access `sub` for a person, `common_name` for a service token
  (`access.mjs:183-186`); both budgets key on it. Through Cloudflare's MCP
  portal the identity depends on the portal's "Require user auth" setting: on,
  each user arrives as themselves; off, every portal user arrives as the admin
  who authorized the server. **Owner check.**
- Recommendation if code mode goes on: `BRIDGE_RATE_LIMIT_PER_MIN=30`,
  `RATE_LIMIT_PER_MIN=60`. A script's every step spends both budgets, and the
  fixed window lets about twice the limit through across a boundary. Worst
  case on the 2-vCPU shared origin is 30 slow calls a minute, about 30 s of PHP
  time per minute; typical is about 5 s. Not changed: Worker variables are the
  owner's.

### F2. Remote tools publish no output schemas (Ship, contract 24)

Shipped. The twins' raw output schemas are projected by the laptop doors' own
function, `sn_mcp_project_output_schema()`, through
`sn_remote_contract_wire_schemas()`.

**Why the null wrap, and why it must not be simplified.** A declared
outputSchema makes `structuredContent` required and an object. Five twins can
answer a non-object: `remote-get-analytics-events` (a list) and insights,
narration, health scan and provenance integrity (null until their first run).
Those five arrive as `{result: …}`, exactly as the laptop doors wrap them
(`mcp-tools-call-parts.php:189-197`). An object-root twin's empty PHP array
arrives as `{}`. An object-root twin that answers anything else cannot match
its schema, so the Worker refuses it as `output_schema_mismatch` rather than
send an invalid result. Before contract 24 the Worker omitted
`structuredContent` for null; that was legal only because no schema was
declared, and it is what made the 2026-08-14 null incident survivable. Remove
the wrap and the five nullable or list answers fail at the client again.

**Why the hash changed what it covers.** The raw schemas did not change, so
hashing them again would have repeated 23's hash, which
`tests/remote-contract-shapes.php` refuses (a bump without a shape change).
From 24 the hash covers the projected (wire) schemas, which is what a client
validates.

**One source.** `php tests/remote-contract-shapes.php --write` writes
`tests/fixtures/remote-output-schemas.json` (the suite pins it byte for byte).
The Worker carries a copy at `src/remote-output-schemas.json`, and its
`test/output-schemas.test.mjs` re-derives the plugin's hash over it with a
PHP-compatible encoding, so the Worker's CI needs no plugin checkout (its
slug-drift test already skips in CI for that reason) and a hand edit to either
copy goes red. No runtime fetch.

**Errors.** Bridge refusals carry their code and message in the text block and
no `structuredContent`, as the laptop doors do (`sn_mcp_error_result`). A
schema covers `structuredContent` whenever it is present, and `{ok, error,
message}` is no twin's shape. Every refusal still refuses. Ping is unchanged,
including its pre-existing quirk: its argument refusal returns `{ok:false, …}`,
which its own outputSchema does not allow.

**Strictness.** No twin schema declares `additionalProperties: false`, so an
additive origin field during plugin and Worker skew is not a client refusal.

**Known limit: the shape is checked at the root only.** The bridge route
returns `execute()`'s output as is, and the Worker checks only the root. The
official TypeScript SDK validates `structuredContent` against the schema (all
19 schemas compile in its Ajv), so a nested object field the origin encodes as
`[]` (an empty PHP `array()`) would now fail at the client. The independent
review traced every free-form object field it could and found no producer that
emits `array()` today (bot-signals cohorts are pre-seeded, rss windows have
fixed keys, Machine Readers verification uses `(object)`); the rest are
unaudited. Closing it means a strict check over real twin outputs in a plugin
test, or schema-driven `[]` to `{}` coercion in the Worker. Not done here.

**Real payloads.** The Worker tests validate a generated full instance per
tool and a null per nullable twin against the schemas, with a checker for the
keywords these schemas use (it is shown to fail). Real production payloads
are not committed as fixtures: they carry site analytics and search queries.

**Size.** The Worker's `tools/list`: 24,715 B (pretty) / 20,035 B (compact)
before, 53,589 B after (compact). That is the price of typed results.

### F3. The laptop doors' definitions are heavy (Propose; not shipped)

Measured live, `tools/list` uncompressed:

| | Read door | Write door |
|---|---|---|
| Tools | 53 | 18 |
| Bytes | 131,787 | 40,894 |
| Estimated tokens (bytes ÷ 4) | ~33k | ~10k |
| Descriptions | 52.2% | 70.1% |
| outputSchema | 33.3% (43,884 B) | 11.0% |

Largest: `sn-apply` 22,152 B (description 19,952 chars, ~5k tokens, 54% of the
write door); `sn-scan` 7,659 B; `edge-errors-summary` 6,512 B (5,304 B of it
outputSchema); `sn-site-facts` 5,551 B. Whether clients pass outputSchema to
the model is unverified.

**sn-apply cannot shrink much safely.** Split into 89 rule units, kept by the
rule "nothing safety-relevant leaves the description": 1,868 chars (9.4%)
could move (history, incident narratives, response-field catalogs). After a
pointer, the write door drops 4.3%. It is small because `change.payload` is
`{type: object}`: the description is the only place the payload contract is
written, and nearly every shape sentence carries an enforced constraint
(byte-exact spans, plain prose, existing tags only, `position` default "after",
UTC-day matching). Two better levers: state each repeated rule once (the
fingerprint rule appears about 7 times; about 1.2-1.4k chars), and type
`change.payload` per change type in the input schema.

**The read-door tools trim well:** `sn-scan` 7,659 → 3,658 B and
`sn-site-facts` 5,551 → 2,622 B by moving catalogs and rationale to
`sn://sn-scan-manual` and `sn://sn-site-facts-manual` (resources are served on
both doors). That is 5.3% of the read door. Costs: three tests pin four
resources, `tests/abilities-sn-scan.php:830-831` pins wording that would move,
and `sn://abilities-catalog` reads the descriptions, so a manual needs its own
source.

**Side finding:** sn-apply's description does not name four types it accepts,
all publish-only (`dismiss`, `merge_tags`, `clear_template_overrides`,
`schedule_cron_event`); one 248-char line would. And `target.scope`'s enum
(`inc/abilities-sn-apply.php:115`) may not admit the scopes three of them
resolve (`executors-resolve-parts.php:126-143`). Unverified.

### F5. The bridge secret: doc and code disagreed (Ship)

Shipped. `bridge_token` resolves from `SN_BRIDGE_TOKEN` only: the keyring row
has no option and no site derivation (the Credentials screen locks it), the
`sn_bridge_secret` filter is gone, and `sn_bridge_secret()` reads the constant.

**Why constant-only, and why it must not be "simplified" back.** An option is
readable by anything that reaches the database (an admin-level compromise, a
plugin vulnerability, a leaked SQL dump), and this value opens `/bridge`.
wp-config.php is readable by no web request.
Since 15.2.0 the keyring could fill the constant from the `sn_bridge_token`
option or the site secret, so the revoke runbook's step 4 (delete the
constant) did not revoke while either held a value.

Live, the value came from the constant (read 2026-10-26 from
`keyring-status`'s per-row `source` field only), so nothing changes on the
site.

**Report only, the other site-derived secrets.** The docblock's reasoning
applies to all of them; ranked by what a database-only reader gains:
`site_secret` (from an option; one read yields every row switched to it),
`prov_hmac_secret` (forges ledger writes; from the constant today), `srv_token`
and `mr_read_token` (from their own options). Not changed.

### F6. The setup page pinned nothing (Ship the page; config reported)

Shipped: both setup surfaces (`inc/admin-forms/mcp-connect.php`, the native
leaf `ai-mcp-connect-steps.php`) say `@automattic/mcp-wordpress-remote@0.5.4`,
and why: the package runs with the admin Application Password in its
environment. The 405 docblock's `mcp-remote` stays; it records a real event.

The owner's Claude Desktop config (read, redacted, not edited): `sn` and
`sn-write` both run `~/.local/bin/mcp-remote`, a global install of
`mcp-remote` 0.3.2 (2026-09-12), so effectively pinned. The Authorization
header points at environment variables. The npm package changed source: to
0.1.37 it came from `geelen/mcp-remote`; 0.3.2 and later from
`punkpeye/mcp-remote`, with a different maintainer. No edit needed while on
0.3.2; any reinstall should name an exact version after checking the new
maintainer.

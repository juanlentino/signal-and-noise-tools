## v4.0.2 — Inline-`<img>` alt Suggest + Copy

### Why

v4.0.0 scoped this out because inline-img findings have no attachment_id (their `subject_id` is the parent post ID), and the existing `snt_ai_alt_suggest_impl()` rejects non-attachment inputs with `snt_ai_not_attachment`. The CHANGELOG entry for v4.0.0 explicitly defers inline-img Suggest to v4.0.x.

Apply itself stays deferred indefinitely (editing `post_content` to mutate inline `<img alt="…">` is a block-serialization-roundtrip problem per WORDPRESS-REFERENCE.md gotcha #4). v4.0.2 ships **Suggest + Copy only** — user copies the suggestion, opens the editor, pastes into the alt field.

### Impl boundary decision (deferred from v4.0.0)

Two options exist:

| Option | Description | LOC |
|---|---|---|
| **A** | Extend `snt_ai_alt_suggest_impl()` to accept polymorphic input — either `attachment_id` OR `(post_id, image_src)` tuple. Schema gets `oneOf` constraint. | ~50 |
| **B** | New impl + new ability `signal-noise/ai-alt-inline-suggest` with separate schema `(post_id, image_src)`. Mirrors the v4.0.0 paired-impl convention but creates a sibling ability. | ~80-100 |

**Recommended: Option B.** Reasoning:
- Polymorphic input schemas (Option A's `oneOf`) are awkward in the Abilities API — every existing ability has a clean single-shape `input_schema`. Breaking that pattern for one ability costs consistency.
- Option B reuses the canonical Suggest+Apply pattern from `feedback_health_suggest_apply_pattern.md` memory — one impl per check-type-variant, clean schemas.
- The prompt design differs anyway: attachment-alt context = attachment title + caption + filename + referencing post; inline-img context = surrounding paragraph in the post body. Two prompts is more honest than one prompt with conditional context gathering.
- Code reuse for the shared parts (AI gate, prompt building helpers, response parsing) can come via small helper functions if the duplication gets ugly.

### Files

**New:**
- `inc/ai-alt-inline-suggest.php` (~90 LOC) — `snt_ai_alt_inline_suggest_impl($post_id, $image_src)` + 1 REST endpoint

**Edited:**
- `inc/abilities-registration.php` — register `signal-noise/ai-alt-inline-suggest` (1 ability, idempotent annotation; no apply ability since Apply is deferred) + 1 execute callback
- `inc/health-checks-admin.php` — modify `sn_health_render_suggest_cell()` to handle the inline-img case (currently returns empty string for `subject_type === 'inline_img'`; change to return a Suggest button with `data-check="missing_alt_inline"` + `data-post-id` + `data-image-src`)
- `assets/health-suggest-actions.js` — add `missing_alt_inline` to `ABILITY_BY_CHECK` dispatch map (no apply ability — `apply` field is null/undefined); modify `renderSuggestion()` to detect the no-apply case and render Copy button + helper text instead of Apply + Discard
- `signal-and-noise-tools.php` — `require` the new file
- `CHANGELOG.md` — v4.0.2 entry

### Prompt design

```
const SNT_AI_ALT_INLINE_SUGGEST_SYSTEM = 'Generate descriptive alt text for an image referenced by URL in a post body. ' .
    'Output 80-125 characters. Describe the image factually based on the surrounding paragraph context + the URL filename. ' .
    'No "image of" / "picture of" / "photo of" preamble. ' .
    'No alt="" (empty) suggestions — if there is not enough context, output only the literal marker: ALT_INSUFFICIENT_CONTEXT. ' .
    'Output ONLY the alt text or the marker — no quotes, no preamble, no markdown.';
```

Context gathered: URL filename (`wp_basename($image_src)`), post title, the paragraph containing the inline-img tag (extracted via regex around the `<img src="...">` match).

### Cost

Same as attachment-alt: ~$0.001 per Suggest click. Bounded to user clicks; no batch generation across inline-img findings unless the existing "Suggest all" button surfaces them.

**Note:** "Suggest all N" on missing_alt sections currently iterates ALL findings (attachment + inline). After v4.0.2, batch generation will hit both impls. This is fine — the throttle stays at 500ms and the per-call cost is the same.

### Verification gates

- G1 (v4.0.2): inline-img Suggest button renders on inline-img missing_alt findings (only the empty-cell case was the v4.0.0 behavior)
- G2: Click Suggest on an inline-img finding → reasonable proposal within ~5s + Copy button + helper text "Open the editor to apply" + NO Apply button
- G3: Click Copy → clipboard contains the suggestion + status text confirms
- G4: "Suggest all N" still works correctly when the section contains both attachment + inline-img findings (each row gets its own Suggest result with appropriate UX)
- G5: `php tests/abilities-integration.php` → adds ~4 new assertions (suggest happy path + capability denial + missing required field), total ~129/0

### Estimated effort

~120 LOC. 1-2 hours via subagent-driven dev.

## v4.0.3 — Before/After Apply preview modal

### Why

v4.0.0's Apply UX is "edit the textarea (optional), confirm() dialog, write." The user accepts the suggestion on faith — no visual confirmation of what changes look like in context. The cost audit conversation surfaced this as a real UX gap.

A Before/After modal shows the original content + the proposed change side-by-side, with Accept/Cancel actions. Catches "wait, that's not what I expected" before the destructive write.

### Scope

Modal triggers on Apply click (replacing the current `window.confirm()`). Modal contents:

**For attachment-alt Apply:**
- "Before" pane: the attachment's current alt text (empty for findings since these are missing-alt findings, but show the attachment thumbnail + filename for context)
- "After" pane: the proposed new alt text
- Visual: side-by-side comparison; mobile collapses to stacked

**For drift-phrase Apply:**
- "Before" pane: a snippet of `post_content` around the phrase position (~80 chars before + ~80 after) with the phrase highlighted in red
- "After" pane: same snippet with the phrase replaced by the proposal (highlighted in green)
- Visual: diff-style, monospace, line-wrapped

### Files

**New (or extend existing JS):**
- `assets/health-suggest-actions.js` — add modal rendering functions (`renderBeforeAfterModal()`, `closeModal()`); modify `onApplyClick()` to call modal instead of `window.confirm()`. ~80-100 new JS LOC
- `assets/health-suggest-modal.css` — modal styling (or inline styles per existing JS file convention). Maybe ~40 LOC

**Edited:**
- `inc/health-checks-admin.php` — possibly enqueue a CSS file if using `.css` approach (probably skip; inline styles match existing pattern)
- `CHANGELOG.md` — v4.0.3 entry

**Optional backend extension:**
- For drift-phrase modal, JS needs the "before" snippet context. Currently the Suggest response includes `fingerprint` but not the raw post_content slice. Options:
  - (a) JS already has `data-context` (the scan-time `context_snippet`) — use that as "before"; works but only ~200 chars
  - (b) Add `context_before` to the Suggest response (last 80 chars before phrase, current post_content)
  - (c) Make a second backend call to fetch the current snippet

  **Recommended: (a)** — use the existing `data-context` attribute. It's the scan-time snippet, but the fingerprint check at Apply time guarantees the post hasn't changed since scan, so the context is still accurate.

### UX details

- Modal overlays the admin page (fixed position, semi-transparent backdrop, escape key closes)
- Focus management: focus moves into the modal on open; returns to the Suggest cell's Apply button on close
- Keyboard: `Enter` = Accept, `Escape` = Cancel
- DOM-built (createElement + textContent, no innerHTML per XSS discipline from `assets/ai-meta-description.js` precedent)
- No external libraries; vanilla JS only

### Cost

Zero new AI cost. Pure UX layer on top of existing Apply flow.

### Verification gates

- G1: Click Apply on a missing-alt finding → modal opens with "Before" (empty / attachment thumbnail) + "After" (proposal) + Accept/Cancel buttons
- G2: Click Apply on a drift finding → modal opens with diff-style before/after of `post_content` snippet
- G3: Accept → write happens (same flow as v4.0.0) → modal closes → row marks Applied
- G4: Cancel → modal closes → row state unchanged
- G5: Escape key closes modal (same as Cancel)
- G6: Enter key in modal triggers Accept
- G7: Tab cycling stays inside modal (focus trap)
- G8: Modal works on mobile viewport (stacked panes instead of side-by-side)

### Estimated effort

~150 LOC. 2-3 hours via subagent-driven dev (the JS is more complex than typical because of focus management + keyboard handling).

## Sequencing rationale

**Why v4.0.2 first (inline-img) before v4.0.3 (modal)?**

1. **v4.0.2 closes the v4.0.0 scope debt explicitly flagged in the CHANGELOG.** It was deferred publicly; shipping it next discharges the obligation.
2. **v4.0.3's modal benefits both old features AND inline-img.** Building the modal in v4.0.3 means the inline-img case ships with v4.0.2's lighter UX (just Copy), then ALSO gets the modal benefit later. If v4.0.3 shipped first, inline-img (v4.0.2) would land with confusing "I see a modal for attachment-alt but not for me" inconsistency.
3. **Cost progression**: v4.0.2 adds a small AI cost (new inline-img Suggest button generates small bursts of AI calls during "Suggest all" batches). v4.0.3 adds ZERO new AI cost. Shipping v4.0.2 first proves the cost stays bounded before v4.0.3 layers UX on top.

**Why not bundle v4.0.2 + v4.0.3 into one ship?**

- Each is a coherent, independently-valuable feature
- Project's v3.8.x pattern was 1 focused feature per patch
- Smaller per-ship verification surface
- Easier CHANGELOG attribution

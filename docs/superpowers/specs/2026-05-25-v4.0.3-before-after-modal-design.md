# v4.0.3 Design — Before/After Apply preview modal

**Status:** Approved 2026-05-25 (brainstorm session, continuing v4.0.x roadmap)
**Target ship:** plugin v4.0.3 (patch 3/7 in v4.0.x)
**Estimated:** ~150 LOC + 6 file edits, 1-2 hours of execution time
**Predecessor decision:** Unified modal with conditional Before content (Option A from brainstorm) over per-check-type layouts.

---

## 1. Why this ships

v4.0.0's Apply UX is "edit the textarea, get a `window.confirm()` dialog, write." The user accepts the destructive AI write on faith — no visual confirmation of what changes will look like in context. The cost audit conversation (which surfaced v4.0.1's drift cache opportunity) also flagged this as a real UX gap.

A Before/After modal shows the original state + the proposed change side-by-side, with Accept/Cancel actions. Catches "wait, that's not what I expected" before the destructive write.

Closes the third planned v4.0.x patch per the roadmap (after v4.0.1 drift cache + v4.0.2 inline-img Suggest).

## 2. Scope

### In v4.0.3

- Custom modal component (vanilla JS, DOM-built, inline styles per existing `ai-meta-description.js` convention) replaces `window.confirm()` in `onApplyClick()`
- One modal component, two render variants based on `checkType`:
  - **Attachment-alt**: thumbnail + filename + "(no existing alt)" caption / read-only textarea with proposed alt
  - **Drift-phrase**: post_content snippet with phrase highlighted (red before / green after)
- Keyboard support: Escape = Cancel, Enter (modal focus, not in textarea) = Apply
- Focus trap: focus moves into modal on open, returns to originating cell on close
- Backdrop click = Cancel
- Mobile layout: panes stack vertically below 600px viewport width
- `signal-noise/ai-alt-suggest` ability gains `thumbnail_url` in output to power the modal's attachment thumbnail

### Out of scope

- **Modal for inline-img findings**: inline-img findings (v4.0.2) have NO Apply path — they use the `apply: null` sentinel which renders Copy button + helper text instead of Apply + Discard. The modal is irrelevant for those findings.
- **Modal for any FUTURE check types**: stale-posts + orphaned-media (v4.1.0) will decide modal usage at their own brainstorm. The v4.0.3 modal is general enough to reuse, but explicit "does v4.1.0 use the modal?" answers belong in v4.1.0's brainstorm.
- **External CSS file**: inline styles in JS match the existing `ai-meta-description.js` convention. No `assets/health-suggest-modal.css` is created.
- **Modal-CSS-as-CSS-Custom-Properties**: theming the modal via `:root` CSS variables is out of scope. Inline color hex values are fine.
- **Animations / transitions**: modal appears/disappears instantly. No fade-in, no slide-up. YAGNI.
- **Modal stack management**: only one modal can be open at a time (Apply clicks on multiple rows are sequenced by user clicks, not concurrent). No need for a modal stack or z-index management beyond a single fixed value.

## 3. Modal structure

Visual reference (ASCII mockup):

```
┌─────────────────────────────────────────────┐
│  Apply alt text to attachment?       [×]    │
├─────────────────────────────────────────────┤
│  Before              After                  │
│  ──────              ─────                  │
│  [160×160            [proposed alt text     │
│   thumbnail]          read-only textarea]   │
│  filename.png                               │
│  (no existing alt)                          │
├─────────────────────────────────────────────┤
│                       [Cancel] [Apply]      │
└─────────────────────────────────────────────┘
```

DOM structure (built via `createElement` chain):

```
div.snt-modal-backdrop (fixed, full-screen, semi-transparent black)
  └── div.snt-modal-box (centered, white, rounded, shadow)
      ├── div.snt-modal-header
      │     ├── h2 (title)
      │     └── button.snt-modal-close (× button)
      ├── div.snt-modal-body
      │     ├── div.snt-modal-pane-before
      │     │     └── (variant-specific content)
      │     └── div.snt-modal-pane-after
      │           └── (variant-specific content)
      └── div.snt-modal-footer
            ├── button.snt-modal-cancel
            └── button.snt-modal-apply
```

### Inline styles (key dimensions)

- Backdrop: `position: fixed; inset: 0; background: rgba(0,0,0,0.5); display: flex; align-items: center; justify-content: center; z-index: 100000;` (high z-index to layer above WP admin bar at z-index 99999)
- Modal box: `background: #fff; border-radius: 6px; box-shadow: 0 8px 32px rgba(0,0,0,0.2); max-width: 720px; width: 90vw; max-height: 90vh; overflow-y: auto;`
- Header: `display: flex; align-items: center; justify-content: space-between; padding: 16px 20px; border-bottom: 1px solid #e0e0e0;`
- Body: `padding: 20px; display: grid; grid-template-columns: 1fr 1fr; gap: 24px;` (on mobile: `grid-template-columns: 1fr;` via JS check on `window.matchMedia('(max-width: 600px)')`)
- Footer: `display: flex; justify-content: flex-end; gap: 8px; padding: 12px 20px; border-top: 1px solid #e0e0e0;`

## 4. Render variants

### Attachment-alt variant

**Before pane content:**
- `<img>` with `src` from `res.thumbnail_url` (new field added in §6), `style="max-width: 160px; max-height: 160px; display: block;"`
- `<p>` with the filename (extracted from `image_src` via JS) in `font-family: monospace; font-size: 12px;`
- `<p>` with "(no existing alt)" in italic gray

**After pane content:**
- `<textarea readonly>` with the user-edited value from the suggest textarea (captured from the existing `ta` variable in `onApplyClick`)
- Same dimensions as the suggest textarea for visual continuity
- A character count below the textarea showing `N chars`

**Title:** "Apply alt text to attachment?"

### Drift-phrase variant

**Before pane content:**
- `<div>` with `white-space: pre-wrap; font-family: monospace; font-size: 13px; line-height: 1.5;`
- Content built as 3 spans:
  - `<span>` with `context_snippet` left part (chars 0 to phrase-position)
  - `<span style="background: #fde8e8; color: #8b1a1a; padding: 2px 4px; border-radius: 2px;">` with the phrase
  - `<span>` with `context_snippet` right part (chars phrase-position+phrase-length to end)

**After pane content:**
- Same `<div>` shell as Before
- Same 3-span structure but the middle span uses the replacement value and green styling: `background: #e8f5e9; color: #0a5a1a;`

**Title:** "Replace phrase in post?"

The snippet position math: the drift Suggest response already has `context_snippet` (200 chars wide centered on the phrase) and the phrase + position. Inside the snippet, the phrase is at a known position computed from the original `position` minus the snippet's start offset. JS computes this client-side; no new backend call.

## 5. Keyboard + focus management

### On open

- Save the originating button (`btn` from `onApplyClick`) to a closure variable so `closeApplyModal()` can restore focus
- Append modal to `document.body`
- Move focus to the Apply button (NOT the Cancel button — primary action gets focus by default)
- Attach event listeners (see "Event handlers" below)

### Event handlers

- **Escape key**: document-level `keydown` listener. If modal is open and key is `Escape`, trigger Cancel.
- **Enter key**: same listener. If key is `Enter` AND focused element is not a `<textarea>`, trigger Apply.
- **Focus trap**: document-level `focusin` listener. If modal is open and the focus target is NOT inside `.snt-modal-box`, redirect focus back to the Apply button.
- **Backdrop click**: click listener on `.snt-modal-backdrop`. If `event.target === backdrop` (NOT a descendant), trigger Cancel.
- **Close button (×) click**: trigger Cancel.
- **Cancel button click**: close modal, no write, restore focus.
- **Apply button click**: close modal, then call the existing apply ability (same `callAbility` invocation as in v4.0.0).

### On close

- Remove all event listeners (avoid leaks)
- Remove the modal DOM
- Restore focus to the originating button
- The Apply path's `setStatus` + `renderApplied` chain continues unchanged (modal close happens FIRST, then the ability runs)

## 6. Backend touch — `thumbnail_url` field

The attachment-alt variant needs a thumbnail URL. Solution: extend `snt_ai_alt_suggest_impl()` output.

### Code change in `inc/ai-alt-text-suggest.php`

In the success-return block (after the `ALT_INSUFFICIENT_CONTEXT` marker handling), the current return is:

```php
return array(
    'ok'            => true,
    'suggestion'    => $suggestion,
    'attachment_id' => (int) $attachment_id,
);
```

Update to:

```php
return array(
    'ok'            => true,
    'suggestion'    => $suggestion,
    'attachment_id' => (int) $attachment_id,
    'thumbnail_url' => (string) wp_get_attachment_image_url( (int) $attachment_id, 'thumbnail' ),
);
```

`wp_get_attachment_image_url()` returns `false` if no thumbnail exists; PHP casts that to empty string. JS handles empty string by hiding the `<img>` and showing only the filename + "(no existing alt)" text.

### Schema change in `inc/abilities-registration.php`

For the `signal-noise/ai-alt-suggest` ability, update `output_schema.properties` to include `thumbnail_url`:

```php
'output_schema'       => array(
    'type'       => 'object',
    'properties' => array(
        'ok'            => array( 'type' => 'boolean' ),
        'suggestion'    => array( 'type' => 'string' ),
        'attachment_id' => array( 'type' => 'integer' ),
        'thumbnail_url' => array( 'type' => 'string', 'description' => 'Thumbnail URL for the attachment, or empty string if no thumbnail exists.' ),
    ),
),
```

### Backward compatibility

The added field is purely additive in the response. Older JS consumers (v4.0.0-v4.0.2 browser cache) ignore unknown fields — no regression. Newer JS (v4.0.3+) reads `res.thumbnail_url` when building the modal.

## 7. Backend touch — drift-phrase context snippet (NO change needed)

The drift Suggest response already returns `fingerprint`, `post_id`, `position`. The `context_snippet` is stored on the DOM element via `data-context` (set at scan-time by `inc/health-checks-admin.php` per v4.0.0 Task 5). JS already has access to it via `btn.getAttribute('data-context')`. No backend changes needed for the drift modal.

## 8. Mobile layout

Detect mobile via `window.matchMedia('(max-width: 600px)')` at modal-open time. If matches, set `grid-template-columns: 1fr` on the body element instead of `1fr 1fr`. Add a `<hr>` between the panes for visual separation when stacked.

No listener on viewport-resize during modal open — if user rotates phone mid-modal, layout may be slightly off but the modal still functions. YAGNI fix; can add later if real users complain.

## 10. Cost

**Zero new AI cost.** Modal is pure UI. `wp_get_attachment_image_url()` is a local function (no network); it queries the database for the attachment's metadata, which is already in WP's object cache from the prior `get_post()` call in the same impl invocation.

## 13. Open questions

The brainstorm phase locked the major decisions:

- ✅ Unified modal with conditional Before content (over per-check-type layouts or skip-attachment-alt)
- ✅ Inline styles in JS (matches existing `ai-meta-description.js` convention)
- ✅ Vanilla JS focus trap via document-level `focusin` listener
- ✅ Escape = Cancel, Enter = Apply (default modal keyboard pattern)
- ✅ Backdrop click = Cancel
- ✅ Mobile breakpoint at 600px
- ✅ Thumbnail via `wp_get_attachment_image_url(..., 'thumbnail')` returned in Suggest response (Option A)

Remaining decisions deferred to execution-time judgment:

- **Modal close animation**: defaulting to instant. Could add a 100ms fade if visual feedback feels too abrupt during gate-walking. Cheap fix-forward.
- **Character count placement**: defaulting to below the textarea, right-aligned. Could move inline-right in textarea label. Cosmetic.
- **"No thumbnail" fallback visual**: defaulting to just hiding the `<img>` element. Could add a placeholder icon. YAGNI for v4.0.3; can revisit if real-world testing surfaces it.

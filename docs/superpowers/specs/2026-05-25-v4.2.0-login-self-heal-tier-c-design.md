## 3. Investigation summary (already complete)

This spec's brainstorming pass located the bug:

**Bug 1 — D-06 instance (latent, contributing):** `inc/admin-page.php:641-648` (`save_login` handler) reads/writes `sn_settings` via direct `get_option`/`update_option`, bypassing the `sn_setting()` accessor (`inc/settings.php:80`). The accessor has a per-request static cache (`static $merged = null` at `settings.php:81`). Within the save POST request, anything that calls `sn_setting('login.slug')` after the save gets the STALE cached value. Currently latent because no co-request code reads the slug post-save, but the failure mode is one refactor away.

Two other direct-call sites in the same file: `admin-page.php:773-779` (`save_insights_settings`) and a related sibling save handler.

**Bug 2 — flush sentinel false-positive (proximate cause of the 404):** `inc/login-hide.php:106-113` only fires `flush_rewrite_rules()` when `sentinel !== current_slug`. The sentinel can desync from the actual `rewrite_rules` option state via:
- Silent `update_option('rewrite_rules', ...)` failure during the original flush
- Another plugin calling `delete_option('rewrite_rules')` after our flush
- WP's `wp_rewrite_rules()` deferring to `wp_loaded` and the deferred handler failing

Once desynced, the sentinel says "done flushing for `backend`" while `rewrite_rules` doesn't actually contain `^backend/?$`. No self-healing path exists.

**Plus a contributing factor:** the `save_login` handler doesn't call `flush_rewrite_rules()` directly. It relies entirely on the next request's init hook firing the flush. If that flush fails silently, there's no second chance until manual intervention (Settings → Permalinks → Save Changes).

## 5. Architecture

### 5.1 Login self-heal

**File:** `inc/login-hide.php`

**Before** (lines 106-113):

```php
add_action( 'init', function() {
    $current = sn_login_get_slug();
    $flushed = get_option( 'sn_login_rewrites_flushed' );
    if ( $flushed !== $current ) {
        flush_rewrite_rules( false );
        update_option( 'sn_login_rewrites_flushed', $current );
    }
}, 99 );
```

**After:**

```php
add_action( 'init', function() {
    $current = sn_login_get_slug();
    $flushed = get_option( 'sn_login_rewrites_flushed' );

    // v4.2.0: verify-before-trust — sentinel can desync from
    // rewrite_rules option (silent update_option failure, another
    // plugin wiping the option, WP's deferred-flush failure). Re-check
    // that our rule is actually present before trusting the sentinel.
    $pattern      = '^' . preg_quote( $current, '/' ) . '/?$';
    $rules_option = get_option( 'rewrite_rules' );
    $rule_present = is_array( $rules_option ) && isset( $rules_option[ $pattern ] );

    if ( $flushed !== $current || ! $rule_present ) {
        flush_rewrite_rules( false );
        update_option( 'sn_login_rewrites_flushed', $current );
    }
}, 99 );
```

**Properties:**
- Sentinel match + rule present → no flush (no regression on happy path)
- Sentinel match + rule absent → flush (self-heal triggered)
- Sentinel mismatch → flush (existing behavior preserved)
- Idempotent: after the heal flush, sentinel matches AND rule is present, so subsequent requests no-op

### 5.3 D-06 fix: accessor enforcement

**File:** `inc/settings.php`

First, refactor `sn_setting()` to support cache reset via a sentinel path:

```php
function sn_setting( $path, $default = null ) {
    static $merged = null;

    // v4.2.0: sentinel path forces cache reset. Used by
    // sn_setting_reset_cache() — no other call site should pass this.
    if ( '__sn_reset_cache__' === $path ) {
        $merged = null;
        return null;
    }

    if ( null === $merged ) {
        $stored = get_option( SN_SETTINGS_OPTION, array() );
        $merged = array_replace_recursive(
            sn_settings_defaults(),
            is_array( $stored ) ? $stored : array()
        );
    }
    // ... rest unchanged from current implementation
}
```

Then add two new helpers below `sn_setting()`:

```php
/**
 * Bust the per-request static cache. Call after any write to
 * sn_settings option that happens outside sn_setting_update().
 */
function sn_setting_reset_cache() {
    sn_setting( '__sn_reset_cache__' );
}

/**
 * Write a single dot-path setting + bust the cache + return success.
 *
 * @param string $path  Dot-delimited path (e.g. 'login.slug').
 * @param mixed  $value New value.
 * @return bool True if value is correctly present after the write
 *              (re-read disambiguates "no change" from "real failure").
 */
function sn_setting_update( $path, $value ) {
    $settings = (array) get_option( SN_SETTINGS_OPTION, array() );
    $segments = explode( '.', $path );
    $cursor   =& $settings;
    foreach ( $segments as $i => $segment ) {
        if ( $i === count( $segments ) - 1 ) {
            $cursor[ $segment ] = $value;
        } else {
            if ( ! isset( $cursor[ $segment ] ) || ! is_array( $cursor[ $segment ] ) ) {
                $cursor[ $segment ] = array();
            }
            $cursor =& $cursor[ $segment ];
        }
    }
    unset( $cursor );

    $ok = (bool) update_option( SN_SETTINGS_OPTION, $settings );
    sn_setting_reset_cache();

    // gotcha #10 disambiguation: re-read confirms vs. update_option
    // returning false on "no change."
    $re_read = (array) get_option( SN_SETTINGS_OPTION, array() );
    $cursor  = $re_read;
    foreach ( $segments as $segment ) {
        if ( ! is_array( $cursor ) || ! array_key_exists( $segment, $cursor ) ) {
            return false;
        }
        $cursor = $cursor[ $segment ];
    }
    return $cursor === $value;
}
```

## 6. Data flow (login self-heal happy path)

```
[Admin saves new slug 'backend2']
  → save_login handler in admin-page.php
  → sn_setting_update('login.slug', 'backend2')
      ├── update_option('sn_settings', [...login.slug = backend2])
      ├── sn_setting_reset_cache()  ← busts static $merged
      └── re-read confirms value present
  → delete_option('sn_login_rewrites_flushed')  ← forces next-init flush
  → redirect to settings page (admin-post.php → wp_safe_redirect)

[Next request — any admin or public page]
  → init priority 10: add_rewrite_rule('^backend2/?$', 'wp-login.php', 'top')
  → init priority 99:
      ├── $current      = 'backend2'  (read via accessor — fresh, cache reset)
      ├── $flushed      = false       (option was deleted)
      ├── $rules_option = get_option('rewrite_rules')
      ├── $pattern      = '^backend2/?$'
      ├── $rule_present = isset($rules_option[$pattern])  → false (rule not yet persisted)
      ├── flush triggered:
      │     - WP's flush_rewrite_rules(false) deletes rewrite_rules option
      │     - WP_Rewrite::wp_rewrite_rules() rebuilds from in-memory $wp_rewrite
      │       (which has our add_rewrite_rule from priority 10)
      │     - rewrite_rules option now contains '^backend2/?$' → 'wp-login.php'
      └── update_option('sn_login_rewrites_flushed', 'backend2')

[Visitor hits /backend2 in incognito]
  → WP request parser checks rewrite_rules
  → '^backend2/?$' matches → 'wp-login.php'
  → wp-login.php renders (NOT blocked by wp_loaded handler at L120-164,
                          because REQUEST_URI is '/backend2', not '/wp-login.php')
```

## 7. Data flow (self-heal trigger from existing desync — the production bug)

```
[Pre-condition: sentinel says 'backend', but rewrite_rules option doesn't have rule]
[Visitor hits /backend]
  → 404 (rule not persisted)
[Any subsequent admin or public page load]
  → init priority 10: add_rewrite_rule('^backend/?$', ...) — in-memory only
  → init priority 99:
      ├── $current      = 'backend'
      ├── $flushed      = 'backend'  (sentinel matches!)
      ├── $rule_present = false      (NEW CHECK catches the desync)
      ├── ($flushed !== $current || ! $rule_present) → true → flush
      └── sentinel stays 'backend' (no-op write since matches)

[Next visit to /backend]
  → Rule now persisted → wp-login.php renders → login works
```

## 10. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| Self-heal flushes on every request if `rewrite_rules` option is genuinely empty (cold cache) | Low | Flushes once; sentinel updates; subsequent requests see sentinel match + rule present → no-op |
| `sn_setting_update()` creates a circular dep with the accessor | Low | Helper writes via `update_option` directly + busts cache; doesn't call `sn_setting()` |
| `sn_setting()` refactor for cache-reset sentinel breaks existing 459 tests | Medium | Sentinel path `__sn_reset_cache__` is namespace-safe (double-underscore prefix); no existing call would use it |
| Retention setting < 7 days bypasses min via direct DB edit | Low | Display only — cron prune impl clamps `max(7, min(365, ...))` defensively |
| CSS modifier breaks visual layout of Insights/cron forms | Medium | Modifier value `display:inline-block` matches current inline style; zero visual diff expected. Verify with screenshots. |
| D-02 legacy URL redirect breaks an unknown bookmarked URL | Low | Audit explicitly identified `?page=sn-login` as the at-risk URL. Redirect target is the canonical tab URL — better than 404-silent on POST |
| Bug fix doesn't actually fix the production /backend break | High → mitigated by live verification gate | Live smoke test on juanlentino.com is a verification gate before tag push |

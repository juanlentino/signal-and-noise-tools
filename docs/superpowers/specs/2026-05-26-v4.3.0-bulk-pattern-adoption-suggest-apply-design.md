## 1. Headline

**Zero-AI structural-block upgrade Suggest+Apply for two of the three v9.2.0 patterns: pull-quote and steps-enumerated.** v4.3.0 scans every published `/notes` post for existing `core/quote` blocks (upgrade candidates for the pull-quote pattern) and ordered `core/list` blocks (upgrade candidates for steps-enumerated), surfaces a per-post review queue in the Health tab's new "Opportunities" sub-section, and applies user-accepted upgrades via fingerprint-validated `parse_blocks ↔ serialize_blocks` round-trip. On-demand scanning only. No cron, no AI calls anywhere in the v4.3.0 module.

**Compare-columns is deliberately excluded** from v4.3.0 detection — it has no structural antecedent in raw HTML (no `<vs-columns>` block to upgrade from), requires prose-detection (regex/AI on paragraph content), and apply is INSERT rather than REPLACE. The pattern stays available in the block inserter for new posts; bulk retroactive adoption simply doesn't ship for it.

Reuses the v4.0.x Suggest+Apply infrastructure (fingerprint conventions, Health-tab UX, `assets/health-suggest-actions.js`) — same shape, new detection target.

## 2. Why this minor exists

User explicitly raised retroactive pattern adoption need during v9.2.0 brainstorming ("the existant published and scheduled notes have all the new stuff") — initially deferred bulk automation in favor of manual adoption as posts get edited over time. v4.3.0 ships the automation if manual adoption proves tedious or if the writer wants a deliberate audit pass.

The strategic value: this completes the v4.0.x "AI-assisted content-health suite" from "find problems" to "find opportunities." Existing checks (alt-text-missing, drift-phrase-outdated, orphan-media) flag REGRESSIONS; v4.3.0 flags ENHANCEMENTS. Same review-queue UX, opposite intent.

**Note on the "AI-assisted" framing:** the prior draft of this spec was titled "AI-assisted bulk pattern-adoption Suggest+Apply." That framing was misleading. The v4.3.0 module ships with **zero AI calls** in the detector and suggest paths — detection is heuristic (block-tree walks); suggest is deterministic template substitution. This rewrite drops the "AI-assisted" label to keep the headline honest. Future minors (v4.4.0 or post-v5.0.0) may extend to AI-driven prose detection for compare-columns or other patterns; v4.3.0 is structural-only.

## 3. Locked decisions (was: 6 open questions)

The 6 open questions from the prior draft are locked. Decision audit:

| # | Question | Decision | Rationale |
|---|---|---|---|
| 1 | Pull-quote detection: heuristic vs AI vs hybrid? | **Heuristic-only** (`core/quote` block upgrade) | Existing `<blockquote>` blocks have ~100% precision as upgrade candidates (a writer who tagged something as a blockquote already considered it quote-worthy). AI prose-detection adds API cost + drift risk + threshold-tuning complexity without proportional value. Respect the writer's structural tagging choice — paragraphs they chose NOT to blockquote, they don't want pulled out. |
| 2 | Compare-columns aggressiveness? | **DROPPED** from v4.3.0 detection | No structural antecedent in raw HTML (unlike `core/quote` and `core/list`, there's no existing block that maps cleanly to "this should be a two-column comparison"). Prose-detection slippery slope (regex for "X vs Y" has high false-positive rate). Apply is INSERT, not REPLACE — requires choosing a structural split point in a paragraph, with worse failure modes. Single highest-value post (Provenance Over Detection) is manually convertible in 5 minutes; building 150-300 LOC of detect+suggest+apply infra to surface that one candidate is a poor ratio. Pattern stays in inserter for new posts. |
| 3 | Steps-enumerated scope: `<ol>` only vs prose-detection? | **`<ol>` upgrades only** (`core/list` with `ordered: true`) | Mirror of Q1 logic. Respect the writer's structural choice — prose with "First, … Second, … Third, …" in flowing narrative was an active choice, not a missed opportunity for a list. Title-keyword heuristics ("Five layers" → assume the post wants enumeration) have unacceptable false-positive rates. |
| 4 | UX placement: Health tab vs new Insights sub-tab? | **Health tab merge**, "Opportunities" sub-heading, collapsed-by-default | Reuses `assets/health-suggest-actions.js` verbatim (zero new JS). Avoids the submenu/in-page-tab count parity issue from desktop-mode portal integration. Health-vs-Insights split is operational vs analytical — pattern adoption is actionable, so it belongs with Health. Conceptual concern (Health implies "fixing" but pattern adoption is editorial) is solved via visual sub-heading ("OPPORTUNITIES" vs "PROBLEMS") inside the same tab. Collapsed-by-default rendering keeps Problems urgent; Opportunities discoverable but not noisy. |
| 5 | Apply safety: byte-offset vs different model? | **Block-markup md5 fingerprint, no byte offsets** | Q1-Q3 collapsed v4.3.0 scope to structural-replace only (no INSERT). `parse_blocks ↔ serialize_blocks` is WP's canonical block round-trip — operating on block-tree nodes sidesteps the entire v4.1.1 raw-vs-stripped coordinate bug class that the drift impl had to engineer around. Fingerprint = `md5(serialize_block($node))`. Apply: re-parse, locate by fingerprint, mutate node in place, serialize, `wp_update_post`. |
| 6 | Scan cadence: one-off vs recurring cron? | **On-demand only**, persistent dismiss state | Opportunities don't degrade over time — a `<blockquote>` candidate today is still a candidate next week. Background cron scans add load for a feature checked rarely. Matches brutalist site's "no schedules, no nags" posture (cf. `/notes` subscribe copy: "No subscription form. No schedule."). New posts use the inserter for active pattern choice; the bulk scanner is for *existing* content only. Dismiss state persists in post meta — a writer's "decline this candidate" sticks across rescans. |

```

     │   └── steps-enumerated: extract <li> items from core/list
     │                          → render as patterns/steps-enumerated.php markup string
     └── return { suggestion_markup, fingerprint, post_id, pattern_type }
  ↓

  ↓

  → snt_pattern_adoption_apply_impl()
     ├── capability check: current_user_can('edit_post', $post_id)
     ├── load post, parse_blocks
     ├── walk tree, locate block by fingerprint match
     ├── if not found: WP_Error('snt_pattern_adoption_conflict', 409)
     ├── replace node in tree (mutate in place: $block = parse_blocks($replacement)[0])
     ├── serialize_blocks($modified_tree) → new post_content
```

### 5.3 Apply safety model (the load-bearing simplification)

The v4.1.1 drift-phrase impl had to engineer around byte-offset / stripped-vs-raw coordinate mismatches because phrase detection operates on **prose inside blocks**. v4.3.0 operates on **whole block nodes** — the natural coordinate system is the block tree itself, not character offsets. The entire apply path is:

```php
function snt_pattern_adoption_apply_impl( $post_id, $fingerprint, $replacement_markup, $pattern_type ) {
    // (input validation + capability check omitted for brevity — see snt_ai_drift_apply_impl
    // for the pattern: trim, length check, capability gate, post-existence gate)

    $post   = get_post( $post_id );
    $blocks = parse_blocks( $post->post_content );
    $found  = false;

    $walk = function( &$tree ) use ( &$walk, $fingerprint, $replacement_markup, &$found ) {
        foreach ( $tree as &$block ) {
            if ( md5( serialize_block( $block ) ) === $fingerprint ) {
                $block = parse_blocks( $replacement_markup )[0]; // mutate node in place
                $found = true;
                return;
            }
            if ( ! empty( $block['innerBlocks'] ) ) {
                $walk( $block['innerBlocks'] );
                if ( $found ) return;
            }
        }
    };
    $walk( $blocks );

    if ( ! $found ) {
        return new WP_Error( 'snt_pattern_adoption_conflict', __( 'Block changed since scan. Re-run scan.', 'signal-noise-tools' ), [ 'status' => 409 ] );
    }

    $new_content = serialize_blocks( $blocks );
    $result      = wp_update_post( [ 'ID' => $post_id, 'post_content' => $new_content ], true );
    if ( is_wp_error( $result ) ) {
        return new WP_Error( 'snt_pattern_adoption_write_failed', sprintf( __( 'wp_update_post failed: %s', 'signal-noise-tools' ), $result->get_error_message() ), [ 'status' => 500 ] );
    }

    return [ 'ok' => true, 'post_id' => $post_id, 'replaced_pattern_type' => $pattern_type ];
}
```

**Conflict cases:**
- Block edited between scan and apply → `serialize_block($node)` produces different markup → fingerprint mismatch → 409
- Block deleted between scan and apply → no node matches → 409
- Post deleted → 404 (caught by `get_post()` returning null)
- Capability lost (rare) → 403

**B-06 acknowledged tradeoff carries over:** `wp_update_post()` triggers downstream WP save-hook fanout (post-save indexing, cache busts, revision creation, any save_post listeners). The md5 fingerprint is the mitigation — if post_content has shifted, we return WP_Error instead of writing. Hook fanout cost is proportional to the number of applies, which is small (handful per scan cycle).

### 5.4 Suggest implementation: deterministic template substitution

**Critical correction (post-code-review, 2026-05-26):** the v9.2.0 theme patterns `signal-noise/pull-quote` and `signal-noise/steps-enumerated` are **WordPress static patterns** registered via `patterns/*.php` header-comment metadata — they are NOT registered block types. The `Block Types: core/quote` header in those pattern files declares the source-block transform link (used by the editor's right-click "Transform to →" menu), but the pattern itself is composed of CORE BLOCKS (`core/group`, `core/paragraph`, `core/list`, `core/list-item`) with className markers.

Therefore, the suggest impl must emit **core-block-composed markup**, not `<!-- wp:signal-noise/pull-quote -->` (which is not a parseable block type and would render as "unexpected or invalid content" in the editor).

**Pull-quote target markup** (mirrors `signal-and-noise/patterns/pull-quote.php`):

```html
<!-- wp:group {"className":"sn-pattern-pull-quote","tagName":"aside","layout":{"type":"constrained"}} -->
<aside class="wp-block-group sn-pattern-pull-quote">
<!-- wp:paragraph {"className":"sn-pull-quote__body"} -->
<p class="sn-pull-quote__body">{QUOTE_TEXT}</p>
<!-- /wp:paragraph -->
<!-- wp:paragraph {"className":"sn-pull-quote__attribution"} -->
<p class="sn-pull-quote__attribution">{CITE_TEXT}</p>
<!-- /wp:paragraph -->
</aside>
<!-- /wp:group -->
```

- Source: `core/quote` with `innerBlocks` of `core/paragraph` + optional `<cite>` in `innerHTML`
- `{QUOTE_TEXT}`: concatenation of all `core/paragraph` `innerHTML` values, stripped of `<p>` wrapper, with inline formatting preserved (`<strong>`, `<em>`, `<a>`, `<code>`) via `wp_kses` allowlist
- `{CITE_TEXT}`: contents of `<cite>` extracted from the quote's wrapper `innerHTML` (regex), with same `wp_kses` allowlist. **The attribution paragraph is OMITTED entirely if no `<cite>` is present in the source.**
- **No auto-added quotation marks or em-dashes.** The pattern file's literal placeholders (`"..."` and `— ...`) are display sugar for the empty-pattern preview; transforms preserve the writer's source content verbatim.

**Steps-enumerated target markup** (mirrors `signal-and-noise/patterns/steps-enumerated.php`):

```html
<!-- wp:group {"className":"sn-pattern-steps-enumerated","layout":{"type":"constrained"}} -->
<div class="wp-block-group sn-pattern-steps-enumerated">
<!-- wp:list {"ordered":true,"className":"sn-steps__list"} -->
<ol class="wp-block-list sn-steps__list">
<!-- wp:list-item -->
<li>{ITEM_1}</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li>{ITEM_2}</li>
<!-- /wp:list-item -->
</ol>
<!-- /wp:list -->
</div>
<!-- /wp:group -->
```

- Source: `core/list` with `attrs.ordered === true`, containing `innerBlocks` of `core/list-item`
- `{ITEM_N}`: contents of each `core/list-item` `innerHTML`, stripped of `<li>` wrapper, with same `wp_kses` allowlist as pull-quote
- **The pattern's label paragraph (`<p class="sn-steps__label">`) is OMITTED** in the transform output. The source `core/list` has no concept of a label; inventing one (e.g., "Steps") would inject editorial content the writer didn't ask for. User adds a label manually after apply if desired. (Alternative considered: inherit from preceding heading — rejected as fragile coupling.)

**Important:** these are pure PHP string templates. **No AI involved.** The "suggest" in Suggest+Apply is the user reviewing a proposed change before applying it, not an AI generating a creative suggestion. The before/after modal carries the editorial weight.

**Maintenance coupling (new risk row in §7):** the hardcoded block markup templates in `inc/pattern-adoption-suggest.php` are coupled to the theme's pattern markup. If theme v9.4.0 redesigns either pattern (new className, new wrapper element, added/removed inner blocks), the suggest impl produces v9.2.0-shaped markup that won't match v9.4.0 styling. Each builder function should carry a comment pointing to the source pattern file in the theme.

## 7. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| Suggested replacement loses content from the original block (e.g., pull-quote omits the `<cite>` if extraction logic misses it) | Medium | Suggest impl uses extracted content from the source block verbatim; before/after modal shows full diff for user review before apply; tests cover citation-present and citation-absent cases |
| Fingerprint check fails because user edited the block between scan and apply | Low | Same mitigation as drift impl — return 409, JS prompts "re-run scan." Acceptable failure mode. |
| `serialize_block()` not deterministic across WP versions, causing fingerprint instability over time | Low | WP core convention is deterministic serialization; cross-version drift would be a core regression worth filing upstream. Transient TTL is 1h, so within-session drift is unlikely. |
| Block is inside a deprecated wrapper (e.g., a custom pattern) and upgrading produces weird nesting | Medium | Detector walks `innerBlocks` recursively and tracks block path; admin UI shows post permalink + block context so user can dismiss if it looks wrong before applying. |
| Pattern source changes in a future theme version (e.g., v9.4.0 redesigns pull-quote) | Low | Block patterns don't update existing usages anyway — applied posts get the OLD pattern markup, new applies get the new. Standard WP block-pattern behavior; no special handling needed. |
| Suggest impl's hardcoded markup templates drift from theme pattern files | Medium | The two builder functions in `inc/pattern-adoption-suggest.php` hold v9.2.0-shaped markup verbatim. If theme v9.4.0 changes pattern className or structure, the suggest produces markup that doesn't match new styling. Mitigation: docblock comment in each builder pointing to source pattern file; quarterly review of theme/`patterns/*.php` vs plugin builder code; consider future v5.0.0 work to refactor toward reading pattern file at runtime (with template-substitution syntax) to eliminate the duplication. |
| Suggest emits unregistered block type slugs (caught in code review of Task 2 b453112) | RESOLVED in remediation | Initial impl emitted `<!-- wp:signal-noise/pull-quote -->` as block-comment delimiters — but `signal-noise/pull-quote` is a pattern slug, not a registered block type. WP would mark applied content as "unexpected or invalid". Fix: emit core-block compositions matching the theme pattern files. Documented in §5.4 with explicit target markup. |
| User runs scan during high site load (lots of posts, slow DB) | Low | Scan runs synchronously in the initiating request; if timeout, user retries. Current /notes corpus (~10s of posts) doesn't stress this. Future optimization: chunked scanning via background job if scale demands. |
| Pattern-adoption surface invites scope creep ("auto-tag posts", "auto-link essays", "scan pages too") | Medium | Spec EXPLICITLY scopes to 2 patterns + structural-replace only + post_type=post only. New detection targets need a separate minor brainstorm + cap-pressure reckoning (v4.4.0 is the last minor before v5.0.0). |
| Hook fanout from `wp_update_post` triggers expensive side effects (cache busts, search reindex, etc.) | Low (B-06 acknowledged) | Inherited acknowledgment from v4.0.x. Cost is proportional to applies, which is small. Same tradeoff as drift impl. |

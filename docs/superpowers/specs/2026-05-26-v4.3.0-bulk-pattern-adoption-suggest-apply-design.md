## 1. Headline

**AI-assisted Suggest+Apply for retroactively adopting the 3 new v9.2.0 patterns across all existing /notes posts.** The /notes catalog has ~10+ posts written before v9.2.0 shipped patterns; without retroactive adoption, the patterns only benefit future posts. v4.3.0 scans every existing post, identifies content that would benefit from `pull-quote` / `compare-columns` / `steps-enumerated`, surfaces suggestions in an Insights-tab review queue, user accepts/declines per suggestion, accepted ones get spliced into post_content via `wp_update_post` with fingerprint-based safety.

Reuses the v4.0.x Suggest+Apply infrastructure (alt-text, drift-phrase, orphan-media) — same pattern, new detection target.

---

## 2. Why this minor exists

User explicitly raised this need during v9.2.0 brainstorming ("the existant published and scheduled notes have all the new stuff") — but consciously deferred bulk automation in favor of manual adoption as posts get edited over time. v4.3.0 ships the automation if manual adoption proves tedious.

The strategic value: this completes the "v4.0.x AI-assisted content-health suite" from "find problems" to "find opportunities." Existing checks (alt-text-missing, drift-phrase-outdated, orphan-media) flag REGRESSIONS; bulk pattern-adoption flags ENHANCEMENTS. Same review-queue UX, opposite intent.

## 3. Investigation needed during kick-off brainstorm

Open questions to resolve before writing the plan:

1. **Detection heuristics — pull-quote candidates:**
   - Naive: any `<blockquote>` block in post_content (would be a candidate to upgrade to the new pattern).
   - Sharper: AI scans paragraphs, flags lines that read like thesis statements (declarative, short, summative — e.g., "The classifier always loses on cost before it loses on accuracy"). Higher recall, lower precision; needs review queue to filter.
   - **Decision needed:** heuristic-based scan (zero AI cost), AI-scored scan (slow + costs API calls), or hybrid (heuristic first-pass + AI confidence scoring)?

2. **Detection heuristics — compare-columns candidates:**
   - Pattern hints: paragraphs that mention "X vs Y" or "X versus Y", paragraphs immediately following a sub-heading that names a contrast (e.g., "## A vs B").
   - Risk: false positives are CHEAP to dismiss (user clicks "decline"), false negatives are EXPENSIVE (user misses an opportunity).
   - **Decision needed:** how aggressive should detection be? Bias toward more suggestions (some noise) or fewer suggestions (some misses)?

3. **Detection heuristics — steps-enumerated candidates:**
   - Pattern hint: existing `<ol>` blocks (ordered lists) — straightforward upgrade.
   - Stretch: posts with "Five layers", "Five years", "Three" etc. in their title (enumerative voice) might have manually-numbered prose that should be ordered lists.
   - **Decision needed:** scope to `<ol>` upgrades only (simple, high confidence) or extend to prose-detection (rich, low confidence)?

4. **Suggest+Apply UX placement:**
   - Reuse the existing `inc/health-checks-admin.php` Health tab pattern? (Goes alongside alt-text, drift, orphan-media checks.)
   - Or new dedicated tab: "Pattern adoption" under Insights?
   - **Decision needed:** dedicated tab or merge into Health checks.

5. **Apply safety:** v4.0.x established the md5 fingerprint pattern for safe content splicing. Does the same approach work when SUBSTITUTING a `<blockquote>` for a `<pre-existing-blockquote>` vs INSERTING a new pattern into a paragraph location?
   - **Decision needed:** structural-replace (`<blockquote>` → pull-quote pattern) is straightforward. INSERT requires choosing a position — different safety model.

6. **One-off run vs recurring scan:**
   - One-off: scan once, surface suggestions, done. Doesn't re-scan after user dismisses.
   - Recurring: weekly cron scan, surfaces NEW candidates (e.g., user wrote a new post; pillar-link still uses raw `<ol>`; suggester says "convert to steps-enumerated?").
   - **Decision needed:** one-off (simpler) or recurring (matches existing Health-check pattern).

## 5. Architecture

### 5.1 Module layout

Mirrors the v4.0.x Suggest+Apply pattern:

```
inc/pattern-adoption-detect.php    — find candidates (DB scan)
inc/pattern-adoption-suggest.php   — generate replacement block markup
inc/pattern-adoption-apply.php     — splice into post_content (fingerprint-safe)
inc/pattern-adoption-admin.php     — admin UI (review queue + per-suggestion actions)
inc/abilities-pattern-adoption.php — register AI ability for the suggester (if AI path chosen)
```

5 new files, each ~100-200 LOC. Total module: ~600-900 LOC. Plus tests (~200 LOC) and CHANGELOG/version (~30 LOC).

### 5.2 Data flow

```
[Admin clicks "Scan for pattern opportunities"]
  → snt_pattern_adoption_run_scan() (the detector)
     ├── For each /notes post:
     │   ├── parse_blocks( $post_content )
     │   ├── walk block tree → identify candidate matches per pattern
     │   └── store candidates in pattern-adoption queue table (or transient + option)
  → admin UI renders the review queue
  → User clicks "Suggest" on a candidate
     ├── snt_pattern_adoption_suggest_for_candidate()
     ├── If AI-path: calls AI client to generate the replacement markup
     └── If heuristic-path: synthesizes the replacement markup directly
  → User reviews → "Accept" or "Decline"
     ├── Accept → snt_pattern_adoption_apply_to_post()
     │   ├── fingerprint check (md5 of original markup at position)
     │   ├── splice replacement into post_content
     │   ├── wp_update_post()
     │   └── log to audit log
     └── Decline → mark candidate as dismissed (no re-suggest unless force-rescan)
```

### 5.3 Patterns this DOESN'T fit cleanly

- **Auto-apply (no review):** intentionally NOT supported. Pattern adoption is editorial — every change is a judgment call. No "fix all" button. Same philosophy as v4.0.x.
- **Cross-post pattern enforcement** (e.g., "every post must end with a steps-enumerated"): out of scope. The 3 patterns are opt-in editorial choices, not enforced conventions.

### 5.4 Reuses v4.0.x infrastructure

- `snt_ai_drift_fingerprint()` style fingerprint check (md5 of content at position).
- Health-check admin tab pattern for the review queue (if §3.4 picks "merge into Health").
- AI client integration via the existing `Prompt_Builder` flow (if §3.1 picks AI scoring).
- Suggest+Apply JS (`assets/health-suggest-actions.js`) for the per-suggestion accept/decline UX.

## 6. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| AI suggestions feel wrong or generic (e.g., upgrades the wrong blockquote) | Medium | Confidence threshold setting (user can tune); decline is cheap; per-suggestion review (no bulk auto-apply) |
| Fingerprint check fails after a post was edited between scan and apply | Low | Same v4.0.x mitigation — return WP_Error, user re-scans |
| Suggested replacement breaks the post visually (e.g., pull-quote replaces inline `<q>` instead of standalone `<blockquote>`) | Medium | Detector limits to structural blocks (`<blockquote>` outside paragraph context); manual review surfaces edge cases |
| Recurring scan adds noise after every new post | Low | If §3.6 picks recurring, default to weekly cron + suppress already-dismissed candidates |
| User triggers full scan during high site load; AI calls + DB writes spike | Low | Scan runs as a background cron job (not on click); admin UI shows "in progress" then refreshes |
| Pattern-adoption surface invites scope creep (next: "auto-detect pillar links", "auto-tag posts", etc.) | Medium | Spec EXPLICITLY scopes to 3 patterns. New detection targets need a separate minor brainstorm. |

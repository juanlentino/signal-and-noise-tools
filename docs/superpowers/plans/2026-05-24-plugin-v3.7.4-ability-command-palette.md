# Plugin v3.7.4 — Theme Ability Command Palette Implementation Plan

> **⚠️ SUPERSEDED 2026-05-24.** This plan is preserved as a historical record. It is NOT to be executed. The successor spec is [`docs/superpowers/specs/2026-05-24-plugin-v3.8.0-anthropic-provider-design.md`](../specs/2026-05-24-plugin-v3.8.0-anthropic-provider-design.md). Reason for supersession: this plan built on incomplete knowledge of desktop-mode's architecture — it bypassed the AI Copilot via `window.prompt()` UX, missed that `desktop_mode_register_command()` strips extra fields outside its 6-key schema (per [WordPress/desktop-mode includes/commands.php:145-153](https://github.com/WordPress/desktop-mode/blob/trunk/includes/commands.php#L145)), and didn't know about `desktop_mode_register_ai_tool()` (since 0.17.0) or `desktop_mode_register_ai_provider()` (since 0.18.0). v3.8.0 replaces this with the proper architecture: register Anthropic as a desktop-mode AI provider + register 26 of our 29 abilities as AI tools with structured JSON-Schema parameters.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add 12 Command Palette (⌘K) commands to the signal-and-noise-tools plugin that dispatch to the theme-registered abilities from theme v9.1.0. Adds a new `input-then-result` render mode to `assets/desktop-mode.js` for the 7 commands that need an input form (the remaining 5 use the existing `result-panel` shape).

**Architecture:** Patch release — no new abilities, no new plugin functionality beyond the Command Palette surface. PHP side: extend `inc/desktop-mode-integration.php` with 12 new command entries (each with an `'ability' => 'signal-and-noise/...'` field pointing at a theme-registered ability + a `'render_mode'` + optional `'input_fields'`). JS side: extend `assets/desktop-mode.js` to handle the `input-then-result` render mode (input form → submit → ability dispatch via `/wp-abilities/v1/abilities/<slug>/run` → result display). All 12 commands set `aiCallable: true` for AI Copilot consumption. Distribution per spec §11.1: 5 commands use `result-panel` (read abilities with no input); 7 commands use the new `input-then-result` (2 read abilities with required input + 5 generative AI calls).

**Tech Stack:** PHP 8.0+, JavaScript (Command Palette commands are registered server-side via `desktop_mode_register_command()` per the existing 15-command pattern; run callbacks live on the JS side via `wp.desktop.registerCommand()` — see CLAUDE memory `reference_command_palette_js_only` for the generic WP 7.0 commands API, but THIS plugin uses desktop-mode's own command surface). WordPress 7.0+ (Abilities API at `/wp-abilities/v1/abilities/<namespace>/<slug>/run`). Standalone PHP test harness (matches existing `tests/health-checks.php` pattern).

**Theme dependency:** This plan assumes theme v9.1.0 has shipped (or is shipping in parallel) and registers the 12 abilities listed in spec §11.1. If theme v9.1.0 is NOT installed when plugin v3.7.4 lands, ⌘K command registration still succeeds — invocations will return WP's standard "ability not found" REST error until theme updates. This is the documented failure mode per spec §3.

```javascript

	/* ── v3.7.4: Theme-ability commands (12 total) ──────────────────────────
	 *
	 * All 12 commands dispatch to abilities REGISTERED IN THE THEME
	 * (signal-and-noise v9.1.0+). The plugin side is pure surface layer:
	 *   - PHP registers the ⌘K commands (data + metadata)
	 *   - JS handles invocation (this block)
	 *
	 * REST endpoint: /wp-abilities/v1/abilities/<namespace>/<slug>/run
	 * (see assets/command-palette.js:128-132 — abilities-api docs are
	 * wrong; implementation has the extra /abilities/ segment).
	 *
	 * v3.7.1 lesson: every catch site logs to console.error AND shows
	 * a user-visible toast. Silent failures are the worst bug class.
	 *
	 * If theme v9.1.0 is not installed, REST returns 404 "ability not
	 * found" — caught by the catch site, toasted as an error with
	 * remediation hint. No fatal.
	 * ─────────────────────────────────────────────────────────────────── */

	/**
	 * Generic abilities-API REST dispatcher.
	 *
	 * @param {string} abilitySlug e.g. 'signal-and-noise/get-design-tokens'
	 * @param {object|null} input  Input payload matching the ability's input_schema.
	 *                             Pass null for no input.
	 * @returns {Promise<any>}     Resolves with the ability's output payload,
	 *                             rejects with WP_Error JSON.
	 */
	function executeAbility( abilitySlug, input ) {
		if ( ! window.wp.apiFetch ) {
			return Promise.reject( new Error( 'wp.apiFetch unavailable' ) );
		}
		// POST verb for all 12 theme-ability commands — none are read-only
		// in the abilities-api sense (read-only abilities use GET, but the
		// 7 "read" abilities in this batch still take optional input, and
		// for consistency we POST every theme-ability invocation; the
		// abilities-api accepts POST for any ability).
		var path = '/wp-abilities/v1/abilities/' + abilitySlug + '/run';
		var opts = { path: path, method: 'POST' };
		if ( input !== null && input !== undefined && typeof input === 'object' && Object.keys( input ).length > 0 ) {
			opts.data = { input: input };
		}
		return window.wp.apiFetch( opts );
	}

	/**
	 * Format an ability's response payload as a readable toast or
	 * inline string. We default to JSON pretty-print for now;
	 * post-v3.7.4 patches can specialize per-ability formatters.
	 *
	 * @param {*} res The raw response from the abilities-api REST endpoint.
	 * @returns {string} A human-readable summary.
	 */
	function formatAbilityResult( res ) {
		if ( res === null || res === undefined ) {
			return 'Ability returned no data.';
		}
		if ( typeof res === 'string' ) {
			return res;
		}
		try {
			var json = JSON.stringify( res, null, 2 );
			// Truncate at 800 chars for toast readability; full result still
			// visible in the browser console via the run() call.
			if ( json.length > 800 ) {
				return json.substring( 0, 800 ) + '\n…(truncated; see console)';
			}
			return json;
		} catch ( err ) {
			return String( res );
		}
	}

	/**
	 * Render mode: result-panel.
	 *
	 * Dispatch the ability with no input; display the result via toast.
	 *
	 * @param {string} slug         ⌘K command slug (for log messages)
	 * @param {string} abilitySlug  Theme-registered ability namespace/slug
	 */
	function runResultPanel( slug, abilitySlug ) {
		// eslint-disable-next-line no-console
		console.log( '[SN] runResultPanel:', slug, '→', abilitySlug );
		executeAbility( abilitySlug, null )
			.then( function( res ) {
				// eslint-disable-next-line no-console
				console.log( '[SN] ability response:', abilitySlug, res );
				toast( formatAbilityResult( res ), 'info' );
			} )
			.catch( function( err ) {
				// v3.7.1 lesson: log + visible toast on every catch.
				// eslint-disable-next-line no-console
				console.error( '[SN] ability failed:', abilitySlug, err );
				var msg = ( err && err.message ) ? err.message : 'Ability call failed';
				// Detect "ability not found" → user-friendly remediation hint.
				if ( err && err.code === 'rest_no_route' ) {
					msg = 'Ability ' + abilitySlug + ' not found. Update theme to v9.1.0+.';
				}
				toast( 'SN command failed: ' + msg, 'error' );
			} );
	}

	/**
	 * Render mode: input-then-result.
	 *
	 * Build a small input form (one row per field), prompt the user via
	 * window.prompt() for each field (sequential), then dispatch the
	 * ability with the collected input and show the result.
	 *
	 * Why prompt() and not a real modal: desktop-mode does not expose a
	 * "show input modal" JS API, and adding HTML/CSS form scaffolding to
	 * this file would push it past the 150-line CLAUDE guideline by a
	 * larger margin. window.prompt() is sequential, accessible, available
	 * in every browser, and zero CSS. Post-v3.7.4 patch can replace with
	 * a richer overlay if the UX is too sparse.
	 *
	 * Cancelling any prompt (Esc / Cancel button) aborts the whole flow.
	 *
	 * @param {string} slug          ⌘K command slug (for log messages)
	 * @param {string} abilitySlug   Theme-registered ability namespace/slug
	 * @param {Array<string>} fields Ordered field names per the ability's input_schema
	 */
	function runInputThenResult( slug, abilitySlug, fields ) {
		// eslint-disable-next-line no-console
		console.log( '[SN] runInputThenResult:', slug, '→', abilitySlug, 'fields:', fields );
		var input = {};
		for ( var i = 0; i < fields.length; i++ ) {
			var field = fields[ i ];
			var val = window.prompt( 'SN ' + slug + ' — ' + field + ':', '' );
			if ( val === null ) {
				// User cancelled — abort.
				toast( 'SN command cancelled.', 'info' );
				return;
			}
			// Empty string is treated as "field not provided" — let the
			// ability's input_schema validation decide if that's an error.
			// For numeric fields the abilities-api will coerce/reject as needed.
			if ( val !== '' ) {
				// Light type coercion: numeric-looking strings → numbers.
				// The abilities-api JSON-decodes the request body, so primitives
				// must be the right type for type:integer/number schemas.
				if ( /^-?\d+$/.test( val ) ) {
					input[ field ] = parseInt( val, 10 );
				} else if ( /^-?\d*\.\d+$/.test( val ) ) {
					input[ field ] = parseFloat( val );
				} else {
					input[ field ] = val;
				}
			}
		}
		executeAbility( abilitySlug, input )
			.then( function( res ) {
				// eslint-disable-next-line no-console
				console.log( '[SN] ability response:', abilitySlug, res );
				toast( formatAbilityResult( res ), 'info' );
			} )
			.catch( function( err ) {
				// v3.7.1 lesson: log + visible toast on every catch.
				// eslint-disable-next-line no-console
				console.error( '[SN] ability failed:', abilitySlug, err );
				var msg = ( err && err.message ) ? err.message : 'Ability call failed';
				if ( err && err.code === 'rest_no_route' ) {
					msg = 'Ability ' + abilitySlug + ' not found. Update theme to v9.1.0+.';
				}
				toast( 'SN command failed: ' + msg, 'error' );
			} );
	}

	// Register the 12 theme-ability commands. All set aiCallable: true per
	// spec §11.3. The data flows from PHP via snDesktopData.themeAbilityCommands
	// (Task 4 — wp_localize_script in inc/desktop-mode-integration.php).
	var themeCommands = ( data.themeAbilityCommands || [] );
	for ( var t = 0; t < themeCommands.length; t++ ) {
		( function( cmd ) {
			var bindOpts = {
				slug: cmd.slug,
				aiCallable: true,
				run: function() {
					if ( cmd.render_mode === 'input-then-result' ) {
						runInputThenResult( cmd.slug, cmd.ability, cmd.input_fields || [] );
					} else {
						runResultPanel( cmd.slug, cmd.ability );
					}
				},
			};
			window.wp.desktop.registerCommand( bindOpts );
		} )( themeCommands[ t ] );
	}
```

#### New render mode: `input-then-result`

The existing 17 commands fall into the existing render shapes (REST→toast for maintenance, navigation, info-toast). The new 12 theme-ability commands introduced a fourth shape: input form → ability dispatch → result display. The new `input-then-result` render mode handles this.

Implementation: sequential `window.prompt()` for each field in the ability's `input_fields`, light type coercion (numeric strings → numbers so type:integer schemas don't reject), POST to `/wp-abilities/v1/abilities/<namespace>/<slug>/run`, then toast the result via JSON pretty-print (truncated at 800 chars for readability; full payload in browser console).

Rationale for `window.prompt()` over a real modal: desktop-mode doesn't expose a "show input modal" JS API; building one would push `assets/desktop-mode.js` further past the 150-line CLAUDE guideline and add CSS scaffolding. Prompt-based UX is functional + accessible + zero-CSS. Post-v3.7.4 patch can replace with a richer overlay if the UX is too sparse for daily use.

#### WP-CLI access (free, automatic)

WordPress 7.0's Abilities API exposes every registered ability to `wp-cli` without per-ability code. Once theme v9.1.0 is installed:

```bash
# List all 12 theme abilities
wp ability list | grep signal-and-noise/

# Run a read ability (no input)
wp ability run signal-and-noise/get-design-tokens

# Run with input
wp ability run signal-and-noise/ai-rewrite-in-brand-voice \
  --input='{"source_text":"...","intensity":"medium"}'

# Filter by category
wp ability list --category=diagnostics
wp ability list --category=ai-generation
```

No plugin code required — registration alone enables CLI access. Same dispatch path as the ⌘K commands above + the desktop-mode AI Copilot.

#### Error handling (the v3.7.1 lesson applied to JS)

Every async `.catch()` in the new `runResultPanel()` and `runInputThenResult()` helpers does THREE things:

1. `console.error` with the failing ability slug + error object (developer visibility)
2. User-visible `toast()` with a human-readable message (user visibility)
3. Special-case for `rest_no_route` (the "ability not found" code) → remediation hint: "Update theme to v9.1.0+."

Silent JS failures were the v3.7.1 bug class. Instrumenting every catch site means future regressions surface in the browser console immediately instead of being invisibly swallowed.

#### Theme dependency

**Theme Required: signal-and-noise 9.1.0+.** The 12 ⌘K commands register cleanly on any WordPress 7.0+ install regardless of theme state, but invocations return REST 404 (`rest_no_route` → "Ability not found") until theme v9.1.0 lands. The catch-site remediation hint above guides users to update the theme.

Ship order per spec §8: theme v9.1.0 first, plugin v3.7.4 second. If you're reading this CHANGELOG entry and theme is older than 9.1.0, this entry is documenting capabilities that aren't yet wired end-to-end.
